## La réécriture (`Instrumenter`)

```kotlin
object Instrumenter {
    fun rewrite(mainClass: String, classes: Map<String, ByteArray>): Map<String, ByteArray>  // mêmes noms binaires + "<Main>$-meter"
    val rewritten: List<RewrittenMember>   // owner, name, descriptor : les membres du JDK envoyés à Guarded
}
class RewriteRefused(message: String) : RuntimeException(message)  // message pour le Forgeron, en anglais
```

ASM, `ClassWriter(reader, COMPUTE_MAXS)`, cadres passés tels quels : aucune insertion n'ajoute de branchement ni ne
touche aux variables locales. Fonction pure, sans état (un cache des classes du JDK par nom), sûre sur le fil du
compilateur.

| Insertion | Où |
|---|---|
| classe porteuse `<Main>$-meter` | `public final synthetic`, un champ `public static Meter m` (non `final` : l'hôte le pose par réflexion), **aucune méthode** (rien ne tourne avant que l'hôte pose le compteur) ; version de classe du module |
| `m.enter()` | entrée de chaque méthode (et de chaque pont) |
| `m.exit()` | avant chaque `xRETURN` |
| `m.tick()` | avant chaque saut **ou `switch`** vers une étiquette déjà vue, et **à l'entrée de chaque gestionnaire d'exception** (après son étiquette et son cadre) |
| `Guarded.array(n)` | avant `newarray`/`anewarray` |
| `Guarded.capacity(n)` | avant **tout** constructeur public à `int` de tête des types de `SandboxPolicy.CAPACITY_CTOR_TYPES`, l'argument atteint là où il est sur la pile (`swap` pour `(int, float)` et `(int, Comparator)`, `dup2_x1 pop2 … dup_x2 pop` pour `(int, float, boolean)`) |
| `Guarded.trusted(cs)` | avant `StringBuilder(CharSequence)` |
| un membre de `rewritten` | remplacé par la méthode statique de `Guarded` de même nom (receveur en premier pour une méthode d'instance), sur le propriétaire de la liste **ou un de ses sous-types** (`LinkedHashMap.newHashMap`, `ArrayList.add`, `Deque.addFirst`…) |
| `toString()` | sur **tout** type du JDK sauf `String`, `StringBuilder` et les boîtes → `Guarded.toString(Object)` |
| `invokedynamic` | `StringConcatFactory.makeConcatWithConstants` → `Guarded.concatenation` ; `ObjectMethods.bootstrap` pour `toString` → `Guarded.record` ; `LambdaMetafactory` : une **référence de méthode vers autre chose que le code du module** passe par un pont |

**Une seule source de vérité** (consigne du superviseur) : les capacités viennent de `SandboxPolicy` —
`CAPACITY_CTOR_TYPES` (tous leurs constructeurs publics à `int` de tête, lus par réflexion) et `CAPACITY_METHODS`
(toutes les surcharges publiques de chaque nom, lues par réflexion ; les ponts covariants qui nomment
`AbstractStringBuilder`, inaccessible, sont écartés). Ce que la garde permet et que **seule** la réécriture borne
(croissance, textes, vues) est la liste propre d'`Instrumenter`. Un test vérifie que chaque entrée de
`CAPACITY_*` est enveloppée et que chaque membre de `rewritten` existe dans le JDK et a son jumeau dans `Guarded`.

### Les ponts (références de méthode)

Une référence de méthode vers le JDK ou le SDK (`list::add`, `Object::toString`, `ArrayList::new`, `List::stream`,
`ctx::log`) ne passe par aucun site d'appel du module : la `LambdaMetafactory` appelle la cible directement. Sans
rien de plus, `IntStream.range(0, 20_000).boxed().forEach(list::add)` contournerait `Guarded.add`, et
`IntFunction<List<X>> f = ArrayList::new; f.apply(500_000_000)` la capacité. La réécriture remplace donc la poignée
d'implémentation par celle d'une méthode **privée statique synthétique** de la classe, `forge$bridge$N`, qui fait
l'appel et qui est réécrite comme le reste : l'appel passe par `Guarded`, et le pont **compte un `tick`** (son
`enter`). Conséquence : `all.stream().flatMap(List::stream).count()` sur 10 000 × 10 000 éléments est arrêté par le
compteur, alors que le JDK n'appelle aucun code du module. Les lambdas du module (`lambda$N`) n'en ont pas besoin. Les
poignées `REF_invokeSpecial` (`super::m`) restent telles quelles.

### Ce que la réécriture refuse (`RewriteRefused`)

| Refus | Pourquoi |
|---|---|
| une classe du module qui **est** une `Collection`, une `Map` ou un `CharSequence` (directement, par une interface à elle ou un super-type du JDK) | **écart** : la garde les permet (« une interface de la liste »). Le JDK croit leur `size()`/`length()` : `new HashSet<>(menteuse)` alloue la table de la taille annoncée au premier `add` (2 Gio pour 500 millions), `new ArrayDeque<>(menteuse)`, `putAll`, `stream().toArray()`, `Set.copyOf`, `menteur.chars().toArray()`… La liste de ces portes est sans fin ; refuser l'implémentation les ferme toutes. Un module garde une liste dans un champ. Testé : les trois modules menteurs passent la garde et sont refusés ici. |
| `multianewarray` | la garde le refuse déjà ; ici, défense en profondeur (les dimensions sont sous la pile, impossibles à borner sans variable locale) |
| un gestionnaire d'exception situé **dans son propre intervalle** | un compteur déclenché y lèverait de nouveau, sans fin (boucle d'exceptions sans `tick` qui avance). ECJ n'en produit pas (le témoin, le module « riche », les `try`/`finally` de la batterie passent) ; seul un bytecode fabriqué en a |
| du code qui nomme `<Main>$-meter` ou `forge.rt` ; une classe d'entrée nommée `<Main>$-meter` | seule la réécriture les nomme (constat 7, défense en profondeur avec la garde et le chargeur) |

**À M5-03 / au superviseur** : la garde pourrait refuser elle-même qu'une classe du module implémente
`Collection`/`Map`/`CharSequence` (un message plus tôt et plus clair pour le Forgeron) ; la réécriture le refuse de
toute façon.

## Le compteur (`Meter`) : le contrat final

- `Meter(owner)` : le chargeur du module (non nul).
- `arm(budgetNanos, allocationBytes)` remet tout à zéro ; `disarm()` termine l'appel. **Lisez `tripped()` après
  `disarm()`** : `disarm` vérifie une dernière fois l'horloge et l'allocation, et **déclenche sans lever** un appel
  qui a dépassé son budget **dans un seul appel du JDK** (aucun `tick` ne pouvait l'arrêter : une recherche de texte
  O(n·m), un tri, un hachage). L'hôte compte donc toujours une faute *limite* pour un appel trop long.
- `enter` compte comme un `tick` ; tous les `ForgeLimits.METER_CHECK_EVERY` (16) : `System.nanoTime` puis
  l'allocation (`com.sun.management.ThreadMXBean`, absent sans `jdk.management` : le temps borne seul).
- Profondeur : au-delà de 64, recompte des cadres réels (`StackWalker`, cadres dont la classe vient du chargeur du
  module ; les cadres cachés des lambdas ne comptent pas) ; déclenche si c'est vrai.
- Collant : après un déclenchement, chaque `enter`/`tick` lève de nouveau. Comme **l'entrée de chaque gestionnaire
  compte un `tick`**, un `catch` ou un `finally` ne peut plus avaler l'erreur du compteur : `finally { return; }`
  autour d'une boucle **relève** l'erreur (plus fort que le §3.4, qui se contentait de « détecté »).
- `tripped()` : `time budget`, `allocation budget`, `call depth over 64`, suivi de ` at TagGame.java:41` (le cadre
  du module le plus profond qui a une ligne ; les ponts n'en ont pas). Désarmé, `enter`/`tick` lèvent
  `ForgeLimit("module code ran outside a metered call")` sans rien déclencher.
- `allocatedSinceArm()` : figé à la valeur de `disarm()` ; -1 sans mesure.

## Les gardes (`Guarded`)

Formes : vérifier puis rendre (`array`, `capacity`, `trusted`), statique à la place d'une statique (même
descripteur), statique à la place d'une méthode d'instance (receveur en premier). Chaque garde **lève avant de
changer quoi que ce soit** (exception : `StringJoiner.add`/`merge`, voir plus bas).

| Famille | Limite | Membres |
|---|---|---|
| tableaux, capacités | 65 536 (`Limits.MAX_ARRAY`, `ForgeLimits.CAPACITY`) | `newarray`, constructeurs à capacité, `ensureCapacity` (`ArrayList`, `StringBuilder`), `newHashMap`… (4), `Arrays.copyOf`/`copyOfRange` (20 surcharges) |
| plages | 65 536 nombres | `IntStream`/`LongStream` `range`/`rangeClosed` (débordements de `long` compris) |
| collections | 10 000 éléments (`Limits.MAX_ELEMENTS`) | `add`, `addAll` (deux formes), `add(int, E)`, `addFirst`/`addLast`, `offer`, `offerFirst`/`offerLast`, `push`, `Collections.addAll`, `put`, `putAll`, `putIfAbsent`, `merge`, `compute`, `computeIfAbsent`, `putFirst`/`putLast` ; `Stream.builder()` et les trois constructeurs de flux primitifs ; `Collections.nCopies` (refusé par la garde : défense en profondeur) |
| vues | 10 000 éléments **de la liste vue** | `List.subList` (une vue dont les ajouts comptent contre la liste racine : `l.subList(0, 0).add(x)` contournait la limite), `List.listIterator()`/`(int)` (`ListIterator.add`) |
| textes | 65 536 caractères (`Limits.MAX_CHARS`) | toutes les surcharges publiques de `StringBuilder.append`/`insert` (sauf `StringBuffer`, type interdit), `appendCodePoint`, `replace`, `setLength`, `repeat` (2), `String.repeat`, `indent` (taille du **résultat** : lignes × (n + 1)), `concat`, `replace(CharSequence, CharSequence)` (y compris la cible vide), `StringJoiner.add`/`merge`, `Collectors.joining` (3), `String.join` (2), `String.format` (2) et `formatted` |
| texte d'un tout | 65 536 caractères, 64 niveaux | `toString()` d'un type du JDK, `String.valueOf(Object)`, `Objects.toString` (2), `append`/`insert(Object)`, les **objets d'une concaténation** et les **composants objets d'un record** (amorces), `Arrays.toString` (9), `deepToString`, `%s` d'un format |

Détails qui comptent :

- **Le texte d'un tout** est fabriqué par `Texts`, élément par élément, **au format exact du JDK** (`[a, b]`,
  `{k=v}`, `(this Collection)`, `(this Map)`, `Optional[…]`, `k=v`, `[...]` de `deepToString`), et s'arrête à la
  limite : le travail est borné par le texte (chaque élément y ajoute au moins deux caractères), même sur une
  structure partagée. Composites reconnus : `Collection`, `Map`, `Optional`, `AtomicReference`, un `Map.Entry` du
  JDK. Un objet du module garde son propre `toString` (code mesuré). `GuardedTest` compare au JDK sur 22 formes.
- **Concaténation** : l'amorce `Guarded.concatenation` construit la même concaténation, chaque argument objet (sauf
  `String` et les boîtes) filtré par `valueOf`, puis le résultat vérifié. Liaison : une fois par site, puis le JIT.
- **Format** : largeur et précision de 3 chiffres au plus (indice d'argument, drapeaux dont `0`, largeur, précision),
  arguments composites remplacés par leur texte borné, sortie écrite dans un `Appendable` borné. Seul écart visible :
  `%h` d'un composite donne le hachage de son texte.
- **À la limite**, un ensemble ou une table qui contient déjà l'élément ou la clé ne grandit pas : permis
  (`set.add(present)`, `map.put(cléPrésente, v)`, `addAll` d'un ensemble compte seulement les nouveaux). En revanche
  `compute`/`merge`/`computeIfAbsent` sur une **clé absente** d'une table pleine sont refusés même si la fonction
  rendrait `null` (prudence).
- `StringJoiner` ne dit pas son délimiteur : `add`/`merge` vérifient avant (l'élément) **et après** (le délimiteur).
  Le dépassement possible est d'un délimiteur.
- Les `append` de nombres ne fabriquent un texte qu'à moins de 25 caractères de la limite (exact, sans coût
  ailleurs).
- `trusted(cs)` : un `CharSequence` du JDK est cru ; un autre est lu une fois (`length()` puis `charAt`), borné.
  Depuis le refus des `CharSequence` du module, c'est une défense en profondeur (testée directement).
- Messages de `ForgeLimit` (pour le Forgeron) : `an array of N elements (at most 65536)`, `a capacity of N (at most
  65536)`, `a collection over 10000 elements`, `a text over 65536 characters`, `a range of N numbers (at most
  65536)`, `a format width or precision over 3 digits`, `a text of collections nested over 64 levels`.
- `Guarded.text` n'est plus public : le bytecode réécrit ne l'appelle plus (les amorces s'en servent).

## Constats nouveaux (à lire)

1. **BLOQUANT (disponibilité), non fermé : le hachage d'une structure imbriquée partagée gèle le serveur.**
   Une liste `L1` de 10 000 références à la même liste `L0` de 10 000 entiers se construit en 20 000 `add`, chacun
   permis. `L1.hashCode()` parcourt 10⁸ éléments **dans un seul appel du JDK** : **70 à 86 ms mesurés** (JDK 25,
   cette machine). Un niveau de plus, `L2` = 10 000 × `L1`, coûte ≈ **630 s** (mesuré sur 100 × `L1` : 6,3 s), trois
   niveaux des jours. Les points d'entrée sont innombrables et implicites : `hashCode`, `equals` (deux structures
   égales mais distinctes), `HashSet.add(L2)`, `map.put(L2, v)`, `contains`, `Set.of`, `Objects.hash`, le `hashCode`
   d'un record qui contient `L2`, `distinct()`, `groupingBy`… Le JDK n'y appelle **aucun code du module** : ni le
   compteur ni une garde de site d'appel ne voient rien, et le partage se fait aussi sans `add` (un tableau rempli
   puis `List.of(tableau)`, `Stream.generate` est refusé mais `mapToObj(i -> l0).toList()` ne l'est pas). Le texte
   (`toString`) est, lui, borné par `Texts`. Le §3.8.1 (« une boucle du JDK n'est bornée que par la taille de ses
   entrées ») suppose des entrées sans partage : c'est faux ici. `disarm()` compte bien une faute *limite* après
   coup, mais le fil du serveur est gelé pendant l'appel. Pistes (décision du superviseur) :
   (a) **faire tourner chaque appel de module sur un fil à lui**, le fil serveur l'attendant au plus 20 ms puis
   l'abandonnant (le SDK refuse tout appel d'un fil abandonné ; le fil perdu brûle un cœur jusqu'à la fin de son
   calcul) — changement d'architecture (§1.1, M5-05, M5-11) ;
   (b) borner aux points d'entrée connus (hachage et égalité explicites, `add`/`put` dans une table de hachage, les
   amorces `equals`/`hashCode` des records) par un parcours compté — partiel, contournable ;
   (c) interdire les collections dans les collections — trop restrictif (`Map<String, List<String>>`).
2. **Important (croissance) : les vues triées par plage** (`subSet`, `headSet`, `tailSet`, `subMap`, `headMap`,
   `tailMap`) : `set.subSet(i, i + 1).add(i)` dans une boucle fait grandir l'ensemble au-delà de 10 000 (la vue ne
   compte que sa plage). Borné seulement par le compteur (16 Mio par appel), l'allocation par minute (256 Mio) et la
   jauge (32 Mio). Les sous-listes et les itérateurs de liste, eux, sont enveloppés (`Views`). Envelopper les vues
   triées demanderait deux enveloppes complètes (`NavigableSet`, `NavigableMap`) : à faire si M5-18 le juge utile.
3. **Mineur (temps)** : un seul appel du JDK peut coûter cher sans rien allouer — `indexOf` d'un motif de 32 768
   caractères dans un texte de 65 536 (O(n·m)), un tri de 65 536 éléments. Il n'est pas arrêté pendant l'appel ; il
   est compté par `disarm()` (faute *limite*, 2 pour désactiver).
4. **Mineur (liaison à froid)** : la première exécution d'un site `invokedynamic` (lambda, concaténation, record) le
   lie **dans** l'appel mesuré ; sur une JVM froide, quelques ms par site. Sur le serveur (JDK chaud), c'est 50 à
   200 µs par site : un module de 50 sites peut perdre ≈ 5 ms de son premier appel.

## Ce que les tâches suivantes doivent savoir

### M5-05 (le chargeur, l'hôte)

- Pipeline : `BytecodeGuard().check(classes)` puis `Instrumenter.rewrite(main, classes)` ; **`RewriteRefused` est un
  refus pour le Forgeron**, comme une violation de la garde (son message est écrit pour lui).
- Le chargeur doit résoudre `forge.rt.*` par le chargeur du mod (`SandboxPolicy.resolvable` le fait) : `Meter`,
  `Guarded`, `ForgeLimit` sont appelés par le bytecode, `Texts` et `Views` le sont par `Guarded` dans le chargeur du
  mod. Les amorces de `Guarded` se lient avec `MethodHandles$Lookup`, `MethodType`, `CallSite`, `TypeDescriptor`,
  `MethodHandle` (déjà dans `LINKAGE_BINARY`).
- L'hôte : `Class.forName(main + Built.METER_SUFFIX, true, loader).getField(Built.METER_FIELD).set(null, meter)`
  (le porteur n'a pas d'initialiseur), puis `Class.forName(main, false, loader)` ; **arm → appel → disarm → tripped()**
  sur le même fil ; `allocatedSinceArm()` est figé au `disarm`. Le harnais de test `forge/sandbox/RewriteHarness.kt`
  (`RewriteLoader`, `LoadedModule`, `FakeContext`) montre le chemin minimal ; il ne remplace pas le vrai chargeur
  (il voit tout `java.*`).
- La jauge de mémoire : une `List` peut être une vue de `Guarded` (`Views.SubList`, une `AbstractList` du mod) ;
  aucune classe du module n'est une collection, une table ou un `CharSequence`.
