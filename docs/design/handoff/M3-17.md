## Les commandes

Toutes sont sous `/narrator`, donc réservées aux opérateurs de **niveau 2** (`Commands.LEVEL_GAMEMASTERS`, posé sur la racine par `NarratorCommand`). Les sorties sont en anglais, grises (titres en `[Narrator]` doré, refus en rouge).

| Syntaxe | Effet | Écrit ? |
|---|---|---|
| `/narrator sheet <player> [part] [page]` | la fiche complète (`FULL`, comme `player_profile`), ou une partie : `all`, `identity`, `recap`, `personality`, `stats`, `history`, `memories` | non |
| `/narrator memory` ou `/narrator memory status` | disponibilité, travaux, horloge du monde, comptes des tables, index, derniers lot, sieste et rêve, prochain rêve, refus et avertissements de voix des 24 h | non |
| `/narrator memory canon [open\|all] [player] [page]` | le canon : ouvert par défaut ; `all` ajoute les entrées closes ; avec un joueur, celles qui le nomment et celles de tout le monde | non |
| `/narrator memory recall <mots…>` | ce que l'outil `recall` trouverait (`RecallPurpose.TOOL`, 8 résultats), avec le score | non |
| `/narrator memory show <ref> [page]` | une ligne `M-`, `C-`, `I-`, `H-` ou `N-` : son contenu, sa provenance (source, travail, tour, conversation, preuves `e…`/`t…`) et son historique `memory_log` (colonnes changées, raison) | non |
| `/narrator memory forget <ref> [raison…]` | archive (jamais de suppression) un souvenir, une entrée de canon ou une interaction | oui |
| `/narrator memory restore <ref> [raison…]` | l'inverse | oui |
| `/narrator memory note <texte…>` | une note `operator` pour le Directeur (prochain briefing) ; texte en français, à la troisième personne (`VoiceGuard`) | oui |
| `/narrator memory docs <clé> [version] [page]` | sans version : les versions d'un document, de la plus récente à la plus ancienne (12 au plus) ; avec une version : son texte et ses preuves. Clé : `grimoire`, `review`, `sheet:<joueur>:<section>` | non |
| `/narrator memory rollback <clé> <version>` | recopie la version comme nouvelle version du document | oui |
| `/narrator memory revert <run>` | annule les écritures d'un travail de mémoire, d'après `memory_log` ; refusé pour le travail en cours | oui |
| `/narrator memory chronicle` | rattrapage du Chroniqueur maintenant (siestes en attente, lot du chapitre ouvert) | met en file |
| `/narrator memory dream` | rêve profond maintenant | met en file |
| `/narrator memory pause` / `resume` | suspend ou reprend les travaux de modèle (le travail en cours finit ; le code seul continue) | état des travaux |

- **Joueur** : en ligne d'abord, sinon par son nom actuel ou un ancien nom dans le Journal (`players`, `player_names`, sans casse, le plus récemment vu d'abord, comme `player_profile`), ou par son UUID. Suggestions : les joueurs en ligne.
- **Référence** : `Ref.parse` (`C-45`, `c45`).
- **Écritures** : toutes passent par `MemoryStore` avec `Author(Source.OPERATOR, operator = <nom>)`, donc `memory_log.actor = operator:<nom>`, et le magasin enregistre sa décision `memory` (`archived`, `restored`, `written`, `rolled_back`, `reverted`, `rejected`). La commande ajoute une décision **`operator`** (sujet = l'opérateur) : `memory_forget`, `memory_restore`, `memory_note`, `memory_rollback`, `memory_revert`, `memory_chronicle`, `memory_dream`. Un refus du magasin (`MemoryRejected`) est rendu tel quel, en rouge : `refused: C-45 is archived already`.
- **Fils** : les lectures et les écritures tournent hors du thread serveur (`replyLater`, ou `replyOn` pour les écritures) ; la réponse revient sur le thread serveur. `chronicle`, `dream`, `pause`, `resume` et le refus sans mémoire répondent tout de suite, sur le thread serveur (ils ne touchent que la file des travaux). La première ligne d'une écriture réussie part aussi aux autres opérateurs (`sendSuccess(…, true)`), comme les commandes du Directeur.
- **Sans mémoire** (`DisabledMemory`) : **chaque** commande est refusée tout de suite, en rouge, avec la raison :
  `[Narrator] the memory is unavailable (not wired yet): nothing to read nor change.`
  et `/narrator status` dit `Memory: unavailable (not wired yet)`.

### Exemple : `/narrator memory status`

Sortie réelle du test `memory status counts the tables and tells the jobs` (magasin réel sur DuckDB en mémoire, travaux simulés) :

Index: 4 rows · 23 postings · 18 terms · audit: 8 changes
Running: nap run 14 (chapter_closed) for 1m12s
Queued: batch, dream
Last batch: run 13 done 19:31:05 after 1m05s (timer)
  12k tokens in, 900 out · 3 writes, 0 refused

## Écarts par rapport au design, et décisions

1. **Pages cliquables au lieu d'un fichier.** Le §14 voulait 20 lignes au plus, puis une coupe avec le chemin d'un fichier sous `world/narrator2/logs/memory/`. Les sorties longues (`sheet`, `canon`, `show`, `docs <clé> <version>`) sont plutôt découpées en pages de 15 lignes, avec un lien cliquable vers la page suivante et la précédente, exactement comme `/narrator trace` (`TraceText.page`, réutilisé). Chaque page tient dans les 20 lignes du chat ouvert (titre, 15 lignes, pied). C'est cohérent avec les commandes existantes, sans fichier à nettoyer. Les sorties courtes par construction (`status`, `recall`, la liste des versions) ne sont pas paginées.
2. **`sheet <player> [part] [page]`** : la partie `all` existe pour pouvoir donner une page (`/narrator sheet Bartok all 2`, le lien du pied de page). Une seule partie à la fois ; le nom du joueur reste en tête (rendu de M3-07).
3. **`forget` et `restore` prennent une raison facultative** (`memory_log.reason`, 300 caractères au plus par le magasin). Sans elle : `forgotten by an operator` / `restored by an operator`.
4. **`docs` et `rollback` lisent le reste de la ligne** (`greedyString`) : Brigadier n'accepte pas `:` dans un mot sans guillemets, et `sheet:Bartok:recap` doit se taper tel quel. `docs` accepte en plus une version, pour lire un texte avant de le restaurer, puis une page. Le joueur d'une clé de fiche est un nom (ou un UUID) ; la sortie montre `sheet:Bartok:recap`. Le message de refus de `rollbackDoc` (magasin) montre, lui, la clé avec l'UUID.
5. **`/narrator memory` seul** = `status`.
6. **`canon` : un nombre après `open`/`all` est une page, tout autre mot un joueur** (l'argument `page` est déclaré avant `player`, et Brigadier garde le premier qui se lit en entier). Un test analyse chaque syntaxe documentée. Limite : 300 entrées, triées par le magasin (échéance, importance, récence).
7. **`recall` : les mots seulement**, sans les filtres de l'outil (joueur, sortes, jours, entrées closes). Chaque résultat est coupé à deux lignes de chat ; le score est en tête (`[0.82]`). **Rien n'est enregistré** (`recalls`) ni renforcé : regarder n'est pas se souvenir. Il en va de même pour `sheet` et `show`.
8. **Les comptes du `status` sont lus dans le Journal par la commande** (une requête, `COUNTS_SQL`, sur le pool de lecture) : `MemoryStatus` n'a ni comptes ni taille d'index, et `status()` ne lit jamais la base (M3-12). Si la lecture échoue, la ligne le dit en rouge et le reste s'affiche. « Index » = lignes de `search_docs`, `search_postings`, termes distincts ; « audit » = lignes de `memory_log`.
9. **La ligne `Memory:` vient après `Guards:`** dans `/narrator status`, pas après `Journal:` : `StatusLinesTest` (T21) fige les indices 0 à 9. `/narrator status` fait maintenant 22 lignes, la limite de ce test.
10. **Décisions `operator`** : une par écriture ou travail lancé (liste plus haut). **Pas pour `pause`/`resume`** : `MemoryJobs` enregistre déjà `memory paused`/`resumed` avec le nom de l'opérateur en sujet (M3-12 demandait de ne pas doubler).
11. **`revert` refuse le travail en cours** (`MemoryStatus.running`) : annuler pendant qu'il écrit laisserait la moitié de ses écritures. Un travail sans écriture répond « wrote nothing in the memory: nothing to undo » (le magasin rend 0).
12. **Provenance de `show`** : lue dans le JSON `after` (ou `before`) de la dernière ligne `memory_log` de la ligne (colonnes `source`, `run_id`, `turn_id`, `conversation_id`, `evidence_events`, `evidence_tools`) ; les types de M3-01 ne portent pas ces colonnes. Sans audit (`FakeMemoryStore`), seule la source de la ligne. L'historique montre les colonnes changées (4 au plus, valeurs coupées à 40 caractères), puis la raison.
13. **Arbre construit avec les constructeurs de Brigadier** (`LiteralArgumentBuilder.literal`, `RequiredArgumentBuilder.argument`, ce que rendent `Commands.literal` et `Commands.argument`) : charger la classe `Commands` dans un test unitaire lance l'amorçage des registres du jeu et échoue. Le test des syntaxes peut ainsi analyser l'arbre réel.
14. **Note de l'opérateur** : `NoteKind.OPERATOR`, sans joueurs ni références ni expiration. Le texte passe par `VoiceGuard` comme tout le reste : une note à la première personne est refusée avec le message du magasin (il faut écrire « Bartok préfère… », pas « Je veux… »).
