# Passation M4-12 : défis, détection et cycle de vie

Vague B de M4 (`design/M4.md` §22.2, §5.1-5.3, §4.4-4.5, §11), sur le chemin critique (01 → 02 → 12 → 17 → 22 → 23 →
24). Elle livre la partie du moteur qui suit les défis : départ (validation, canon, état), détection des six objectifs,
jugement, fin anticipée, et la **fin commune** des défis et des duels (paris, barres, enjeux, canon, interactions,
décision, signal). Le serveur tourne toujours avec `DisabledMechanics("not wired yet")` : M4-23 assemble. **En cas de
contradiction avec `M4.md`, le code et cette passation font foi.**

Aucun contrat sans propriétaire n'a changé (`Mechanics.kt`, `MechanicsTypes.kt`, `MechanicsState.kt` intacts).

### API

```kotlin
class Challenges(services, store: StateStore, bars: Bossbars,
                 stakes: StakePayer = StakePayer.NONE, bets: BetBook = BetBook.RETURN_ALL,
                 clock: Clock = services.clock) : MechanicPart {
    suspend fun start(spec: ChallengeSpec, caller: Caller): ChallengeView          // coroutine ; MechanicRejected
    suspend fun end(ref: Ref, outcome: ChallengeOutcome, winners: List<UUID>, note: String, author: Author): ChallengeView
    fun list(): List<ChallengeView>                                                  // tout fil (instantané)
    fun finish(id: Long, ending: Ending, winners: List<UUID>, how: String? = null,
               note: String? = null, author: Author? = null): Deferred<String>?     // thread serveur
    fun room(state: MechanicsState, now: Long, duel: Boolean): MechanicRejected?    // le rythme, pur
    companion object { CHALLENGE_LIMIT, CHALLENGE_PACE, STARTED, JUDGING }
}
enum class Ending(val status: CanonStatus) { WON, LOST, EXPIRED, CANCELLED }        // id = nom de la décision
interface StakePayer { suspend fun check(reward, penalty, caller) {}; suspend fun pay(challenge, winners, losers): List<String> = emptyList() }
interface BetBook { fun settle(state, challenge, ending, winners: List<String>): Pair<MechanicsState, String?> = giveBack(state, challenge) }
```

## Le cycle de vie, tel que le code l'applique

### Départ (`start`)

Dans l'ordre, la première erreur l'emporte (`MechanicRejected`, à rendre par `toResult()`) :

1. **Champs requis** (`Goals.shape`, pur) : `goal obtain needs item…`, `goal kill needs entity…`, `kill cannot target
   players: a fight between players is a duel (propose_duel)` (`player` ou `minecraft:player`), `goal reach needs
   place…` (lieu vide), `place: a point needs x and z (y is optional)`, `place: y_above 100 is above y_below 40…`,
   `goal answer needs answers…`, `answers[1] has no letter nor digit…`. Un champ en trop (un `item` pour `reach`) est
   ignoré. Puis un titre vide une fois nettoyé (`Speech.clean`).
2. **Sous un verrou** (un départ à la fois), sur le thread serveur : les ids dans les registres (`Goals.target` :
   objet ou `#tag`, créature ou `#tag`, avec les plus proches ; structure et biome par `Structures` de l'Oracle ;
   dimension connue du serveur) ; les participants (les noms donnés, en ligne, sans tenir compte de la casse :
   `Bob is not online; online: …` ; sans noms, tous les joueurs en ligne hors `FakePlayer`, au moins un) ; **le
   rythme** (`room`).
3. `StakePayer.check(reward, penalty, caller)` (M4-17 ; ne fait rien aujourd'hui).
4. `journal.barrier()` (les lignes `players` des joueurs tout juste connectés, que le canon vérifie), puis la ligne du
   canon : `CanonDraft(CHALLENGE, statement, quote, players = les participants nommés ou [] pour « tous », stakes,
   importance, mechanic = CHALLENGE, dueAt = null)`, auteur `Source.DIRECTOR` (tour et conversation du `Caller`). Un
   refus du magasin (voix, longueur…) devient `MechanicRejected(e.rule, e.message)`.
5. Sur le thread serveur : le rythme **revérifié**, puis l'état (`RUNNING`, `endsAt`, `betsCloseAt` si `bets`,
   `lastChallengeAt`), décision `mechanic started` (raison : `ChallengeLines.started`). Si le rythme refuse à ce
   moment (un duel est arrivé entre-temps), la ligne du canon est résolue `cancelled` par le moteur et le refus levé.

`stakes` du canon (code, anglais, ≤ 160) : `reward 1x golden_apple · penalty tiny (2) · bets`. **Le nom français d'un
objet n'y est pas** (`1x diamond_pickaxe (named)`) : le magasin vérifie la voix de ce texte, et un nom entre
guillemets peut y dépasser la moitié du texte.

### Détection (une `MechanicPart`)

| Objectif | Quand | Comment |
|---|---|---|
| `obtain` | chaque seconde, participants en ligne ni réussis ni éliminés | `Goals.count` : `0 until inventory.containerSize` (36 cases, puis armure, seconde main, corps, selle : vérifié au bytecode, `getContainerSize` = 36 + `EQUIPMENT_SLOT_MAPPING.size()`) ; `progress` = le maximum tenu |
| `reach` | chaque seconde | **position, dimension et biome lus sur le joueur vivant** (`Goals.spot`) ; la structure, sur `PlayerStates` (5 s de retard au plus) |
| `kill` | au fait `EntityKilled` d'un participant, `pvp` faux | type exact ou `#tag` ; appliqué au tick suivant |
| `survive` | au fait `PlayerDied` → `died` ; chaque seconde avec `no_armor`, tout objet dans une case d'armure (élytres et citrouille comprises) → `armor` ; `LEAVE` → `left` | |
| `answer` | au fait `ChatMessage` `PUBLIC` ou `PRAY` d'un participant | `Answers.matches` dans `onEvent` ; jamais `WHISPER` |
| `judged` | rien | à l'échéance : `JUDGING` |

- `onEvent` (tout fil) n'apparie que sur l'instantané et **met en file** ; la file est appliquée au tick suivant
  (`everyTick`), puis les verdicts. Aucun texte de chat n'est gardé dans la file.
- Deux participants qui réussissent dans le même tick gardent l'ordre où ils ont été vus : chaque `doneAt` est au moins
  une milliseconde après le précédent.
- **Retardataires** (défi ouvert à tous) : `onJoin` les inscrit `late = true` ; leur barre suit à la seconde. Un
  participant parti reste participant (sauf `survive`).

### Verdict (`Goals.verdict`, pur)

- `winners` = N > 0 : fini dès que N ont réussi (les N premiers, dans l'ordre).
- **Liste fermée** (joueurs nommés) : fini dès que **chaque** participant a réussi (ou est éliminé) — écart : le design
  ne finissait qu'à l'échéance avec `winners` = 0 ou N plus grand que la liste.
- À l'échéance : gagné par ceux qui ont réussi (même moins que N), perdu si personne.
- `survive` : perdu dès que plus personne n'est en lice ; à l'échéance, gagné par tous ceux encore en lice.
- `judged` : à l'échéance, `JUDGING` pour `mechanics.judgeMinutes` (à partir du moment où la seconde le voit),
  décision `mechanic judging` et signal `JUDGE` (prioritaire) ; passé `judgeUntil` : `expired`, sans enjeux.
- Les duels ne sont jamais jugés ici (`null`) : M4-19.

### Fin commune (`finish`, thread serveur)

1. Dans **un seul** `update` : le défi sort de l'état ; ses positions d'arène passent dans `returns` (comme
   `Reconcile.drop`) ; `BetBook.settle` ajoute les instructions des paris (une exception de `settle` : tout est rendu).
   Puis `bars.hideAll(Bossbars.key(id))`.
2. Coroutine (`services.scope`), chaque étape protégée (une erreur est loguée, la suivante continue) :
   - enjeux (`StakePayer.pay`) pour `won` et `lost` seulement : gagnants ; perdants = participants **non `late`** hors
     gagnants (`won`), ou tous les non `late` (`lost`) ;
   - canon résolu par `Author(Source.ENGINE, conversationId = "mechanics:C-50")`, gagnants compris (8 au plus), avec
     la note s'il y en a une, sinon le résumé du code ; si le magasin refuse le texte, une résolution sûre
     (`won (challenge C-50)`) ;
   - une interaction `challenge_result` par participant (+1 gagnant, 0 sinon ; `canon` = le défi ; `Source.ENGINE`),
     **pour `won` et `lost` seulement** (écart : rien pour `expired`, `cancelled`) ; résumé anglais `won the challenge
     C-50 (obtain 1 turtle_egg)` ;
   - décision `mechanic won|lost|expired|cancelled`, sujet `C-50`, raison = **la ligne entière**, conversation
     `mechanics:C-50`, `detail` (`ending`, `what` = `challenge`/`duel`, `winners`, `by`) ;
   - signal `CHALLENGE` (ou `DUEL`), **sauf quand l'auteur est le Directeur** (son outil lui rend la ligne) ;
     prioritaire, sauf un duel qui finit en invitation (refus, invitation échue).
3. Rend un `Deferred<String>` : la ligne entière. `null` si le défi n'est plus là (déjà fini).

Lignes (`ChallengeLines.summary`, anglais, noms échappés) :

```
C-50 won by Mimosa in 9m12s (turtle_egg 1/1) · reward: … · penalty: … · bets: 1 stake given back
C-51 lost: nobody reached the_nether in 20m · …
C-53 won by Mimosa, Josiane: still in after 10m; out: Bartok (died)
C-53 « La plus belle statue » ended: judge it now with end_challenge C-53 (winners); participants: …; you have 15m   (JUDGE)
C-53 expired: not judged within 15m; no stakes
C-53 won by Mimosa (ended by the Director); note: « Mimosa a sculpté la plus belle statue. »
C-50 cancelled (ended by the operator Clement); note: « … » · bets: 1 stake given back
```

### Fin anticipée (`end`)

- Défi ou duel en cours (invitations et jugement compris), sinon `C-50 is not one of your running challenges;
  running: C-53` (ou `none`).
- `won` exige des gagnants parmi les participants (`won needs winners among the participants: …`) ; `lost` et
  `cancelled` refusent des gagnants (`winners only go with won: leave them out`).
- La note passe `VoiceGuard` **avant** de rien finir (`note …` en `Invalid arguments`).
- Attend toute la fin (enjeux compris) et rend la vue du défi tel qu'il a fini, **sa `line` = la ligne de fin** (pas
  la ligne de situation).

### Situation (`Challenges: …`, ≤ 400)

`Challenges: C-50 obtain 1 turtle_egg « Œuf de tortue » → all · Bartok 1/1 (done), Josiane 0/1 (late) · ends in 12m ·
bets open 2m (1 bet); C-52 duel « Duel au soleil » Bartok vs Mimosa · invited, Bartok accepted, waiting for Mimosa ·
answer by 21:22 (in 2m) · next challenge possible at 20:10 (in 6m)`

Défis séparés par `; `, rythme en dernier (`next challenge possible at …`, `no new challenge until one ends (2/2)`).
Rien quand rien ne court et que le rythme permet un défi ; `Challenges: none running · …` sinon. Trop long : les
participants sont comptés (`8 players, 2 done`), puis les derniers défis retirés (`(+1 more)`). La partie rend aussi
les duels (M4-19 n'a pas à écrire de ligne `Challenges`).

## Écarts par rapport au design, et pourquoi

1. **Le rythme est dans `start`** (et `room` pour les duels), pas dans `ChallengeTools` : il doit être vérifié sur le
   thread serveur au moment d'écrire l'état, sinon deux appels simultanés passent tous deux.
2. **`reach` lit le joueur vivant** (position, dimension, biome), pas `PlayerStates` : même coût sur le thread serveur,
   sans la seconde de retard. La structure reste celle de `PlayerStates`.
3. **`Ending`** (avec `EXPIRED`) au lieu de `ChallengeOutcome` pour `finish` ; `Ending.of(outcome)`.
4. **`finish` a `how`, `note`, `author`** : un duel dit lui-même comment il a fini (`how`), un opérateur ou le Directeur
   sont nommés dans la ligne et la décision, jamais dans la source du canon.
5. **Arène → `returns` dans `finish`**, comme `Reconcile.drop` : M4-19 remet ses duellistes en place depuis `returns`
   (en ligne : chaque seconde ; sinon à la connexion), quel que soit le chemin de la fin.
6. Une liste fermée finit quand tous ont réussi ; interactions seulement pour `won` et `lost` ; pas de nom d'objet dans
   `stakes` (voir plus haut).
7. Le titre est vérifié non vide après nettoyage ; un champ inutile à l'objectif est ignoré.

## Ce que les tâches suivantes doivent savoir

### M4-17 (outils et enjeux)

- `start_challenge` : `services.mechanics.challenges.start(args, ctx.caller)` ; `MechanicRejected.toResult()`. La
  validation des champs, des ids, des joueurs et **du rythme est déjà faite** ; vous écrivez `StakePayer` (`check` au
  départ avec le `Caller` du Directeur ; `pay` à la fin). Pour la réponse : `ChallengeLines.started(state, clock)` donne
  `C-50 started: obtain 1 turtle_egg « … » · Mimosa, Bartok · ends 20:15 (in 15m) · reward 1x golden_apple · penalty
  tiny (2) · bets open until 20:05` (le défi est dans `store.snapshot.challenge(view.ref.id)`), ou composez depuis la
  vue.
- `end_challenge` : convertir les noms en UUID (participants), `challenges.end(ref, outcome, uuids, note,
  ctx.author())` ; `ok: ${view.line}`. Un `Author(Source.DIRECTOR)` n'envoie pas de signal.
- `pay(challenge, winners, losers)` : les perdants ne contiennent jamais de retardataire ; payez seulement les joueurs
  en ligne ; un acte par joueur (`actions.open("stake", ref, nom, …)`, `actions.run`) ; écrivez les interactions
  `gift`/`blessing`/`punishment` (`canon` = le défi, `Source.ENGINE`) ; rendez les segments (`reward: Mimosa got 1x
  golden_apple`, `penalty: Bartok refused (no_pile_on: …)`). Un duel n'a que `duel.reward`.
- M4-23 passe vos objets au constructeur de `Challenges`.

### M4-19 (duels)

- `room(state, now, duel = true)` dans votre propre `update` (le rythme ne compte pas l'écart entre deux départs pour
  un duel, seulement `maxChallenges`).
- Fin d'un duel : `challenges.finish(id, Ending.WON|LOST|CANCELLED, winners, how = "won by Mimosa: Bartok's fatal blow
  was stopped at 1 hp; …")` sur le thread serveur ; `how` remplace le résumé après la référence (et sert de résolution
  sans note). Signal `DUEL`, prioritaire sauf depuis `INVITED`. Les positions d'arène vont dans `returns`.
- La partie des défis ignore les duels pour la détection et les verdicts ; elle rend leur ligne de situation.
- `end` (Directeur, opérateur) marche aussi sur un duel : éteignez et remettez en place ceux dont le duel a quitté
  l'état (votre seconde), quel que soit le chemin.

### M4-20 (paris)

- `BetBook.settle(state, challenge, ending, winners)` : **pur**, appelé dans l'`update` qui retire le défi ; rendez
  l'état avec vos `settlements` et le segment `bets: …` (null sans paris). `winners` : UUID en texte, dans l'ordre.
  Une exception rend tout (`BetBook.giveBack`). Pour `expired` et `cancelled`, tout est rendu.
- `ChallengeState.betsCloseAt` est posé au départ : `min(betWindowMinutes, minutes / 3)`, une minute au moins.

### M4-21 (commandes)

- `/narrator challenge list` : `challenges.list()` (`line` = ligne de situation) ; `cancel` : `end(ref, CANCELLED,
  emptyList(), note, Author(Source.OPERATOR, operator = nom))` — la note passe `VoiceGuard` (troisième personne).

### M4-23 (assemblage)

- `Challenges(services, store, bars, stakes, bets)` **avant** `ChallengeBars` dans la liste des parties, avec le même
  `Bossbars`. `MechanicsService.challenges` délègue `start`, `end`, `list` ici, `proposeDuel`/`answerDuel` à M4-19,
  `bet` à M4-20. `situationLines` vient de l'`Engine` (la partie rend `Challenges: …`).

### M4-22 (prompts)

- Événements `CHALLENGE` et `JUDGE` (lignes ci-dessus) ; `Challenges:` dans la situation ; un `end_challenge` du
  Directeur ne le réveille pas (le résultat de l'outil porte la ligne) ; le moteur note lui-même les résultats.
