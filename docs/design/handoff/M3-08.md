# Passation M3-08 : le schéma pour le modèle

Tâche M3-08 de `design/M3.md` (§13, §19.2). L'outil `sql` sait maintenant interroger la mémoire : six vues `mem_*`, décrites dans une section à part de `SchemaDoc`. Les types d'événements quittent la description pour une table interrogeable, `event_types`. La description passe de **≈ 7 476 à 6 637 caractères** (≈ 2 492 → ≈ 2 213 tokens à 3 caractères par token), et chaque section a son budget, vérifié par un test. **En cas de contradiction avec `M3.md`, le code et cette passation font foi.**

Le total comprend les cinq sauts de ligne entre sections. Avant : ≈ 7 476 caractères, dont 2 179 pour la liste des 46 types (mesure du lot CD, que M3-01 n'avait pas changée). `SchemaDocTest` affiche ces chiffres à chaque passage (`SchemaDoc: 6637 characters…`).

**Il reste 10 caractères dans la section des tables.** Une table de plus devra raccourcir un commentaire de cette section, ou rester hors de la description (comme les tables de la mémoire). C'est la règle du §13 : une donnée de référence va dans une table interrogeable, une vue nouvelle tient dans le budget de sa section ou en remplace une.

## Les vues de la mémoire

```
MEMORY (what the Narrator remembers: ref as the memory tools take it, M-812, C-45…; players by current name; forgotten rows left out)
mem_memories(ref, kind, occurred, title, content, players[], tags[], importance, valence, strength) — Episodes, observations, reflections (French); strength: 1 fresh to 0.02 faded
mem_canon(ref, kind, status, statement, quote, players[], due_at, resolved_at, resolution, created_at) — What the Narrator said or decided: promises, challenges, laws, nicknames, places, lore…; open: status active or planned
mem_interactions(ref, ts, player, kind, valence, disrespect, summary, quote) — Noted conduct toward the Narrator (insult, prayer…) and his punishments, blessings, gifts
mem_favor(player, favor, trend, disrespect) — Favor with the Narrator, -100 to 100; trend: change over the player's last 5 h of play
mem_stats(player, stat, value, detail JSON) — Stats the code computes: deaths, kills, mining, travel (m), gear (0-5), luck (0-100), style…
mem_chronicle(ref, level, period_from, period_to, title, summary) — The chronicle (French) by chapter, session, season and saga
```

Chaque colonne utile a un commentaire, lu par `columns_of('mem_canon')` : vocabulaires des sortes et des statuts, bornes de l'importance et de la valence, sens de la force.

- **Références** : `'M-' || id`, `'C-'`, `'I-'`, `'H-'`, exactement ce que prennent `resolve`, `recall`, `mark_used`… (`WHERE ref = 'C-45'`).
- **Joueurs** : nom actuel (`players.name`), dans les listes (`list_contains(players, 'Bartok')`) comme dans `mem_interactions.player` (un joueur renommé garde son histoire). Un UUID qu'aucune ligne de `players` ne connaît reste écrit en UUID.
- **`strength`** : la formule de `Decay.strength`, `max(0,02 ; 2^(−Δ/S))`, avec `Δ` en heures de jeu du monde depuis `reinforced_play_s`. L'horloge est `memory_state.world_play_s`, que `DuckPlayClock` sauve toutes les 5 minutes : la force lue a au plus 5 minutes de jeu de retard, ce qui ne change rien à deux décimales.
- **`mem_favor`** : la formule de M3-05, mot pour mot, avec sa tendance (faveur maintenant moins faveur 5 h de jeu plus tôt, avec les seules interactions connues alors). L'horloge du joueur est `playtime_s` plus la session en cours, jusqu'à `now()`.

## Écarts par rapport au design (et pourquoi)

1. **`mem_favor(player, favor, trend, disrespect)`** au lieu de `player, favor, respect, disrespect, last_attention` :
   - le respect (moyenne mobile sur les messages, interactions comptées double) et l'attention restent dans `Favor.kt`, comme le recommandait M3-05 : trop longs pour une vue lisible, et la fiche les montre déjà ;
   - la tendance est ajoutée, puisque M3-05 l'avait formulée en SQL ;
   - `disrespect` = le nombre d'interactions non archivées marquées comme manque de respect (`Favor.Reading.disrespect`) ;
   - une ligne par joueur connu ; `favor` et `trend` sont nuls sans interaction qui compte.
2. **Ce qui est oublié n'apparaît pas dans les vues**, et `mem_memories` n'a pas de colonne `archived` : les vues écartent les lignes archivées (souvenirs, canon, interactions) et les entrées de chronique remplacées (`superseded_by`). Un `forget` d'opérateur, un souvenir fané archivé par l'hygiène ou fusionné dans un autre ne reviennent donc pas par les vues `mem_*`. Le canon clos (tenu, rompu, retiré…) reste visible : il fait partie de l'histoire, et `status` le dit (`recall`, lui, ne le montre qu'avec `includeClosed`).
   - **Correction (relecture de M3, constat 18)** : cette règle vaut pour les **vues** seulement. Les tables brutes (`memories`, `canon`, `interactions`, `memory_log`…) restent lisibles par `sql` (voir « Confidentialité »), archivées comprises : `forget` ne les efface jamais.
   - Ce que fait réellement `/narrator memory forget` : la ligne sort **des briefings, des réminiscences et de `recall`, même avec `include_closed`** (le lot D de la correction fait exclure de `recall` les lignes archivées par un opérateur ; avant lui, `include_closed` les rendait). C'est ce que dit la réponse de la commande. Une ancienne version de cette passation promettait « ne doivent pas revenir par `sql` » sans réserve : c'était trop fort.
3. **`strength` nulle tant que l'horloge du monde est inconnue** (aucune ligne `world_play_s`) plutôt que 1 : `greatest()` de DuckDB ignore les nuls et aurait dit « parfaitement en mémoire ».
4. **Pas d'arrondi dans les vues** : le format de `sql` montre déjà deux décimales au plus (`SqlFormat`). Les valeurs exactes se comparent aux fonctions Kotlin à 10⁻⁹ près dans les tests.
5. **`event_types.detail` est un objet JSON** qui a les mêmes clés que `events.detail`, chacune avec son sens : `(detail ->> 'placed_by')` lit la même clé dans les deux tables, et `json_keys(detail)` les liste dans l'ordre où le Journal les écrit. Les autres colonnes sont celles du §13 : `type, summary, subject, amount, other` (nul : colonne inutilisée par ce type). Seuls les types de la table `events` y sont : jamais `whisper`.
6. **`event_types` est décrite juste sous `events`**, pas à la fin des tables. Recréée à chaque ouverture, c'est toujours la table la plus récente ; or le commentaire de `events` renvoie déjà aux types d'événements.
7. **`occurred` = `occurred_from`** (le début de l'épisode) ; `occurred_to` reste dans la table.
8. **En-tête de la section des tables raccourci** : `TABLES (traces: see columns_of)` au lieu de `TABLES (traces without columns: see columns_of)`, pour tenir le budget de 1 800 avec la ligne d'`event_types`.
9. **Un cinquième exemple**, sur la mémoire : `SELECT ref, statement, due_at FROM mem_canon WHERE status = 'active' AND list_contains(players, 'Mimosa')`. Il montre la forme des listes de joueurs et la référence.
10. **`SchemaDoc.sections(connection)`** rend les sections une à une (`Map<Section, String>`) ; `generate` les joint par un saut de ligne. Le texte est le même octet pour octet sur une base neuve et sur un Journal qui a vécu (test).

## Confidentialité

- Aucune vue `mem_*` ne lit `private_messages` : test sur la définition de chaque vue (`SqlViewsTest`, 24 vues), seconde barrière du plan à chaque requête du modèle (`SqlRunnerTest`, les six vues et `event_types` passent la liste blanche de lot H : parcours de tables visibles, opérateurs connus).
- Aucune vue ne lit de fichier ni de réglage (`read_`, `glob`, `current_setting`… absents des définitions).
- `SchemaDoc` ne nomme ni `private_messages` ni le type `whisper` ; `event_types` n'a que les types de `events`.
- Les tables de la mémoire restent lisibles par `sql` (comme avant) mais ne sont pas décrites ; `MemorySchemaTest` le vérifie toujours. Elles contiennent aussi les lignes archivées et `memory_log` : **l'oubli par un opérateur est un oubli des briefings, des réminiscences et de `recall`, pas un effacement** (constat 18 de la relecture de M3).

## Limite à connaître : les cellules longues

> **Tranché (relecture de M3, constat 17)** : `SqlLimits.maxCellChars` vaut **400** par défaut (le total reste plafonné à 8 000 caractères). Un `content` de 400 caractères se lit donc entier par `sql`, et un `statement` de 300 aussi ; seuls les résumés de chronique et quelques `event_types.detail` peuvent encore être coupés. Le texte ci-dessous décrit l'état d'avant (120).

`sql` coupe chaque cellule à 120 caractères (`SqlLimits.maxCellChars`, `…(+N)`). C'est vrai pour toutes les vues, mais la mémoire a de longs textes : `content` jusqu'à 400 caractères, `statement` 300, les résumés de chronique davantage, et quelques `event_types.detail` (explosion, consommation, échange, cassage de bloc) dépassent 120. Le modèle peut lire la suite avec `substr(content, 121)` ou une clé précise (`detail ->> 'nearby'`) ; `recall` et `player_profile` rendent les textes entiers. Je n'ai pas touché à `SqlLimits` ni à `SqlTool` (hors de mes fichiers). **À trancher par le superviseur** : relever `maxCellChars` pour le modèle (400 ?) au prix de résultats plus longs, ou le dire dans les prompts.

## Ce que les tâches suivantes doivent savoir

- **M3-16 (prompts)** : le Directeur et l'Analyste peuvent interroger la mémoire par `sql`. Points utiles :
  - canon ouvert : `status IN ('active', 'planned')` ; d'un joueur : `list_contains(players, 'Bartok')` ;
  - souvenirs les plus présents : `ORDER BY strength DESC` ; récents : `ORDER BY occurred DESC` ;
  - historique d'un joueur : `SELECT ts, kind, valence, summary FROM mem_interactions WHERE player = 'Bartok' ORDER BY ts DESC` ;
  - faveur de tous : `SELECT * FROM mem_favor ORDER BY favor` ;
  - ce que contient `events.detail` pour un type : `SELECT * FROM event_types WHERE type = 'death'` (la liste n'est plus dans la description) ;
  - `sql` sert à compter, filtrer, croiser ; pour lire un texte entier, `recall` ou `player_profile` (cellules coupées à 400 caractères depuis le constat 17, 120 avant) ;
  - `sql` ne renforce aucun souvenir et n'écrit aucune ligne `recalls` : seuls `recall`, `player_profile` et les rappels automatiques le font.
  - `PromptToolMentionsTest` vérifie que les vues citées entre parenthèses dans `analyst.md` existent dans `SchemaDoc` : on peut y ajouter `mem_canon`, `mem_memories`, etc.
- **M3-18 (assemblage)** : rien à brancher. Les vues existent dès V2, même avec `DisabledMemory` (résultats vides ; `mem_favor` liste les joueurs avec une faveur nulle ; `strength` nulle sans horloge). `event_types` se recrée seule à chaque ouverture, aussi après une réouverture par `Recovery`.
- **Toutes** : la description de `sql` a changé, donc le préfixe mis en cache aussi (une fois). Toute vue ou table nouvelle doit tenir dans le budget de sa section (`SchemaDocTest` échoue sinon) : tables à 10 caractères de leur plafond, mémoire à 93, vues à 373.
