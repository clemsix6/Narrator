# Passation M4-14 : règles, format, validation, outils

Vague B de M4 (`design/M4.md` §22.2 ; §8, §12). Les lois et les plans existent maintenant de bout en bout côté
création : `create_rule` valide une règle sous tous les garde-fous (§8.5), écrit sa ligne du canon (`law` ou `plan`,
`mechanic = rule`) et son entrée d'état ; `remove_rule` la termine ; les trois pseudo-outils des règles
(`mob_effect`, `mob_attribute`, `notify`) ont leurs arguments, leur `check` et leur exécution. Le déclenchement
(appariement, délais, bilans, fins automatiques, marques retirées) reste à M4-18. **En cas de contradiction avec
`M4.md`, le code et cette passation font foi.**

Aucun contrat partagé n'a changé (`Mechanics.kt`, `MechanicsTypes.kt`, `MechanicsState.kt` intacts ; le schéma de
`RemoveRuleArgs` est inchangé, le budget de `MechanicsContractsTest` aussi).

### La validation (§8.5), dans l'ordre

1. **Décodage** : la spécification est réencodée puis redécodée par `ToolArgs` : une `RuleSpec` construite par le
   code (une commande, un test) est tenue aux mêmes bornes que celle du modèle.
2. **Conditions** :
   - chacune s'applique au déclencheur, d'après le tableau du §8.2 lu à la lettre (« lieu » = `dimension`, `near`,
     `y_below`, `y_above` pour `block_break`, `block_place`, `kill`, `damage_dealt`, `projectile_hit`, `death`, `chat`,
     `sleep`, `position` ; `dimension` et `near` aussi pour `mob_spawn`, `dimension` pour `dimension_change` ;
     `players` pour tout déclencheur qui a un acteur). Message : `when.block does not apply to chat; it applies to
     block_break, block_place` ;
   - `mob_spawn` exige `entity`, `position` exige un lieu, `y_above` > `y_below` est refusé (jamais vrai), un mot sans
     lettre ni chiffre est refusé ;
   - identifiants connus du serveur (`ServerRuleIds`), sinon les plus proches : `when.entity "zombi" is unknown;
     closest ids: zombie, zombie_villager, zombified_piglin…` ; un `#tag` est cherché parmi les tags (`closest tags`) ;
   - **`when.entity player` est refusé, sauf pour `damage_dealt`** (voir écarts) ;
   - joueurs connus du Journal (`knownPlayers` de M3, en ligne ou non) : `when.players: no player named Bob has ever
     played here; online: …`.
3. **Effets**, chacun préfixé `effect N (outil)` :
   - outil permis : `effect 2: give_item cannot be used in a rule; allowed: say, actionbar, …, notify` (mot pour mot le
     §8.5) ; tout autre nom (`run_command`, `take_item`, `propose_duel`, `create_rule`, `execute`…) reçoit ce refus ;
   - `mob_spawn rules may only use mob_effect and mob_attribute` ;
   - `at` permis pour l'outil (`at everyone is not allowed; punish takes at actor or subject`) et pour le déclencheur
     (`at subject: chat has no subject; these triggers have one: damage_dealt, projectile_hit, death, mob_spawn`), avec
     le bon genre de sujet (`at subject is a creature for projectile_hit (when.entity skeleton), and apply_effect acts
     on players; …`) ;
   - le champ cible laissé hors d'`args` : `leave players out: at (actor) says who` (mot pour mot le §8.5), `leave x, y,
     z out: at (position) says where`, `leave fact out: the engine writes what happened` ;
   - `apply_effect` ne donne jamais `wither`, `poison` ni `instant_damage` dans une règle (voir écarts) ;
   - puis, **pour chaque cible que l'effet peut recevoir** (un `subject` de `damage_dealt` sans `when.entity` est un
     joueur ou une créature : les deux sont vérifiées), les arguments avec la cible fictive remplie passent
     `EngineActions.check` avec le `Caller` du Directeur : décodage de l'outil, puis son `check` (identifiants,
     plafonds du chaos, cohérence). `power must be between 0.5 and 4 (got 6)`, `at chaos 3 an explosion has a power of
     at most 3 (asked 3.5)` : mot pour mot le §8.5. Un refus `DENIED (règle)` de l'outil garde sa règle.
4. **Limite** (dans `RuleBook`, qui a l'état) : `DENIED (rule_limit): 8 rules are active (C-60, …); remove one first`,
   avec `mechanics.maxRules`.

Les cibles fictives : un joueur `RuleTargetPlayer` (**16 caractères, la longueur maximale d'un nom**) ; le point `0 64
0` de `when.dimension` (ou de `when.near.dimension`, sinon l'Overworld) ; la créature `00000000-…`. `{actor}` est
remplacé par ce nom avant les vérifications : un texte qui tient avec ce nom tient avec n'importe quel joueur
(`text is longer than 100 characters (got 109)` pour un `actionbar` de 100 caractères avec `{actor}`).

### Les sept exemples du §8.8

Acceptés tels quels au chaos 3 (le défaut), en test unitaire avec les vrais outils et en jeu avec les vrais
identifiants. Au chaos 1 ou 2, la vache (lévitation niveau 2) et les silverfish (rayon 300) sont refusées par les
plafonds : c'est voulu.

### Création, retrait, fin (`RuleBook`)

- `create(spec, caller)` (un verrou : une création ou une fin à la fois) : validation, limite, ligne du canon écrite
  **comme le Directeur** (`Source.DIRECTOR`, tour et conversation du `Caller` ; `CanonDraft(LAW|PLAN, statement, quote,
  players = UUID de when.players, importance, ACTIVE, mechanic = RULE)`), puis l'état sur le thread serveur
  (`RuleState` : échéance = maintenant + `minutes`, `playerIds`, **spécification normalisée**). Si l'état ne peut pas
  être écrit (serveur qui s'arrête), la ligne est résolue `cancelled` (« it never took effect: the server was
  stopping »). Décision `mechanic started` (sujet `C-60`, conversation `mechanics:C-60`).
- `remove(ref, note, author)` : loi → `retired`, plan → `cancelled`. Sortie de l'état d'abord (thread serveur), puis
  canon résolu par **`Source.ENGINE`** avec la note telle quelle ; le tour et la conversation du demandeur vont dans
  l'`Author` du moteur, son nom dans la décision `mechanic removed` (`C-60 law retired by operator Clement: 12 fired, 3
  skipped; « … »`). Une résolution refusée (ligne déjà fermée) ou ratée est loguée ; l'état est retiré quand même.
- `end(id, status, note, decision)` : la même fin, pour M4-18 (une fois, échéance, désactivation) ; `null` si la règle
  n'est plus active.
- `list()` : les règles actives, de la plus ancienne, depuis l'instantané de l'état (tout fil).

### Les textes

- `create_rule` : `ok: rule C-60 (law) active until 10-25 20:15 (in 7d0h): block_break where grief → punish tiny (2)
  on the actor, actionbar to the actor; announce it if you like` (un plan : `; it stays secret`).
- `remove_rule` : `ok: rule C-60 (law) retired (12 fired, 3 skipped)` ; `Invalid arguments: C-60 is not an active
  rule; active: C-61` (ou `none`) ; `Invalid arguments: O-812 is not a rule; active: …`.
- Ligne de situation (`RuleView.line`, `RuleText.line`) : `C-60 law block_break grief → punish, actionbar (2 fired,
  until 10-25 20:15)`, `C-61 plan once dimension_change Bartok the_nether → spawn, notify (3 failed in a row, until
  21:40)`. L'heure seule le jour même, `MM-dd HH:mm` sinon (`RuleText.time`).
- Un Journal indisponible ou trop lent donne `FAILED` ; toute autre exception passe par `ToolRunner` (`FAILED`).

### Les pseudo-outils (`RuleOnlyTools.kt`)

Des `NarratorTool` qu'aucun rôle ne voit (**pas dans `ToolCatalog.allTools`**) : M4-23 les ajoute à `EngineActions`
(`ToolCatalog.allTools(services) + ruleOnlyTools()`). Le moteur remplit ce que le modèle ne peut pas savoir, comme la
cible des autres outils : `creature` (UUID de la créature du déclencheur) et `fact` (ce qui s'est passé).

- **`mob_effect {effect, seconds, level, creature}`** : plafonds des effets nuisibles du chaos (`harmfulSeconds`,
  `harmfulLevel`) **pour tout effet**, nuisible ou non ; chaos 0 : `DENIED (chaos_0): the chaos level is 0: no rule
  changes a creature.` ; refusés (`DENIED (forbidden_effect)`) : `invisibility`, `resistance`, `regeneration`,
  `absorption`, `health_boost`, `instant_health`, `wither`, `poison`, `instant_damage`, et ceux qui agissent sur le monde
  (`forbiddenEffectIds` d'`apply_effect` : présages, `infested`, `oozing`, `weaving`, `wind_charged`).
- **`mob_attribute {attribute, multiply, creature}`** : `MobAttributeKey` de `spawn` et ses bornes, sauf `max_health`
  de **1** à 5 (`max_health multiplies by 1 to 5 in a rule: a rule never lowers a creature's health (asked 0.5)`) ;
  chaos 0 refusé. Modificateur permanent `narrator2:rule/<id>/<attribut>` (`ADD_MULTIPLIED_TOTAL`, montant `multiply −
  1`) posé par `addOrReplacePermanentModifier` ; une `max_health` relevée relève la vie d'autant, une seule fois (pas
  quand le modificateur était déjà là). Une créature sans l'attribut : `FAILED: minecraft:cow has no attack_damage`.
- Les deux marquent la créature (`RuleMarks.mark`) : tags `narrator2` et `narrator2_rule_<id>`. Exécution directe sur le
  thread serveur possible : `MobEffectTool.apply(mob, rule, args)`, `MobAttributeTool.apply(mob, rule, args)` ; par
  `EngineActions.run`, le `run` retrouve la créature par son UUID (`getEntityInAnyDimension`) : `FAILED: the creature of
  the trigger is gone` si elle n'est plus là. La règle de l'acte est lue dans la conversation de son `Caller`
  (`mechanics:C-60`, avec `firingId`) ; hors d'un acte : `Invalid arguments: mob_effect runs only in a rule's act
  (create_rule)`.
- **`notify {note, fact}`** : envoie lui-même `DirectorSignal.Mechanic(RULE, line, now, priority = false)` avec `line` =
  `C-61 fired: <fact>; your note: « <note> »`, coupée à 600 caractères, **et écrit la décision `mechanic notified`**
  (sujet `C-61`, raison = la ligne : le contrat de M4-08). Une fois par règle toutes les 5 min
  (`NOTIFY_GAP_MS`) ; entre-temps : `ok: held: you were told about C-61 30s ago; this one is counted in the next, from
  19:45:00 (1 held)`, et la suivante dit `(+1 more since 19:40:30)`. Compteurs en mémoire (perdus au redémarrage).

## Écarts par rapport au design (et pourquoi)

1. **`apply_effect` dans une règle ne donne jamais `wither`, `poison` ni `instant_damage`** (`DENIED (forbidden_effect):
   effect 1 (apply_effect): a rule never gives instant_damage: an effect that wounds is yours to give, one call at a
   time, never a law's`). Le design ne l'interdisait qu'à `mob_effect`. Une loi agit sans le jugement du Directeur,
   à chaque déclenchement : un effet qui blesse en automatique n'aurait que la garde de mort comme frein. Le Directeur
   garde ces effets pour ses propres appels.
2. **`when.entity player` est refusé sauf pour `damage_dealt`** : pour `kill`, `death`, `projectile_hit` et
   `mob_spawn`, la créature du fait n'est jamais un joueur (le PvP est filtré de `kill`) ; la règle ne se déclencherait
   jamais. Le refus le dit (`… a fight between players is a duel's, never a rule's`) : une « prime » pour un joueur tué
   est refusée à la création. Pour `damage_dealt`, `player` reste permis (une loi contre le PvP).
3. **La spécification gardée dans l'état est normalisée** : `entity`, `block`, `item`, `structure`, `biome`,
   `advancement` en identifiants complets (`minecraft:skeleton`, `#minecraft:diamond_ores`), `dimension` et
   `near.dimension` en identifiants complets (`minecraft:the_nether`), `players` aux noms actuels du Journal. Les
   effets restent tels qu'écrits (cibles remplies au déclenchement). Ainsi l'appariement de M4-18 compare ce que la
   validation a résolu, sans deuxième résolution qui pourrait diverger.
4. **`mob_effect` plafonne tous les effets** (pas seulement les nuisibles) par les plafonds nuisibles du chaos : un
   creeper sous `speed V` 15 min est un châtiment pour les joueurs. Et les deux outils des créatures sont refusés au
   chaos 0.
5. **Champs remplis par le moteur** : `creature` (`mob_effect`, `mob_attribute`) et `fact` (`notify`). Le design disait
   « la créature » sans dire comment elle arrive à l'outil : un argument, comme la cible des autres outils. Le modèle
   ne voit jamais ces outils ; la validation refuse ces champs s'il les écrit.
6. **`RuleIds`** : une interface pour les identifiants du serveur (`ServerRuleIds` en jeu), parce que les tests
   unitaires n'ont ni tags ni registres dynamiques (structures, biomes), ni progrès, ni dimensions. Les tests unitaires
   amorcent quand même les registres du jeu (`Bootstrap`) pour que les `check` réels de `spawn`, `apply_effect`,
   `play_sound` tournent.
7. **Décisions** : `started` à la création, `removed` au retrait (noms du §19) ; `notified` écrite par `notify` lui-même
   (M4-08 l'attribuait à M4-18, mais l'exécution de `notify` est à M4-14).
8. **`punish` est celui de M4-13** (fusionnée pendant ma tâche) : la loi du grief (`punish tiny 2`) passe son vrai
   `check` (sévérité ≤ `maxSeverity`, raison lisible), en test unitaire comme en jeu.

## Ce que les tâches suivantes doivent savoir

### M4-18 (déclencheurs et effets)

- **Remplir la cible** : `RuleTargets.aimed(tool, args, aim)` avec `Aim.Player(nom)`, `Aim.Point(x, y, z, dimension)`,
  `Aim.Creature(uuid)` ou `Aim.Everyone` ; `null` = effet sauté (un `apply_effect` dont le sujet est une créature). Pour
  un outil `Aiming.PLACE` (`particles`, `fireworks`, `lightning`, `explosion`) visant une créature, donnez le
  `Aim.Point` où elle se tient **à l'exécution** (après le délai). `RuleTargets.withActor(args, nom)` remplace
  `{actor}` (appelez-le avant `aimed`). `RuleTargets.subjects(trigger, entity)` dit ce que peut être le sujet.
- **`notify`** : ajoutez `fact` aux arguments (`JsonObject(args + ("fact" to JsonPrimitive(…)))`, ≤ 600 caractères,
  anglais, noms échappés) ; l'outil envoie le `RULE`, tient l'écart de 5 min et écrit `mechanic notified`. **N'envoyez
  pas vous-même de `RULE` pour un `notify`** ; les `RULE` de désactivation et d'échéance sont à vous.
- **`mob_effect`, `mob_attribute`** sur le thread serveur : `ToolArgs.decode(MobEffectArgs.serializer(), json)` puis
  `MobEffectTool.apply(mob, ruleId, args)` (idem `MobAttributeTool`) ; ou `EngineActions.run` avec `creature` rempli.
  Retrait à la fin : tag `RuleMarks.tag(id)`, modificateurs `RuleMarks.modifier(id, key)` pour chaque `MobAttributeKey`,
  puis `NarratorMobs.TAG` quand il ne reste aucun tag commençant par `RuleMarks.TAG_PREFIX` et que la créature n'a pas
  la pièce jointe `narrator2:mob`.
- **Fins** : `RuleBook.end(id, status, note, decision)` (loi `retired` ; plan `fulfilled` après un `once`, `expired` à
  l'échéance, `cancelled` désactivé) ; jamais sur le thread serveur (`services.scope`). Le livre ne prévient personne
  d'une création ni d'une fin : comparez les identifiants de l'état à ceux que vous connaissez (chaque seconde, ou à
  chaque tick) pour appliquer une loi `mob_spawn` aux créatures déjà chargées dès sa création (§8.5) et retirer les
  marques d'une règle partie (y compris par `dropped`).
- **Conditions normalisées** (écart 3) ; `RuleState.playerIds` pour `players`. Compteurs (`fired`, `skipped`,
  `failures`, `lastFiredAt`) : `store.update` sur le thread serveur. Ligne de situation : `RuleView.line` /
  `RuleText.line(rule, now, zone)` ; la ligne `Rules: …` (≤ 400, `(+N more)`) est à vous.
