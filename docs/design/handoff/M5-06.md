# Passation M5-06 : SDK réel — faits, minuteurs, lectures, état

Vague A de M5 (`design/M5.md` §4.2, §4.3, fiche M5-06 au §17.2). Le côté serveur des parties du SDK qui ne font rien au
monde : la traduction des faits du bus (`Facts`, **seul traducteur**), leur file et les abonnements (`Events`), les
minuteurs (`Timers`), les lectures du monde (`World`), le petit état sauvé (`Storage`) et les paramètres d'un
déploiement (`Args`, et leur vérification contre le manifeste au déploiement). Rien n'est encore branché : le moteur
des modules (M5-11) assemble ces pièces dans son `RunContext`. **Le code et cette passation font foi** en cas de
contradiction avec `M5.md`.

**Aucun contrat n'a changé** : ni le SDK (`forge/api`, figé), ni `ForgeLimits`, ni `Mechanics.kt`, ni `MechanicsState.kt`.

## Les faits (`Facts`)

### Traduction (§4.3, table de la passation M5-01)

`at` = le milieu du sol du bloc du fait (`x + 0.5`, `y`, `z + 0.5`), dimension dans la forme du SDK ; identifiants sans
`minecraft:` (ceux d'un autre mod gardent leur espace de noms). `Who(type, uuid, name)` ← `EntityRef` : `type` =
`player` pour un joueur (`EntityRef.player` non nul ou type `minecraft:player`), sinon l'identifiant court ; `name` = le
nom du joueur ou le nom personnalisé de la créature.

| Fait du SDK | Fait du bus | Précisions |
|---|---|---|
| `BlockBroken` | `BlockBroken` | `builtByAnother` = `placedBy` non nul et différent du joueur |
| `BlockPlaced` | `BlockPlaced` | `PlaceKind.BLOCK` seulement (pas de fluide, de feu, de portail) |
| `CreatureHit` / `PlayerHit` | `DamageDealt` | selon la victime ; `health` = `victimHealth` ; `PlayerHit.victim` = le nom du joueur |
| `PlayerHurt` | `DamageTaken` | `cause` = `damageType` court ; `attacker` nul sans attaquant ; regroupé (5 s) par l'Observateur |
| `CreatureKilled` | `EntityKilled` | jamais en JcJ (`pvp`) |
| `ProjectileHit` | `ProjectileHit` | `shooter`, `target` : des `Who` (nuls quand le bus n'en a pas) |
| `PlayerDied` | `PlayerDied` | `cause` court, `killer` : `Who` ou nul |
| `Chat` | `ChatMessage` | **canal `PUBLIC` seulement** ; `at` = la dernière position du rédacteur dans `PlayerStates` (nulle si inconnue) |
| `DimensionChanged` | `DimensionChanged` | `from` = `from.dim`, `to` = `pos.dim`, formes du SDK |
| `StructureEntered`, `BiomeEntered`, `Advancement`, `Crafted`, `Consumed`, `Slept`, `Joined`, `Left` | `StructureEntered`, `BiomeEntered`, `AdvancementEarned`, `ItemCrafted`, `ItemConsumed`, `SleepStarted`, `PlayerJoined`, `PlayerLeft` | `Left` aussi à l'arrêt du serveur (`LeaveReason.SERVER_STOP`) |
| `CreatureAppeared` | (crochet `onMobLoad` du moteur) | `Facts.appeared(mob, level)` : nul pour une créature du Narrateur (tag `narrator2` ou pièce jointe `narrator2:mob`), apprivoisée (`OwnableEntity.getOwnerReference`), nommée ; sinon le joueur en ligne le plus proche (ni spectateur ni `FakePlayer`) à `ForgeLimits.APPEAR_DISTANCE` (64) blocs, ou nul |
| `CreatureGone` | (contrôle de chaque seconde du moteur) | `Facts.gone(entity)` : `unloaded` (`UNLOADED_TO_CHUNK`, `UNLOADED_WITH_PLAYER`), `died` (`KILLED`, ou `isDeadOrDying` pendant l'animation de mort), `vanished` sinon (`DISCARDED`, `CHANGED_DIMENSION`) ; `player` nul |

Tout autre fait du bus rend `null`. **Une prière (`PRAY`), un message privé (`WHISPER`, `/msg`…) et toute commande ne
produisent jamais de fait** ; aucun autre fait ne porte un texte écrit par un joueur.

### Seul traducteur (constat 11) : comment c'est vérifié

`FactsTest` › *Facts is the only class of the mod that turns the bus into facts* lit le **bytecode** de tout le mod
(classes Kotlin et Java du `main`) avec ASM : seule une classe de `forge/sdk/Facts*` peut à la fois **construire** un
record de `GameFact` (`NEW io/github/…/forge/api/GameFact$…`) et **nommer une classe du bus**
(`io/github/clemsix6/narrator2/event/`). Conséquences pour les tâches suivantes :

- le moteur (M5-11) peut recevoir des `GameEvent` et manipuler des `GameFact`, mais **ne construit aucun fait** : il
  appelle `Facts.of`, `Facts.appeared`, `Facts.gone` ;
- le banc (M5-08, `forge/sim`) peut construire des faits (il ne voit jamais le bus) ;
- une classe qui ferait les deux casse ce test : c'est voulu.

## Les abonnements et la file (`FactQueue`)

- `on(type, handler)` : `type` ∈ `Facts.TYPES` (jamais `GameFact` lui-même, jamais une autre classe : `ForgeRefusal`) ;
  `handler` non nul ; 16 abonnements actifs au plus (`ForgeRefusal … cancel one first`) ; un abonnement annulé libère sa
  place. Paramètres déclarés nullables : un `null` d'un module donne une `ForgeRefusal`, pas une `NullPointerException`.
- `offer(fact)` (tout fil, l'appel du bus) : mis en file **seulement si un abonnement actif veut sa classe à cet instant**
  (`wanted`, volatil) ; au-delà de `FACTS_PER_TICK` (256) faits en attente, jeté et compté.
- `drain(now)` (thread serveur, une fois par tick) : chaque fait en attente, dans l'ordre, à chaque abonnement actif de
  sa classe, dans l'ordre où ils ont été faits. **Les limites comptent les livraisons** (un fait livré à deux
  abonnements compte deux) : 256 par tick, 3 000 par minute ; le reste est jeté et compté. La minute est une fenêtre
  fixe qui commence à la première livraison (pas une fenêtre glissante).
- `Delivery.deliver()` appelle le gestionnaire **sauf si son abonnement a été annulé entre-temps** (par une livraison
  précédente du même tick) : « no more facts from now on, even those already queued ». `live` permet au moteur de ne pas
  armer d'appel pour rien ; `label` (`subscription 2 (Chat)`) sert aux journaux.
- `takeDropped()` rend le nombre de faits jetés depuis le dernier appel (le moteur en fait la décision
  `facts_dropped`, une par minute au plus).
- `stopping()` : plus d'abonnement (`ForgeRefusal`) ; `close()` : tout annulé, file vidée, `on` refusé, `offer` ignoré.
- Écart assumé : un abonnement fait pendant un tick reçoit au tick suivant les faits de sa classe déjà en file (ceux
  qu'un autre abonnement de même classe avait fait mettre en file). Sans importance pratique (on s'abonne dans `start`).

## Les minuteurs (`Scheduler`)

- Le `Scheduler` compte **ses propres ticks** : le moteur appelle `advance()` une fois par tick, puis `next()` jusqu'à
  `null`, et lance chaque `Due.run()` dans un appel armé. Un minuteur fait au tick `t` pour `n` ticks est dû à `t + n`
  (au plus tôt le tick suivant) ; ordre : échéance, puis ordre de création ; un minuteur répétitif est replacé à
  `tick + période` **dans `next()`, avant de lancer la tâche** (une `ForgeLimit` au milieu ne laisse rien à moitié fait).
- Limites : délai 1 à 72 000, 64 en attente (répétitifs compris), 16 répétitifs ; au-delà `ForgeRefusal`, rien ne change.
  Un minuteur unique sorti par `next()` libère sa place avant de tourner.
- `cancel()` (deux fois : rien), `active()` ; `Due.run()` ne lance rien si le minuteur a été annulé entre-temps.
- `stopping()` : plus de minuteur ; `close()` : tout annulé, `after`/`every` refusés.

## Objets du module opaques (constat 8)

`FactQueue` et `Scheduler` gardent les `Consumer`/`Runnable` du module tels quels, dans des objets à nous (`Sub`,
`Timer`) : jamais une clé de map ou d'ensemble, jamais journalisés, jamais d'`equals`/`hashCode`/`toString` (retraits
par identité, file de priorité ordonnée sur nos propres champs). Ils ne sont appelés que par `Delivery.deliver()` et
`Due.run()`, **que le moteur doit lancer dans un appel armé par l'hôte**. `FactQueueTest` et `SchedulerTest` le
prouvent avec des gestionnaires et des tâches dont `equals`, `hashCode` et `toString` lèvent, et qui échouent s'ils
tournent hors d'un appel « armé » par le test. Les autres objets reçus d'un module par mes pièces sont des `String`,
des `Class`, des records du SDK (`Place`, `Cell`) : des classes finales du JDK ou du SDK, dont les méthodes sont les
nôtres.

## Les lectures (`WorldView`)

- **Thread serveur seulement** (`server.isSameThread`, sinon `ForgeRefusal`) ; **jamais de chargement de tronçon** :
  tout passe par `ServerChunkCache.getChunkNow` (nul si non chargé) ou `getEntitiesOfClass` (qui ne charge rien).
- Joueurs : les vrais joueurs en ligne, **ni spectateurs ni `FakePlayer`**, dans l'ordre d'arrivée
  (`playerList.players`) ; par nom sans tenir compte de la casse. Le même filtre vaut pour `count` (−1 pour un
  spectateur, comme `player` rend `null`). `PlayerInfo` : pieds (`x`, `y`, `z`), `health`, `maxHealth`, `food`,
  `gameMode().serializedName`, `onGround()`, `isShiftKeyDown` (accroupi), `isSprinting`, `isSwimming`, `isFallFlying`,
  `yRot`, `xRot`, l'objet en main (`air` main vide), `underground` lu dans `PlayerStates` (la notion du Narrateur,
  rafraîchie chaque seconde par l'échantillonneur ; faux tant qu'il n'a pas vu le joueur).
- Créatures : des `Mob` vivants dans la boîte de `radius`, puis dans la sphère, les plus proches d'abord, 32 au plus ;
  `radius` hors de 0–48 (NaN compris) → `ForgeRefusal` ; `type` inconnu → `ForgeRefusal` avec les identifiants les plus
  proches (`closestIds`) ; `player` → `ForgeRefusal` (« read world().players() »). `own` vient d'un **prédicat donné au
  constructeur** (`own: (Entity) -> Boolean`) : c'est M5-07/M5-11 qui savent quelles créatures sont au déploiement (ses
  marques `narrator2_module_<id>`).
- Blocs : `null` hors tronçon chargé ; `air` = `isAir`, `liquid` = `BlockState.liquid()` (eau, lave),
  `solid` = forme de collision non vide (on peut se tenir dessus : dalle, verre, feuilles…), `placedByPlayer` =
  `PlacedBlocks.placerAt(chunk, pos)` (qui retire au passage une entrée périmée de l'index : le comportement normal de
  tous ses lecteurs).
- `surface` = `chunk.getHeight(MOTION_BLOCKING, x & 15, z & 15) + 1`, c'est-à-dire `Level.getHeight` (vérifié en jeu) ;
  `Integer.MIN_VALUE` hors tronçon chargé. `biome` : vérifie le tronçon avant `getBiome`. `dayTime` =
  `floorMod(overworld.defaultClockTime, 24 000)` ; `weather` : orage, pluie ou clair dans l'Overworld.
- Dimension inconnue → `ForgeRefusal` qui liste celles du serveur. `close()` : tout refusé.

## L'état (`StorageMap`)

- `LinkedHashMap` : l'ordre de première écriture (une clé retirée puis remise repasse à la fin) ; `keys()` est une
  copie non modifiable. `put(clé, null)` retire. Clé de 1 à 40 caractères (vide ou nulle : `ForgeRefusal`, y compris en
  lecture) ; valeur de 512 ; 64 clés ; **8 192 caractères en tout, clés et valeurs** ; une écriture au-delà ne change rien.
- `putInt`/`putDouble` écrivent le texte (`Int.toString`, `Double.toString`) ; `getInt`/`getDouble` rendent le repli
  quand la valeur n'est pas un nombre.
- **Les écritures marchent pendant `stop`** (un module sauve à `SERVER_STOPPING` ce qu'il lui faudra au redémarrage) ;
  seul `close()` (après `stop`) les refuse. `changes()` rend une copie quand l'état a changé depuis le dernier appel
  (réécrire la même valeur ne compte pas) : à recopier dans `ModuleRun.storage` chaque seconde **et après `stop`** ;
  `snapshot()` marche encore après `close()`.

## Les paramètres (`ParamCheck`, `ArgsView`)

### Au déploiement : `ParamCheck.check(specs, given, lookup)` (§6.4, étape 3)

- `specs` = `ArsenalEntry.params` ; `given` = `deploy_module params` ; `lookup` = un `ParamLookup` (le serveur :
  `ServerParamLookup(services, caller)`). Rend `CheckedParams(params, players)` ou lève
  `MechanicRejected(null, …)` → `Invalid arguments: …`, au premier problème, dans l'ordre du manifeste.
- **Forme résolue** (à ranger dans `ModuleRun.params`) : **chaque** paramètre du manifeste y est, replis compris
  (vérifiés et résolus comme une valeur donnée), `null` pour « aucun ». `PLAYER` → le nom tel que le Journal le connaît ;
  `PLAYERS` → tableau de ces noms ; `INTEGER` → entier ; `NUMBER` → réel ; `TEXT` → texte coupé de ses espaces (un
  choix rendu dans sa forme du manifeste : `SÉVÈRE` → `sévère`) ; `BOOLEAN` → booléen ; `PLACE` → `{"x", "y", "z",
  "dimension"}` (forme du SDK), **un nom de joueur résolu là où il se tient** (`ParamCheck.json(place)`).
- `players` : les joueurs nommés par les `PLAYER`/`PLAYERS`, une fois chacun (→ `ModuleRun.playerIds` et les joueurs de
  la ligne du canon). Le joueur qui a servi à résoudre un `PLACE` n'en fait pas partie (c'est un lieu, pas un
  participant).
- Formats acceptés (Javadoc de `ParamType`) : JSON, ou la forme texte dans une chaîne JSON (`"6"`, `"Bartok, Mimosa"`,
  `"120 64 -30 nether"`, `"TRUE"`). Un tableau vide et `null` valent « laissé de côté ». Un `PLACE` objet n'accepte que
  `x`, `y`, `z`, `dimension` (une faute de clé n'envoie pas en silence dans l'Overworld).
- Refus (exemples exacts, testés) : `params.ducks is not a parameter of this module; its parameters: …` ;
  `params.wolf is required: <doc>` ; `params.chickens must be between 3 and 8 (got 12)` ; `… must be a whole number
  (got 4.5)` ; `params.speed must be at least 0.5 (got 0.1)` ; `params.hunters names Mimosa twice` ;
  `params.hunters must name between 1 and 8 players (got 9)` ; `params.mood must be one of: taquin, sévère (got
  "gentil")` ; `params.note must have between 3 and 300 characters (got 2)` ; `params.arena: Mimosa is not online (…);
  give x, y and z instead` ; `params.arena: unknown dimension "moon"; dimensions: overworld, the_nether, the_end` ;
  `params.wolf: no player named Bob has ever played here; online: …` (le texte de `knownPlayers`, comme les règles) ; un
  repli fautif : `params.victim (its fallback): …`.
- Plafonds durs de la Javadoc de `ParamType` : 8 joueurs, 300 caractères, ceux du manifeste (`Manifest.PARAM_PLAYERS`,
  `Manifest.PARAM_TEXT_CHARS`, M5-09 : une seule source). Un texte vide (après rognage) est refusé, même si le manifeste
  permet une longueur minimale de 0 : un texte vide ne dit rien, `fallback = ""` veut déjà dire « aucun ».

### `ServerParamLookup(services, caller)`

`players` = `ToolContext(services, caller, …).knownPlayers(names, field)` (le Journal, comme `create_rule` ; une
`Refusal` devient `MechanicRejected`) ; `standing` = la position des pieds d'un joueur en ligne (pas un `FakePlayer`,
spectateurs admis : ce n'est qu'un lieu), lue sur le thread serveur ; `dimensions` = `server.levelKeys()`. **Jamais sur
le thread serveur** (il l'attend).

### À l'exécution : `ArgsView(specs, params)`

- Lit la forme résolue, vérifiée **une fois, à la construction** : une valeur qui n'est pas de son type, ou un `PLACE`
  donné par un nom de joueur (non résoluble ici) → `IllegalArgumentException` (pour M5-11 : démarrage raté,
  `restart_failed`). Une clé absente lit le repli (les `ModuleRun` d'avant la résolution complète, comme
  `ForgeSamples.run`).
- Nom non déclaré, ou méthode d'un autre type → `ForgeRefusal` qui dit la bonne méthode (`Args.integer: "wolf" is a
  PLAYER parameter: read it with args().player("wolf")`) ; `number` lit aussi un `INTEGER` ; `integer`, `number`,
  `bool` sans valeur → `ForgeRefusal` (`has no value`) ; `players` rend une liste non modifiable, vide sans valeur.

## Ce que les tâches suivantes doivent savoir

### M5-11 (le moteur des modules)

Assemblage d'un déploiement dans `RunContext` (aucune de mes classes ne connaît l'hôte ni le `Meter`) :

- `args = ArgsView(entry.params, run.params)` ; `events = FactQueue()` ; `timers = Scheduler()` ;
  `world = WorldView(server, services.players, own = <le prédicat de M5-07 : marque du déploiement>)` ;
  `storage = StorageMap(run.storage)`.
- `listensTo = Facts.EVENTS` ; `onEvent(envelope)` : `Facts.of(envelope.event, services.players)` une fois, puis
  `queue.offer(fact)` pour chaque déploiement (`wants(fact.javaClass)` évite un appel inutile). `offer` est sûr depuis
  tout fil.
- `onMobLoad` : `Facts.appeared(mob, level)` seulement si un déploiement `wants(GameFact.CreatureAppeared::class.java)` ;
  chaque seconde, `Facts.gone(entity)` pour chaque créature du module partie.
- Chaque tick, par déploiement : `for (d in events.drain(now)) if (d.live) host.invoke { d.deliver() }` ; puis
  `timers.advance()` et `while (true) { val due = timers.next() ?: break; host.invoke { due.run() } }` (un `Due` à la
  fois : une tâche peut en annuler une autre). **Jamais `deliver()` ni `run()` hors d'un appel armé.**
- Chaque seconde : `storage.changes()?.let { … ModuleRun.storage = it }` ; `events.takeDropped()` → décision
  `facts_dropped` (une par minute au plus).
- Fin : `events.stopping()`, `timers.stopping()` (et `acts.stopping()` de M5-07), `stop(why)` mesuré, puis
  `storage.changes()` une dernière fois, puis `close()` sur les cinq (`args`, `events`, `timers`, `world`, `storage`).
  Une poignée gardée par le module (un champ statique) ne fait plus que des `ForgeRefusal`.
- Déploiement, étape 3 : `ParamCheck.check(entry.params, spec.params, ServerParamLookup(services, caller))` hors du
  thread serveur ; `CheckedParams.params` → `ModuleRun.params`, `players` → `ModuleRun.playerIds` (UUID en texte) et
  les joueurs de la ligne du canon.

### M5-07 (actes, créatures)

- `WorldView` attend le prédicat `own: (Entity) -> Boolean` : exposez-en un (la marque `narrator2_module_<id>`).
- `Facts.gone(entity)` donne le `CreatureGone` de vos créatures parties ; `Facts.who(EntityRef.of(entity))` un `Who`.

### M5-08 (le banc)

Rien n'est imposé, mais `StorageMap`, `Scheduler`, `FactQueue` et `ArgsView` ne dépendent pas du serveur : le banc peut
les reprendre. `Bench.start("chickens=4")` → `JsonObject(mapOf("chickens" to JsonPrimitive("4")))` passe par
`ParamCheck.check` avec un `ParamLookup` du banc (ses joueurs, ses positions, les trois dimensions).
