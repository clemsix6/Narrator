# Passation M4-01 : contrats de M4

état vivant et son codec, crochets Fabric, moteur désactivé, migration V3, catégories et plafonds des châtiments,
contrat étendu des garde-fous, signal du Directeur, configuration `mechanics`, textes des joueurs, familles d'outils
et commandes vides, faux et échantillons. Le serveur tourne avec `DisabledMechanics("not wired yet")` jusqu'à M4-23 ;
le Directeur voit toujours ses 37 outils. **En cas de contradiction avec `M4.md`, le code et cette passation font
foi.** Les décisions G à L du superviseur sont consignées au §24.3 de `M4.md` (toutes les recommandations acceptées).

## Écarts par rapport au design (et pourquoi)

Le propriétaire laisse les structures libres ; chaque écart rend un contrat partagé plus sûr ou moins cher.

### Spécifications et coût du schéma (§5.1, §12.1)

1. **`StakeSpec` est scindé en `RewardSpec` et `ForfeitSpec`.** Mesuré : avec `StakeSpec`, les arguments des sept nouveaux outils faisaient **14 154 caractères** de schéma à eux seuls, plus que tout le budget du §12.1 (14 000 caractères, descriptions comprises). Maintenant :
   - `RewardSpec(kind: RewardKind, item, count, name, effect, seconds, level, minutes)` : la récompense, jamais `punish` (le type l'interdit, plus besoin de le valider) ; `RewardKind.tool` dit l'outil qui la paie (`give_item`, `apply_effect`, `favor`, `favor`).
   - `ForfeitSpec(punishment: PunishmentId, severity: Int = 1)` avec `@Range(1.0, 2.0)` : le gage (décision H) est borné **dans le schéma même** (`penalty.severity must be between 1 and 2 (got 3)`).
   - **Plus de `lore`** sur une récompense (220 caractères de schéma) : un objet peut être nommé (« La Pioche du Pardon ») ; son histoire, le Directeur la raconte lui-même.
2. **`@Doc` raccourcis** partout (types de M4 et arguments `PunishArgs`, `FavorArgs`, `EndChallengeArgs`, `RemoveRuleArgs`) : ce que le nom dit déjà n'a plus de description ; les consignes vont dans les descriptions d'outils. Total des arguments : **9 261 caractères** ; `MechanicsContractsTest` les borne à **9 300**, ce qui laisse ≈ 4 700 caractères aux noms et descriptions des sept outils (≈ 3 800 au §12.2, ≈ 4 150 avec les noms et les clés JSON des définitions). Voir « Toutes » plus bas.
3. Les propriétés Kotlin sont en camelCase avec `@SerialName` (`noArmor` → `no_armor`, `yAbove`, `delaySeconds`…), comme le reste du code ; sur le fil, rien ne change.
4. `PlaceSpec.isEmpty` et `RewardKind.tool` : deux aides sans état.

### État vivant (§3.2)

5. **`Participant.late`** : le design dit « un joueur arrivé en cours de défi peut gagner, jamais perdre », mais l'état ne savait pas qui était inscrit au départ. `late = true` pour un participant ajouté après le départ ; la pénalité l'épargne.
6. **`Participant.out` est une énumération `OutReason`** (`died`, `armor`, `left`, `declined`) au lieu d'une chaîne.
7. **`RuleState.playerIds`** : les UUID de `when.players`, résolus à la création (§8.3 « changés en UUID à la création ») ; le design ne disait pas où les garder.
8. **`MechanicsState.unreadable`** (`@Transient`, jamais sauvé) : ce que le décodage a écarté (`Unreadable(what, id, error)`). Le design voulait une décision `mechanic unreadable` et un canon `cancelled` à la réconciliation, mais le codec n'a ni services ni base : il garde la trace pour le moteur (M4-02).
9. Clés JSON en snake_case (`last_challenge_at`, `ends_at`…) ; le JSON s'écrit **valeurs par défaut comprises** (`encodeDefaults`) : un défaut changé dans une version future ne change jamais le sens d'un état sauvé. Lecture tolérante (`ignoreUnknownKeys`) ; chaque défi, règle, retour et règlement se décode seul.
10. `ChallengeState` exige exactement un de `spec` et `duel` (`init { require }`) : une entrée qui viole la règle est écartée au décodage. Aides : `ref`, `isDuel`, `title`, `participant(uuid)` ; `MechanicsState.challenge(id)`, `rule(id)` ; `RuleState.ref` ; `Participant.playerId`.
11. **Les `TYPE` de pièces jointes sont paresseux** (`by lazy`) : `MechanicsState.TYPE`, `ReminderState.TYPE`, `BlockRestorer.TYPE` **et `GuardState.TYPE`**. Toucher le type l'enregistre toujours (les crochets le font à l'initialisation du mod) ; mais un test unitaire peut maintenant se servir du codec sans le registre de Fabric, qui ne s'initialise pas hors du jeu (`NoClassDefFoundError: AttachmentRegistryImpl`).

### Moteur (§4.1)

12. **`MechanicPart` reçoit aussi les crochets** : `listensTo` (les classes de faits voulues, pour le filtre du bus), `everyTick`, `onJoin`, `onLeave`, `onRespawn`, `onMobLoad`, `allowDeath` (le premier refus l'emporte). Sinon `MechanicsService` (M4-23) aurait dû connaître chaque partie ; l'hôte (M4-02) les distribue toutes pareil.
13. `RuleView` gagne `skipped` et `failures` (`/narrator rule list` les montre, §18.1).
14. `MechanicRejected.toResult()` : `DENIED (rule): …` avec une règle, `Invalid arguments: …` sans.
15. `DisabledMechanics(reason, ui)` : `ui` donne le texte `mechanics.unavailable` des réponses de `/duel` et `/bet` (une ligne anglaise sans `ui`, pour les tests). Son contrôle des défis et celui des règles sont deux objets (deux `list()` de types différents ne tiennent pas dans une classe). Règle de ses refus : `DisabledMechanics.MECHANICS_OFF`.
16. `ChallengeOutcome` a `id`.

### Garde-fous (§13.2)

17. **`LedgerPurpose`** (`CONFISCATION`, `STAKE`, `OFFERING`, `OWED`) au lieu d'une chaîne `purpose`. Une valeur inconnue (écrite par une version future) se relit `CONFISCATION` : les objets reviennent à leur propriétaire à l'échéance, la voie sûre.
18. **`OpenEpisode.turnId` est renommé `act`** ; écrit `act`, relu depuis `turn_id` pour un état d'avant M4. `GuardsImpl` ouvre déjà les épisodes et sauve `OpenEpisode` avec `caller.act` (identique au tour pour le Directeur) ; `TargetingPolicy` compare encore `turnId` (M4-04).
19. `GuardState` a bien 14 champs (`graceUntil`, `lastGraceEnd`, `jokersGivenAt`, `lastOfferAt` ajoutés), tous facultatifs.
20. `PunishmentCategory` a en plus `phrase` (pour les refus : `made smaller or bigger`), `rests` (`other` ne se repose jamais), `ofId` et `of(PunishmentId)` (le tableau du §6.3, pour que `punish` et le test des catégories partagent la même source). L'effet `unluck` est rangé dans `other`, comme l'attribut `luck` (le design disait « tout autre effet nuisible » → `harm`) : la malchance change le butin, elle ne blesse pas.
21. `FakeGuards` enregistre aussi le péril de chaque garde de mort armée (`armedPerils`), et répond à `pardon`, `grace`, `isPunished`, `rescue`, `pacing` (voir « Toutes »).
22. **`ToolContext.punish(…, category)` et `NarratorExplosionDamage.allow(…, category)`** : ces deux aides appellent `hostile` et n'appartenaient à aucune tâche ; sans le paramètre, M4-03 n'aurait pas pu passer la catégorie sans toucher des fichiers à personne. Défaut `null`, aucun comportement changé.

### Mémoire (§3.3, §10)

23. **`CanonMechanic`** (`CHALLENGE`, `DUEL`, `RULE`) au lieu d'une chaîne ; `kinds` (les sortes de canon permises : `challenge`, `challenge`, `law`/`plan`) et `endedBy` (`end_challenge`, `remove_rule`, pour le refus du magasin) ; `CanonMechanic.of(id)`.
24. `CanonKind.PLAN(dueAllowed = false)`, clôtures `fulfilled`, `expired`, `cancelled` dans `closedBy` (la branche explicite demandée ; `allows` reste générique).
25. `MemoryLimits.ACTIVE_ARCS` (2), `ARC_MAX_DAYS` (7), `THEME_REST_PLAY_HOURS` (20), `THEME` (`[a-z0-9_]{2,40}`) : M4-07 ne possède pas `MemoryTypes.kt`.
26. V3 commente ses deux colonnes (`COMMENT ON COLUMN`), sans chevrons. **`MemorySchema.MIGRATION` vaut maintenant `V3__mechanics.sql`** : la mémoire exige V3 (M4-07 lit les nouvelles colonnes) ; un Journal resté en V2 laisse la mémoire désactivée avec ce nom dans la raison.
27. **V3 remplace aussi les commentaires de V1 qui nommaient Jev** (demande du superviseur après REFLEX-HAIKU ; une migration publiée ne se modifie pas) : `llm_calls` (« One row per Claude call, role reflex included »), `llm_calls.provider` (`anthropic`, `jev` pour les vieilles lignes), `llm_calls.role` (`… or reflex: the small model that reads the chat`) et `chat_signals.source` (`reflex:` suivi du modèle, ou `heuristic`). Le commentaire de la table `llm_calls` entre dans la description du schéma montrée au modèle (`SchemaDoc`, section `TABLES`) : **1 797 caractères sur 1 800**, il ne reste que 3 caractères dans cette section. Les commentaires `--` de V1 (`jev:<model> | heuristic`, `anthropic | jev`) restent : ils ne sont pas dans la base. Test : `MemorySchemaTest` › *no comment of the schema names Jev any more…*.

### Directeur, configuration, textes

28. `EventFormatter.MECHANIC_LINE_MAX` = `MechanicsLimits.EVENT_LINE` = **1 000 caractères** après le mot-clé (une fin de défi avec enjeux et paris dépasse les 600 de la mémoire) ; la ligne est échappée de nouveau et coupée, comme celles de la mémoire.
29. `MechanicsConfig` est placée entre `memory` et `safety` (la section `reflex` de REFLEX-HAIKU suit `safety`) ; `enabled` n'est lu qu'au démarrage (comme la mémoire).
30. **Textes** : `offer.unavailable` devient **`mechanics.unavailable`** (les trois commandes de joueur, moteur arrêté). Ajouts : `duel.where.arena` (`x`, `y`, `z`) et `duel.where.here` (le `{where}` de `duel.invite`), `duel.cancelled`, `bet.on_nobody` (le `{on}` de `bet.placed` pour « personne »), `offer.returned` (`items` ; `items.returned` dit « confisqué », faux pour une offrande), `items.delivered` (`items`, ce qui était dû et trouve enfin de la place), `joker.given`. **Aucune autre tâche ne possède `UiTexts.kt` ni `fr.properties`** : j'ai mis toutes les clés dont j'ai vu le besoin.
