Vague A de M6 (`design/M6.md` §9, §13, §15, fiche M6-13 ; décision D7 du superviseur : serveur vide seulement ;
relecture, constat 1). `/narrator restart` reconstruit le Narrateur sans arrêter Minecraft : l'ancien runtime s'arrête,
un nouveau s'ouvre (réglages relus, Journal rouvert, mémoire relue) et se câble, pendant que les connexions attendent.
Il sert surtout à sortir d'un `DisabledJournal` sans redémarrer le serveur. **En cas de contradiction avec `M6.md` §9,
le code et cette passation font foi.**

## La commande

```
> narrator restart                         (un joueur en ligne)
[Narrator] cannot restart: 1 player online (Bartok); restart when the server is empty, or restart the server.
> narrator restart                         (serveur vide)
[Narrator] restarting the Narrator; the logins wait until it is done…
[Narrator] Narrator restarted in 0.5 s: Journal available · memory on · mechanics on · forge on
```

Refus (`cannot restart: …`) : un joueur en ligne (`2 players online (Bartok, Mimosa); …`), **un joueur en train de se
connecter** (`1 player joining (Bartok); …`, phase de connexion ou de configuration), le serveur qui s'arrête (`the server
is stopping`), un redémarrage déjà en cours (`a restart is already running`). Un échec : `the restart failed after 6.2 s,
the Narrator stays off: <raison>; /narrator restart tries again.`, en rouge. La réponse finale part aussi aux opérateurs
(`broadcast`).

**Un opérateur en jeu est un joueur en ligne** : depuis le jeu, la commande est donc toujours refusée. Elle se lance de
la console du serveur, ou par RCON (la réponse RCON ne porte que la première ligne ; la fin arrive dans le journal du
serveur et chez les opérateurs).

## L'ordre exact

```
1. Thread serveur (la commande)                                            RestartSequence.start
   refus ? (RestartSequence.refusal(server, …) : joueurs en ligne, en connexion, serveur qui s'arrête)
   porte des connexions posée (une CompletableFuture ; un 2e redémarrage est refusé tant qu'elle existe)
   ancien runtime.stopInGame() : ShutdownSequence.stopInGame (phase STOPPING → tableau de bord → mécaniques (modules
       arrêtés, état gardé dans le monde, barres retirées) → Forge), puis flush() de l'Observateur ; current = null
   lancement du fil « narrator2-restart » (pas un démon : un arrêt du serveur pendant ce temps attend la fermeture du Journal)
2. Fil narrator2-restart
   ancien runtime.stopAndClose() : ShutdownSequence.stopWaiting (mémoire ≤ 11 s → travail en cours ≤ 2 s → abonnements
       du Directeur) puis close (bus → Journal ≤ 12 + 2 s → clients → STOPPED)
   NarratorRuntime.prepare(server) : réglages relus (ou défauts), puis runtime.prepare() : Journal (3 tentatives en 10 s,
       JOURNAL-RETRY), PlayerStates, prepareMemory (schéma puis horloges, 30 s au plus ensemble)
3. Thread serveur (une tâche server.execute)
   serveur qui s'arrête ? → pas câblé
   nouveau runtime.wireAndRun() : wire() (tick, bus, abonnement des états des joueurs, garde-fous (registerLoaded),
       Observateur, réflexes, travailleurs, mémoire (createMemory(prepared)), veille du style, relecture, Forge (démarrée
       hors du thread serveur), mécaniques (Engine.start : réconciliation, modules redémarrés à leur construction),
       Directeur (rappels relus du monde), tableau de bord), puis current = nouveau, ligne « ready »
   finally : porte complétée → les connexions reprennent
   en cas d'échec : log « restart: cannot start, the Narrator stays off », nouveau.stopInGame() (ce que le câblage a fait)
4. Fil narrator2-restart
   en cas d'échec : nouveau.stopAndClose() (son Journal, ses clients)
   RestartReport ; sur le thread serveur (abandonné si le serveur est arrêté) : décision operator restarted (nouveau
       Journal), réponse à l'opérateur ; puis la porte est retirée : un nouveau redémarrage peut partir
```

Au démarrage du serveur (`SERVER_STARTED`), `start(server)` enchaîne `prepare()` puis `wire()` **sur le thread serveur**,
comme avant (ARCHITECTURE §17.8 inchangé) ; un échec appelle `abandon()` = `stopInGame()` + `stopAndClose()`.

## Écarts et décisions

1. **Refus aussi pour un joueur en train de se connecter.** `QUERY_START` ne retient que les connexions qui l'atteignent
   pendant le redémarrage ; un joueur déjà au-delà (fin de la phase de connexion, phase de configuration) entrerait sans
   Narrateur. Les connexions dont l'écouteur est `ServerLoginPacketListenerImpl` ou `ServerConfigurationPacketListenerImpl`
   (`server.connection.connections`, sous son verrou) sont donc un refus, nommées (`getUserName()`, `owner.name()`).
   Vérifié à javap. Un client bloqué en connexion retarde un redémarrage de 30 s au plus (la limite du jeu).
2. **L'Observateur est vidé à l'étape 1, sur le thread serveur** (le design le mettait à l'étape 2) : ses parties sont
   « server thread only », et serveur vide, il ne tient rien.
3. **`Restartable`** : la séquence ne connaît pas `NarratorRuntime` (les tests unitaires ne peuvent pas en construire un) ;
   le runtime l'implémente. Ses deux moitiés d'arrêt valent aussi pour un runtime au câblage raté (ce qui a été créé) ou
   jamais câblé (ce que `prepare` a ouvert) : c'est le nouvel `abandon()`.
4. **`abandon()` arrête aussi les mécaniques** quand elles ont été créées (un câblage qui échouait dans `createDirector`
   laissait un moteur démarré, ses fils de modules compris).
5. **`PlayerStates` est créé dans `prepare()`** (le `DuckPlayClock` de la mémoire le prend) ; il s'abonne au bus dans
   `wire()`.
6. **Le nouveau runtime n'est jamais câblé si le serveur s'arrête** pendant l'échange, ou si le thread serveur ne prend
   pas la tâche du câblage en 60 s (`WIRE_WAIT_MS`) : le fil du redémarrage réclame la tâche (un `AtomicBoolean`), la tâche
   tardive ne câble plus rien, et le nouveau runtime est fermé. Un serveur arrêté exécute une tâche sur le fil appelant :
   détecté (`isSameThread`), jamais câblé ailleurs.
7. **La porte des connexions et le verrou du redémarrage sont deux choses** : les connexions reprennent à la fin du
   câblage (étape 3) ; un autre `/narrator restart` n'est possible qu'à la fin du fil (étape 4), pour qu'un runtime raté
   finisse de fermer son Journal avant qu'un suivant l'ouvre.
8. **Décision `operator restarted`** (`DecisionRecord.Kind.OPERATOR`), dans le Journal du nouveau runtime : sujet = qui l'a
   demandé, raison = la réponse et les durées (`stop 174 ms · prepare 279 ms · wire 2 ms · 489 ms without a Narrator`),
   détail JSON `stop_ms`, `prepare_ms`, `wire_ms`, `gap_ms` (le trou de journalisation : de `current = null` à
   `current = nouveau`), `total_ms`, `journal`, `memory`, `mechanics`, `forge`. Un redémarrage qui laisse le Narrateur
   éteint n'a pas de décision (pas de Journal) : il est dans le journal du serveur (`WARN`).
9. **`NarratorRuntime.restart(…, prepare)`** prend la fabrique du nouveau runtime en paramètre (par défaut
   `prepare(server)`) : le GameTest y tient le fichier du Journal juste avant l'ouverture. Pas de crochet de test mutable.
10. **Chaque redémarrage réécrit la ligne `ready`** (même texte qu'au démarrage, `summary()` partagé).

## Mesures

- **`ServerLoginPacketListenerImpl.MAX_TICKS_BEFORE_LOGIN` = 600 ticks** (javap `-constants` sur le jar 26.3 :
  `sipush 600` puis `multiplayer.disconnect.slow_login`), soit **30 s** à 20 ticks par seconde : un joueur retenu plus
  longtemps est déconnecté (« slow login ») et réessaie. Le compteur avance pendant l'attente de Fabric.
- **Durée d'un redémarrage** (monde neuf ou presque, Journal de 3 à 11 Mo, machine partagée avec d'autres builds) :

  | Où | Total | Arrêt | Préparation | Câblage (thread serveur) | Sans Narrateur |
  |---|---|---|---|---|---|
  | GameTest, 1 défi, 1 loi, 1 module | 0,5 s | 299 ms | 138 ms | 7 ms | 454 ms |
  | GameTest, Journal tenu par un autre processus | 7,0 s | 2 ms | 6 912 ms (3 tentatives) | — | — |
  | GameTest, juste après (Journal libéré) | 0,1 s | 2 ms | 106 ms | 2 ms | 128 ms |
  | Serveur réel, console, 1er | 0,5 s | 174 ms | 279 ms | 2 ms | 489 ms |
  | Serveur réel, console, 2e (serveur en pause, vide depuis 60 s) | 0,6 s | 149 ms | 334 ms | 1 ms | 564 ms |
  | Serveur réel après la fusion de M6-10, tableau de bord actif, 1er | 0,2 s | 48 ms | 119 ms | 4 ms | 159 ms |
  | Idem, 2e (en pause) | 0,1 s | 25 ms | 94 ms | 8 ms | 128 ms |

  Bornes au pire : arrêt ≈ 27 s (mémoire 11, travail 2, Journal 14), préparation ≈ 40 s (Journal 10, mémoire 30) :
  au-delà de 30 s, un joueur qui se connectait est déconnecté et réessaie ; d'ordinaire, une demi-seconde.
- **Le câblage tient en 1 à 7 ms sur le thread serveur** (gardes, Forge, mécaniques compris) : `createForge` ne fait que
  construire le service et lancer son démarrage dans `services.scope`, `createMechanics` démarre le moteur (réconciliation
  en coroutine), `createGuards` relit les créatures chargées. Aucune attente.
- **Fils** (vidage `jcmd Thread.print` du serveur réel avant, après le 1er et après le 2e redémarrage) : `narrator2-journal`
  ×1, `narrator2-sql-N` ×2 (×3 après la fusion de M6-10, sa troisième connexion de lecture), `narrator2-forge-compiler`
  ×1, `duckdb-query-cancel-scheduler-thread` ×1, `HTTP-Dispatcher` ×1 (tableau de bord actif) à chaque fois (64 à 83 fils
  en tout) : aucun fil du Narrateur ne fuit, aucune connexion DuckDB doublée (« Journal closed »
  toujours avant « opened », dans le même fil). Le JVM sort avec le code 0 après `stop`.

   pas de clé). `/narrator restart` est refusé (`1 player online (rs_…)`), rien ne s'arrête.

   (l'invocateur de l'événement de Fabric, un vrai `ServerLoginPacketListenerImpl`) : elle reçoit une future non
   terminée, terminée une fois le redémarrage fini. Nouveau runtime `RUNNING`, l'ancien `STOPPED` et son Journal fermé ;
   défi `RUNNING`, loi et module là, décision `restarted` du module, canon actif dans la nouvelle mémoire, rappel relu,
   décision `operator restarted`.
3. Nettoyage (défi annulé, loi levée, module arrêté, rappels du monde rendus), puis un redémarrage dont la fabrique attend
   qu'un **autre processus** (`JournalChild hold` des tests unitaires, lancé par son nom de classe sur le class path du
   serveur de test) tienne le fichier du Journal : `Journal unavailable · memory off (the Journal is unavailable: opening
   failed after 3 attempts…` ; `DisabledJournal`, mémoire et mécaniques éteintes.
4. Le processus tué, `/narrator restart` : `Journal available · memory on · mechanics on · forge on`.
