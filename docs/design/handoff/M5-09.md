## Le manifeste (`Manifest.kt`)

`data class Manifest(name, mainClass, summary, params: List<ParamSpec>, scenarios, classes, bytes)`, et :

- **`Manifest.read(name, classes)`** : lit le manifeste dans les classes **compilées, avant la réécriture** (nom
  binaire → octets), avec ASM (`SKIP_CODE`) : rien n'est chargé ni exécuté (testé avec un module dont l'initialiseur
  statique et le constructeur lèvent). Lève `ForgeRejected(null, …)` (`Invalid arguments`) avec **tous** les problèmes,
  **un par ligne**, sans numéro ni préfixe : le rapport du Forgeron (M5-10, `Diagnostics`) les met en forme.
- `Manifest.nameProblem(name)` : la règle du nom (`ForgeLimits.MODULE_NAME`, ASCII) **plus les noms de périphériques
  de Windows** (`con`, `prn`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`, nouveau : le nom est aussi un dossier).
- `Manifest.mainClass(name)` (`orbiting_chickens` → `OrbitingChickens`), `Manifest.hash(source)` / `hash(bytes)`
  (`sha256:` + hexadécimal minuscule des octets UTF-8, comme `ForgeSamples.hash`).
- `manifest.entry(version, status, builtIn, savedAt, by, note, hash)` : l'`ArsenalEntry` (`sdk = Sdk.VERSION`,
  `problem = null`). C'est aussi ce que `TestReport.manifest` peut porter.
- `Manifest.encode(entry)` / `Manifest.decode(text)` : le fichier `v<k>.json`.

**Règles vérifiées** (chaque message est écrit pour le Forgeron, en anglais) :

- la classe `mainClass(name)` existe (sinon le message nomme les classes de tête trouvées), est une classe (ni interface
  ni enum : ce seul problème est dit), non abstraite, publique, implémente `ForgeModule` (elle-même ou par une classe ou
  une interface du module), et a un constructeur public sans argument ; une classe non publique ne reçoit pas en plus
  le message du constructeur (son constructeur par défaut n'est pas public) ;
- `@ModuleInfo` présent, `name` égal au nom, `summary` non vide, une ligne, ≤ `ForgeLimits.SUMMARY_CHARS` (rogné) ;
- `@Param` : 8 au plus ; nom `ForgeLimits.PARAM_NAME`, unique ; `doc` non vide, une ligne, ≤ `PARAM_DOC_CHARS` ;
  `@Param` seul ou répété (ECJ écrit `ParamList`) ; `@Param` **et** un `@ParamList` écrit à la main ensemble : refusés ;
- **bornes** : seulement pour `INTEGER`, `NUMBER`, `PLAYERS` (combien, 0 à 8), `TEXT` (longueur, 0 à 300) ; entières
  sauf pour `NUMBER` ; dans un `int` pour `INTEGER` ; `NaN` refusé ; `min ≤ max` ;
- **`choices`** : pour un `TEXT` seulement, chacun une fois, non vide, dans les bornes de longueur ;
- **`fallback`** : un paramètre requis n'en a pas ; `INTEGER`, `NUMBER`, `BOOLEAN` non requis en exigent un ; sinon il
  est lisible dans la forme texte de son type, dans ses bornes et ses choix (formes au §« M5-06 » ci-dessous) ;
- **`Scenarios`** (facultative) : classe imbriquée `public static`, concrète, constructeur public sans argument ;
  chaque méthode **publique d'instance** (ni statique, ni synthétique) doit être `void x(Bench b)` ; 8 au plus, dans
  l'ordre de la source. Les méthodes privées, de paquet ou statiques sont des aides, ignorées (les lambdas aussi).

Constantes ajoutées (absentes de `ForgeLimits`, que la tâche ne possède pas) : `Manifest.PARAM_PLAYERS = 8`,
`Manifest.PARAM_TEXT_CHARS = 300` (les « 8 au plus » et « 300 au plus » de la Javadoc de `@Param`).

## Le fichier `v<k>.json`

Celui du §6.1, clés dans cet ordre : `name`, `version`, `sdk`, `hash`, `saved_at` (ISO-8601, à la seconde), `by`,
`status` (`ready`, `pending`, `rejected`), `summary`, `params`, `scenarios`, `classes`, `bytes`, `note`. Un paramètre :
`name`, `type` (`players`…), `doc`, `required`, et seulement s'ils existent `fallback`, `min`, `max` (écrits `2.0`),
`choices`. **Absent plutôt que `null`** ; clés inconnues ignorées à la lecture ; `broken` n'est **jamais** écrit (un
fichier qui le dit est illisible), ni `builtIn`, ni `problem`. `decode` refuse un statut, un type, une empreinte, une
date ou une version (< 1) invalides.

## L'arsenal (`ArsenalStore.kt`)

```kotlin
ArsenalStore(dir /* world/narrator2/forge */, clock, builtInNames = BUILT_IN, readBuiltIn = jar, beforeMove = {})
suspend fun load()                                            // une fois ; IOException si le dossier est inutilisable
val builtInSources: Map<String, String>                        // après load
fun addBuiltIn(manifest: Manifest): ArsenalEntry               // v0, ready, built-in, Instant.EPOCH
suspend fun save(manifest, source, note, by, status): ArsenalEntry   // READY ou PENDING
suspend fun review(name, version?, approve, operator): ArsenalEntry
fun markBroken(name, version, problem): ArsenalEntry?          // en mémoire
fun noteFault(name, version, fault): ArsenalEntry?             // en mémoire
suspend fun checkedSource(name, version): String               // pour construire : empreinte vérifiée
// Arsenal : list(), entry(name, version?), source(name, version), file(name, version)
```

- **Disposition** : `world/narrator2/forge/<nom>/v<k>.java` et `v<k>.json`, comme au §6.1. Rien d'autre n'est écrit.
- **Écritures atomiques** : chaque fichier va dans un temporaire du dossier du module (`.v3.java.<aléa>.tmp`), écrit
  puis **forcé sur le disque** (`FileChannel.force`), puis déplacé en une fois (`ATOMIC_MOVE`). La source d'abord, le
  manifeste ensuite : **une version existe quand son manifeste est là**. Une panne laisse donc rien, un temporaire, ou
  une source sans manifeste (orpheline) : `load` supprime les temporaires (fichiers ordinaires à ce motif seulement),
  ignore l'orpheline (`WARN`) et ne réutilise jamais son numéro. Un échec d'écriture (exception, pas un arrêt brutal)
  supprime la source que la sauvegarde avait posée.
- **Immuabilité** : le numéro est toujours le suivant du plus grand vu sur disque (orphelines et manifestes illisibles
  compris) ; **`ATOMIC_MOVE` remplace un fichier existant sur tous les systèmes** (Windows le fait avec
  `MOVEFILE_REPLACE_EXISTING`) : `writeNew` vérifie donc l'absence de la cible juste avant (sous le verrou des
  écritures) et échoue sinon (`FAILED … FileAlreadyExistsException`), sans jamais toucher le fichier trouvé. La seule
  réécriture est le manifeste lors d'une revue (`review`), avec le même temporaire et le même déplacement : seul le
  statut change.
- **Chemins** (constat de la mission : rien de ce qu'écrit le modèle ne sort du dossier) : tout chemin part du **chemin
  réel** du dossier, d'un nom qui passe `nameProblem` (ni `.`, ni séparateur, ni `:`, ni périphérique de Windows, ASCII
  seulement) et d'un numéro entier ; une version inconnue ne mène à aucune lecture. Un dossier de module ou un fichier
  de version qui est un **lien** (symbolique, ou jonction de Windows : `isOther`, et `toRealPath` différent) n'est
  **jamais suivi** : sauté à la lecture (`WARN`), refusé à l'écriture (`FAILED`), lu `broken` pour une source. Les
  fichiers sont ouverts avec `NOFOLLOW_LINKS` et lus dans une borne (4 × 48 000 octets pour une source, 64 Kio pour un
  manifeste) : un fichier énorme déposé là n'est jamais lu en entier. Ce qui n'est pas un module (`README.txt`,
  `Tag/`, `v01.java`…) est ignoré et nommé dans un `WARN`.
- **Statuts** : celui du manifeste, sauf `broken`, calculé : source manquante, qui n'est pas un fichier ordinaire,
  trop grosse, ou dont l'empreinte ne correspond plus (`load` vérifie chaque source ; `checkedSource` revérifie avant
  une construction et marque `broken`) ; ou `markBroken` (ne compile plus, M5-10). `problem` = la cause de `broken`,
  sinon la dernière faute notée par `noteFault`. Rien de cela n'est écrit : un redémarrage recalcule.
- `entry(name, null)` : la plus haute version `ready` (jamais `pending`, `rejected` ni `broken`) ; `list()` : du plus
  récent au plus ancien (`savedAt`, puis nom, puis version décroissante), les modules de départ (`EPOCH`) en dernier.
- **Limites** : `DENIED (arsenal_full)` au-delà de 64 noms (**les modules de départ comptent**) et quand le plus grand
  numéro d'un nom atteint 20 : les versions vont de 1 à 20.
- **Fils** : `list`, `entry`, `file`, `markBroken`, `noteFault`, `addBuiltIn` sont en mémoire (tout fil, dont le
  serveur) ; toute lecture et écriture de fichier passe par `Dispatchers.IO`, les écritures une à la fois (un `Mutex`).
  Un test vérifie que les écritures ne tournent pas sur le fil de l'appelant.
- **Modules de départ** : `ArsenalStore.BUILT_IN` = les sept noms du §10, lus dans le jar
  (`/narrator2/forge/arsenal/<nom>.java`) par `load` ; un absent est un `ERROR` au log. Ils n'apparaissent dans
  `list()` qu'après `addBuiltIn(Manifest.read(…))`, puisque leur manifeste vient de leur compilation. `file(nom, 0)`
  est nul ; `source(nom, 0)` rend la source du jar même avant `addBuiltIn` (pour la compiler) ; une version forgée
  d'un nom de départ commence à 1.

## Écarts et décisions

1. **Les noms réservés de Windows** sont refusés (nouvelle règle, dans `nameProblem`).
2. **Le nombre de versions** est borné par le numéro (1 à 20), pas par un compte : plus simple, et un numéro n'est
   jamais réutilisé.
3. **Un manifeste illisible** (JSON abîmé, un autre module, un lien) n'est pas une entrée `broken` : il est sauté avec
   un `ERROR`, son numéro reste pris. Une entrée `broken` demande un manifeste lisible (résumé, paramètres).
4. **Une revue réécrit le manifeste** (statut seulement) : c'est le seul fichier qui change après coup ; la source
   jamais. L'opérateur va au log ; la décision `forge approved|rejected` est à M5-10.
5. **Les modules de départ** ne sont listés qu'une fois compilés (`addBuiltIn`) : il n'existe pas d'entrée sans
   manifeste. La liste des noms est une constante, comme `DuckDatabase.MIGRATIONS` (une ressource de jar ne se liste
   pas de façon sûre sous Knot).
6. **Règles du manifeste plus précises que le §5.2** (bornes par type, `choices` uniques, formes strictes des
   `fallback`, `Scenarios` concrète) : voir plus haut.
7. Le format du fichier : `fallback` et `choices` ajoutés aux paramètres (absents du dessin du §6.1).

## Ce que les tâches suivantes doivent savoir

### M5-10 (le service, les outils du Forgeron)

- **Démarrage** (fil du compilateur ou `Dispatchers.IO`, jamais le serveur) : `ArsenalStore(services.dataDir
  .resolve("forge"), clock)` (`dataDir` est déjà `world/narrator2`), `load()`, puis pour chaque `builtInSources`
  compiler, garder, réécrire et `addBuiltIn(Manifest.read(nom, classes))` ; un échec : `ERROR` et pas d'entrée. Pour
  les versions forgées : `load` a déjà vérifié les empreintes ; la compilation (et `markBroken(nom, v, premier
  diagnostic)` si elle échoue) est à vous, au démarrage ou à la première construction.
- **Étape 1** du §5.4 : `Manifest.nameProblem(name)` (même message que le magasin). **Étape 5** :
  `Manifest.read(name, classes)` sur les classes **non réécrites** ; ses lignes vont dans le rapport.
- **`save`** : la règle « au moins un scénario » est la vôtre (`manifest.scenarios`) ; puis `store.save(manifest,
  source, note, by, READY | PENDING selon forge.approval)`. Les refus sont déjà des `ForgeRejected` (`arsenal_full`,
  `FAILED`, `Invalid arguments`).
- **`build`** : `arsenal.entry(name, version)` (nul : inconnu ; `PENDING` → `awaiting_approval` ; `REJECTED` ; `BROKEN`
  → `FAILED` avec `entry.problem`), puis **`store.checkedSource(name, v)`** (relit et vérifie l'empreinte ; sinon
  `FAILED` et `broken`), puis la compilation. La clé du cache peut prendre `entry.hash`.
- **`review`** : `store.review(name, version, approve, operator)` ; la décision `forge` est à vous.
- `module_read` : `arsenal.source(name, version)` (version 0 : le jar) ; `module_list` : `arsenal.list()`, `problem`
  y est déjà (broken ou dernière faute).
- Le crochet `beforeMove` n'est là que pour les tests (simuler une panne entre l'écriture et le déplacement).

### M5-11 (le moteur des modules)

  régler avec M5-10/M5-21 (le plus simple : `ForgeService` expose le magasin, ou une méthode de la Forge).
- Au redémarrage, `ModuleRun.hash` peut être comparé à `entry.hash` ; `build` refuse de toute façon une source
  changée.

### M5-15 à M5-17 (l'arsenal de départ)

- Fichier `src/main/resources/narrator2/forge/arsenal/<nom>.java`, nom de fichier = nom du module, classe =
  `Manifest.mainClass(nom)`. Les sept noms sont déjà dans `ArsenalStore.BUILT_IN` : rien d'autre à toucher. Jusqu'à
  leur arrivée, un magasin réel logue un `ERROR` par module absent (le serveur n'en construit pas avant M5-21).
- `ManifestTest` montre ce que le manifeste refuse ; `Manifest.read` est le moyen rapide de vérifier un module.

### M5-06 (les paramètres d'un déploiement)

Le manifeste accepte ces formes texte de `fallback` ; `ArgsView` doit les lire (au moins) :
`INTEGER` `-?[0-9]{1,10}` (dans un `int`) ; `NUMBER` `-?[0-9]{1,15}(\.[0-9]{1,15})?` (ni exposant, ni `NaN`, ni
suffixe `d`) ; `BOOLEAN` `true`/`false` ; `PLAYER` `[A-Za-z0-9_]{1,16}` ; `PLAYERS` des noms séparés par des virgules,
**espaces autour permis** (`Bartok, Mimosa`), chacun une fois sans tenir compte de la casse ; `PLACE` `x y z` ou
`x y z dimension` (`[a-z0-9_.-]+(:[a-z0-9_./-]+)?`), ou un nom de joueur ; `TEXT` tel quel. `Manifest.PARAM_PLAYERS`
et `PARAM_TEXT_CHARS` sont les deux plafonds.
