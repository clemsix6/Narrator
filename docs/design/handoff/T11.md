# Passation T11 : moteur de conversation

Branche `worktree-agent-a72468bba26654629`. Voici l'API finale d'`AgentLoop` pour T18, T19 et T20, les écarts par rapport à `M1_M2.md` §12.7 à §12.9, §14.2 et §17.2, et ce que les tâches suivantes doivent savoir. **En cas de contradiction, le code fait foi**, et ce fichier explique pourquoi.

## Ce qui est en place

- `agent/Pending.kt` : `Pending(blocks, notes)`, ce qu'une requête ajoute après l'historique. Il n'entre dans l'historique qu'avec une réponse utilisable.
- `agent/OperatorChannel.kt` : `OperatorNote` et le rendu d'un `Pending` en messages, selon `OperatorChannelMode`.
- `agent/TurnOutcome.kt`, `agent/GatewayError.kt`, `agent/AgentLoop.kt` (avec `TurnLimits` et `TurnHooks`).
- `llm/ClaudeClient.kt` : `send(conversation, pending)` et `exchange(conversation, pending)`.
- `llm/Conversation.kt` : l'historique ne contient que ce qui a été validé ; un constructeur prend le `ToolSet`.
- `trace/Transcripts.kt` : messages `SENT`, réponses `COMMITTED` ou `NOT COMMITTED (…)`, notes `OPERATOR / ENGINE NOTE`.
- `testing/FakeAnthropic.kt` : les deux règles du §12.8, plus deux règles réelles de l'API.

## API pour T18, T19 et T20

```kotlin
class AgentLoop(services: NarratorServices, executor: ToolExecutor) {
    suspend fun runTurn(
        conversation: Conversation,          // construite avec son ToolSet
        opening: Pending,                    // non vide
        caller: Caller,                      // caller.conversationId == conversation.id
        limits: TurnLimits,
        hooks: TurnHooks = TurnHooks.NONE,
        purpose: LlmCallRecord.Purpose = if (caller.taskId != null) WORKER else TURN,
    ): TurnOutcome
    fun channelMode(configured: OperatorChannelMode): OperatorChannelMode   // USER_TAG après un repli
}

data class TurnLimits(val maxSteps: Int, val hardSteps: Int = maxSteps + 2)

interface TurnHooks {
    suspend fun afterTools(): Pending = Pending.EMPTY                        // avant chaque requête de suite
    fun onReply(reply: Message, stats: CallStats, llmCallId: Long) {}        // après chaque réponse, utilisable ou non
}

sealed interface TurnOutcome {          // tous : calls, toolCalls, acted
    Ended(finalText)                    // fin normale ; tout est validé
    Refused(pending, category)          // stop_reason refusal
    Truncated(pending, reason)          // max_tokens, appel d'outil coupé
    Empty(pending)                      // deux réponses vides de suite (voir plus bas)
    Failed(pending, error: GatewayError, requestId)
    StepLimit(carry)                    // limite dure : carry = tool_result à renvoyer en tête
    Cancelled                           // coroutine annulée
}

data class Pending(val blocks: List<ContentBlockParam>, val notes: List<OperatorNote> = emptyList()) {
    val isEmpty: Boolean
    operator fun plus(other: Pending): Pending; operator fun plus(note: OperatorNote): Pending
    companion object { val EMPTY; fun text(text: String, notes: List<OperatorNote> = emptyList()) }
}
data class OperatorNote(val source: String, val text: String) {   // source = "engine" | "operator:<nom>"
    companion object { fun engine(text); fun operator(name, text) }
}
```

### Exemple (Directeur)

```kotlin
val loop = AgentLoop(services, ToolRunner(services))  // une instance pour toute la vie du Directeur
val chapter = Conversation(
    Role.DIRECTOR, "Chapter 13", listOf(TextBlockParam.builder().text(prompt).build()),
    tools = ToolCatalog.toolSetFor(Role.DIRECTOR, env, services), transcripts = services.transcripts,
)
val opening = Pending(
    blocks = carried + ContentBlockParam.ofText(briefing + wakeMessage),   // carried : tool_result d'un échec précédent, en tête
    notes = listOfNotNull(whisper?.let { OperatorNote.operator(it.from, it.text) }),
)
val hooks = object : TurnHooks {
    override suspend fun afterTools(): Pending {
        val events = inbox.takeInjectable()            // IMMEDIATE, SOON, NEXT arrivés depuis la requête précédente
        return if (events.isEmpty()) Pending.EMPTY else Pending.text(formatter.newEvents(events), whispersOf(events))
    }
    override fun onReply(reply: Message, stats: CallStats, llmCallId: Long) { lastContextTokens = stats.contextTokens }
}
val caller = Caller(Role.DIRECTOR, chapter.id, turnId, taskId = null)
when (val outcome = loop.runTurn(chapter, opening, caller, TurnLimits(config.director.maxStepsPerTurn), hooks)) {
    is TurnOutcome.Ended -> finishTurn(if (outcome.acted) ACTED else IDLE)
    is TurnOutcome.Refused -> retryLater(outcome.pending + OperatorNote.engine("Your previous reply … (category ${outcome.category})."))
    is TurnOutcome.Failed -> when (outcome.error) { is GatewayError.Transient -> backoff(outcome.pending) /* … */ }
    // …
}
```

`AgentLoop` n'écrit que les lignes `llm_calls`, la décision `operator` du repli et des notes dans la transcription. Les lignes `turns`, les décisions `refusal`, `backoff`, `budget` et `chapter`, et l'indicateur « réfléchit » restent à T18 et T19. Les lignes `tool_calls` sont écrites par `ToolRunner` (T08).

## Garanties

- **L'historique n'est jamais modifié** et ne contient que des échanges validés : chaque requête (le `Pending` rendu) est validée avec sa réponse, et seulement si celle-ci est utilisable. Un refus, une troncature, une réponse vide, une erreur ou une annulation ne valident rien.
- **Un `Pending` non validé** est rendu par `Refused`, `Truncated`, `Empty` et `Failed`. S'il contient des `tool_result`, l'historique se termine par les appels d'outils auxquels ils répondent : **la requête suivante sur cette conversation doit commencer par eux**. Il suffit de renvoyer ce `Pending` (avec `plus` pour ajouter des événements ou une note) au prochain `runTurn`, même bien plus tard, même après un redémarrage de tour. `StepLimit.carry` suit la même règle.
- **Aucun tour assistant vide.** Une réponse sans aucun bloc (ou avec seulement du texte vide), fréquente juste après des `tool_result`, n'est jamais validée : `AgentLoop` renvoie une fois la même requête avec la note moteur `EMPTY_REPLY_NOTE`. Une seconde réponse vide donne `TurnOutcome.Empty`. Les blocs de texte vides sont retirés d'une réponse validée (l'API les refuse).
- **Une réponse qui ne contient que de la réflexion est validée** : `liveTest` a vérifié le 25/09/2026 qu'un tour assistant fait d'un seul bloc `thinking` est accepté dans l'historique.
- **`tool_result` toujours en tête** du message `user`, un par appel et dans l'ordre, quoi que fasse l'exécuteur : s'il lève une exception, ou s'il perd ou désordonne des résultats, les manquants deviennent `FAILED: the engine could not run this tool call` (log `ERROR`).
- **Chaque réponse et chaque appel en échec** donnent une ligne `llm_calls` (`LlmCallRecord.anthropic`), avec le résumé de réflexion tronqué à 4 000 caractères, `turn_id = caller.turnId`, `http_status` 200 pour une réponse et le code d'erreur sinon. Une écriture de trace qui échoue est loguée et ne casse pas le tour.

## Écarts par rapport au design

1. **`ClaudeClient`** :
   - `send(conversation, pending = emptyList())` n'a pas de paramètre `purpose` : le but va dans `llm_calls`, écrit par `AgentLoop`.
   - `exchange(conversation, pending): Exchange` est ajouté. Il renvoie `Exchange.Failed(error, stats)` au lieu de lever l'exception, car les lignes `llm_calls` des appels en échec ont besoin de leurs mesures. `send` lève toujours les mêmes exceptions qu'en M0 : le `ping` et les tests M0 n'ont pas changé.
   - `ClaudeClient.EMPTY_REPLY` et `isEmptyReply(message)` sont publics.
2. **`Conversation`** a deux constructeurs publics :
   - `Conversation(role, label, system, tools: ToolSet, transcripts, id)` pour le moteur, avec `toolSet` non nul ;
   - `Conversation(role, label, system, tools: List<ToolUnion>, …)` pour déclarer des outils sans les exécuter (le ping, `liveTest`). `AgentLoop` refuse une telle conversation.
   - `append` reste disponible pour préparer une conversation hors du moteur (ping, tests). Le moteur, lui, n'ajoute jamais rien directement : il passe par les messages en attente.
3. **`TurnOutcome`** :
   - `acted` est présent sur toutes les issues : un tour peut avoir parlé avant un refus ;
   - `Truncated` porte `reason` et `Failed` porte `requestId` (l'identifiant à donner à l'opérateur, `X-Cpa-Trace-Id` derrière LLMGW) ;
   - `Empty` est nouveau (voir « Garanties »). T18 peut le traiter comme `Truncated`, avec une note adaptée, et T20 comme un échec (`failed: empty reply`).
4. **`GatewayError`** :
   - `Budget.resetAt` est nullable : le corps du 402 peut ne pas le donner. Le Directeur choisit alors lui-même un délai ;
   - `Unavailable(reason)` est ajouté : pas de clé, ou un client fermé et jamais remplacé (serveur qui s'arrête). À traiter comme `Auth` : bloqué jusqu'au prochain `SettingsChanged` ;
   - `description` donne une ligne pour les logs et les opérateurs ;
   - `Transient.kind` vaut `rate_limited`, `overloaded`, `server_error`, `timeout`, `network`, `stream` ou `unexpected`. Tout ce qui n'est pas prévu est classé `unexpected`, pour que le moteur survive à une réponse illisible ;
   - `ContextExceeded` couvre `stop_reason: model_context_window_exceeded` et une 400 « prompt is too long ».
5. **`TurnHooks.afterTools` est `suspend`**, pour laisser T18 lire sa boîte. `onReply` est appelé pour chaque réponse, y compris refusée ou incomplète.
6. **Limites d'étapes**, telles que codées : les outils des réponses aux requêtes 1 à `maxSteps - 1` s'exécutent. À partir de la réponse à la requête `maxSteps`, les appels d'outils reçoivent `is_error` `STEP_LIMIT_RESULT` et une note moteur `STEP_LIMIT_NOTE`. Si la réponse à la requête `hardSteps` appelle encore un outil, c'est `StepLimit`, avec les `tool_result` refusés dans `carry`. Avec 12 étapes, la requête 13 porte les premiers refus et la réponse à la requête 14 arrête le tour. C'est la lecture de S9 et de `maxStepsPerTurn` (« Model requests per turn before its tool calls are refused »).
7. **Canal opérateur** :
   - le mode est lu dans `director.operatorChannel` au début de chaque tour, et non figé par chapitre : T18 et T19 closent le chapitre au moment calme quand le mode change (§2.3), et les deux formes restent valides dans un même historique ;
   - le repli sur `USER_TAG` (400 sur le rôle `system`) vaut **pour la vie de l'instance d'`AgentLoop`**. Si le Directeur et les assistants ont chacun leur instance, chacun découvre le rejet une fois (une requête perdue) ;
   - le renvoi n'a lieu qu'une fois par requête, et seulement si la requête contenait un message `system`. Une seconde 400 donne `Failed(SystemRoleRejected)` : c'est le cas si l'historique déjà validé contient des messages `system` que la passerelle refuse désormais. Il faut alors clore le chapitre, comme pour `BadRequest` ;
   - des notes sans aucun bloc sont toujours rendues en balises dans un message `user`, car un message `system` doit suivre un message `user` ;
   - chaque note est sur sa propre ligne (`Operator Clement: …` ou `Engine: …`). Une note sur plusieurs lignes, comme `chapter_summary`, est gardée intacte. Le nom de l'opérateur est échappé dans l'attribut `from`.
8. **`Cancelled`** est rendu comme une valeur, mais la coroutine reste annulée : sa prochaine suspension lève l'exception, et `withTimeout` lève toujours son `TimeoutCancellationException`. Une annulation pendant les outils laisse l'historique finir sur des appels sans réponse : cette conversation ne doit plus servir (fin de chapitre `shutdown`, tâche annulée).
9. **`ClientClosedException`** (client remplacé par `/narrator reload` entre la lecture des réglages et l'envoi) : `AgentLoop` relit les réglages et renvoie, jusqu'à deux fois. Rien n'était parti, donc rien n'est compté.
10. **Transcriptions** (§14.2) :
    - JSONL : un nouveau type `sent` par message en attente, et dans `response`, `narrator2_appended` (validé ou non) plus `narrator2_not_committed` (la raison) ;
    - Markdown : `SENT`, `OPERATOR / ENGINE NOTE` (au lieu de `SYSTEM INSTRUCTION`), `CLAUDE — … — COMMITTED` ou `NOT COMMITTED (refusal | <raison de l'incomplet> | error | cancelled)` ;
    - l'historique réel se reconstruit à partir des lignes `message`, puis, pour chaque réponse validée, des lignes `sent` de sa requête et de la réponse.
11. **`FakeAnthropic` strict** :
    - l'ajout seul se vérifie désormais par rapport au **dernier échange réussi** de la session : la requête doit commencer par ses messages, **suivis de la réponse servie, inchangée** (comparée sur le texte, la réflexion et sa signature, l'id, le nom et les arguments des appels d'outils, sans les textes vides). Le prompt système et les outils sont comparés à la première requête de la session ;
    - un message `system` doit suivre un message `user` et être le dernier ou suivi d'un tour `assistant` ;
    - deux règles réelles de l'API sont ajoutées : un `tool_result` ne peut pas venir après un autre bloc de son message, et un texte fait seulement d'espaces est refusé ;
    - l'échange réussi est enregistré juste avant `message_stop`, puis oublié si le client n'a pas pu le lire (annulation) : la requête suivante ne peut donc pas le devancer.

## Pour chaque tâche

- **T18** :
  - Une seule instance d'`AgentLoop` pour la vie du Directeur, construite avec `ToolRunner`.
  - Le message de réveil est un `Pending` : les `tool_result` d'un échec précédent d'abord, puis le texte.
  - Les événements injectés et les consignes arrivées en cours de tour passent par `afterTools()`. `AgentLoop` les place après les `tool_result`.
  - Refus en cours de tour : renvoyer `outcome.pending + OperatorNote.engine(...)`, ce qui fait un nouveau `runTurn`.
  - `Failed(Transient)` : garder `outcome.pending` et le reconstruire au réveil suivant, en gardant ses `tool_result` en tête (`Pending(old.blocks.filter { it.isToolResult() } + nouveaux événements, notes)`).
  - `Failed(BadRequest)` : donner `outcome.requestId` dans le log `ERROR`.
  - `S12` : un tour annulé rend `Cancelled`. Écris la ligne `turns` dans le `finally`, comme prévu.
- **T19** :
  - Clôture après `StepLimit` : `Pending(outcome.carry, listOf(OperatorNote.engine(prompts.get("chapter_summary"))))`, avec `purpose = CHAPTER_SUMMARY`.
  - Pour « tools are disabled while the chapter closes », le plus simple est une seconde instance d'`AgentLoop` dont l'exécuteur répond cette erreur à tout appel, avec `TurnLimits(maxSteps = 3)`.
  - Les appels d'outils de la réponse à la requête `maxSteps` reçoivent alors le texte de limite d'étapes, et non le tien.
- **T20** :
  - `purpose` vaut `WORKER` par défaut dès que `caller.taskId` est posé.
  - `withTimeout(workers.timeoutSeconds)` autour de `runTurn` donne `Cancelled` à l'intérieur, et la `TimeoutCancellationException` à l'extérieur.
  - `Ended.finalText` est le rapport (vide possible : considère-le comme un échec).
  - `Failed(Budget)` donne `failed: budget`.
- **T22** : le sondage de T11 (non commité, voir « Vérifications ») a déjà couvert contre le vrai serveur les points 1 et 2 du §17.4 : un `tool_result` suivi d'un texte dans le même message `user`, et un message `system` placé après les `tool_result`. Ils restent à écrire dans `liveTest`.
