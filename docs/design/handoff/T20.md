## Comment ça tourne

1. **`delegate`** appelle `workers.submit(role, brief, caller)`, qui rend l'identifiant **tout de suite** : une ligne `tasks` `queued`, puis `running` si une place est libre (`workers.maxConcurrent`, lu à chaque démarrage). L'outil ne suspend jamais : le tour du Directeur continue (S11 le prouve : le Directeur envoie sa requête suivante et finit son tour pendant que la première réponse de l'Analyste est retenue par le faux serveur).
2. **Démarrage** : l'identifiant de conversation (`analyst-<8 hex>`, qui est aussi l'`X-Session-ID`) est tiré au passage en `running` et écrit dans la ligne `tasks`. La tâche tourne dans sa coroutine de `services.scope` (`narrator2-task-<id>`), lancée `LAZY` sous le verrou puis démarrée hors du verrou ; un `invokeOnCompletion` fait le bilan, **une seule fois, même pour une coroutine annulée avant d'avoir démarré**.
3. **Conversation** : `Conversation(analyst, "Task T-12 (analyst)", [prompt analyst.md], ToolCatalog.toolSetFor(analyst, ToolEnv(journal ouvert, workerRoles = ∅)), transcripts, id)`, ligne `conversations` (`task_id`, `transcript`), note dans la transcription. Tour unique d'`AgentLoop` (une instance pour tous les assistants, avec son propre `ToolRunner`), `TurnLimits(workers.maxSteps)`, dans `withTimeoutOrNull(workers.timeoutSeconds)`.
4. **Fin** : `tasks` (`done` + `result`, ou `failed`/`timeout`/`cancelled` + `error`), `conversations` (fin, raison, `summary` = rapport), note de fin, fermeture de la transcription, `DirectorSignal.TaskDone` (voir plus bas), puis démarrage de la tâche suivante de la file.

### Premier message d'une tâche

```
<task id="T-1" from="director">
Where does Bartok mine these days? Coordinates please.
</task>
<context now="2026-09-25 21:32:00" players_online="Bartok"/>
```

`now` est au format `yyyy-MM-dd HH:mm:ss`, **dans le fuseau du Journal** (`journal.timeZone`, sinon celui de l'horloge du moteur, qui est aussi le défaut de DuckDB) : c'est l'heure que donnent les en-têtes des résultats de `sql`. `players_online="none"` sans joueur. Le brief est recopié tel quel : il vient du Directeur, et le texte des joueurs qu'il cite a déjà ses chevrons remplacés par `‹ ›` (T18).

### Sorties des outils

`delegate` (`role`: `analyst` ; `brief` : 20 à 2 000 caractères) :
```
ok: task T-1 analyst started; its report will arrive as a TASK event
ok: task T-3 analyst queued (the workers are busy: it starts when a running task ends); its report will arrive as a TASK event
FAILED: the server is stopping: no task can start
Invalid arguments: brief is too short (at least 20 characters): say what to find out, about whom, over which period
```

`tasks` (`action`: `list` | `cancel` ; `task_id` requis pour `cancel`) :
```
tasks: 1 running, 1 queued, 4 ended in the last 30 minutes
T-10 analyst done 9m19s ago, in 41s: "Réponse : Bartok mine vers -1400 -40 3100. Faits : - 72 % de ses minerais [R1]."
T-11 analyst failed 4m57s ago, in 3s: "budget: the LLMGW budget is spent until 22:00"
T-12 analyst timed out 3m20s ago, in 3m
T-13 analyst cancelled 1m30s ago
T-14 analyst running for 12s: "Where does Bartok mine these days? Coordinates and ores, over the last three days."
T-15 analyst queued for 3s: "Where does Bartok mine these days? Coordinates and ores, over the last three days."
```
```
no task running, queued or ended in the last 30 minutes
ok: task T-1 cancelled; its report will never come
ok: task T-2 cancelled before it started; its report will never come
Invalid arguments: task T-2 already ended (cancelled)
Invalid arguments: no task T-9; tasks: T-3 running, T-4 queued
Invalid arguments: task_id is required to cancel a task
```
Les extraits (brief ou début du rapport) sont cités comme le chat (`EventFormatter.quote`), 160 caractères au plus.

### Ce qui revient au Directeur

`TaskDone(taskId, role, status, result, at = fin)` ; `result` est le rapport pour `done`, la raison sinon. T18 le rend `TASK T-1 analyst done in 18s:` suivi du rapport indenté (ou cité sur une ligne s'il est court). Raisons d'échec, telles qu'écrites dans `tasks.error` et dans `TaskDone.result` :

| Cas | Statut | Raison |
|---|---|---|
| 402 | `failed` | `budget: the LLMGW budget is spent until 22:00` (heure de l'horloge du moteur ; sans `reset_at` : `budget: the LLMGW budget is spent`) |
| refus | `failed` | `refused by the safety filter (category cyber)` |
| `max_tokens`, appel coupé | `failed` | `reply cut off: <raison d'AgentLoop>` |
| deux réponses vides (`TurnOutcome.Empty`) | `failed` | `empty replies: no report` |
| fin sans texte (réflexion seule) | `failed` | `empty report: the last reply had no text` |
| limite dure d'étapes | `failed` | `step limit: still calling tools after 17 requests, no report` (15 étapes : 17 requêtes, règle de T11) |
| autre erreur de la passerelle, pas de clé | `failed` | `GatewayError.description` (`LLMGW key refused (HTTP 401/403)`, `overloaded: …`, `no LLMGW client: the key is missing`…) |
| exception du moteur | `failed` | `engine error: <message>` (log `ERROR` avec la pile) |
| délai | `timeout` | `no report within 180 s` |

Le rapport est coupé à 3 000 caractères (`Workers.RESULT_MAX_CHARS`, 2 999 + `…`).

## Écarts par rapport au design

1. **Pas de `TaskDone` pour une tâche annulée par le Directeur**, ni pour une tâche arrêtée par l'arrêt du serveur. Le §13 prévoyait `TASK T-12 analyst failed: <raison>` aussi pour l'annulation ; mais le Directeur vient de l'annuler lui-même et le résultat de `tasks` le lui a dit : poster un `TaskDone` le réveillerait 3 s plus tard (un appel à Opus) pour rien. Pendant l'arrêt, le Directeur ne reçoit plus rien de toute façon (`post` ignoré en `STOPPING`). Les délais et les échecs, eux, sont postés.
2. **Annulation immédiate dans les traces** : `cancel` passe la ligne `tasks` à `cancelled` (et `list()` aussi) tout de suite, puis annule la coroutine ; son flux est fermé et rien n'est validé. **Sa place n'est libérée qu'à la fin de la coroutine** (quelques millisecondes), pour ne jamais dépasser `maxConcurrent`. Une tâche en file sort de la file sans jamais appeler Claude.
3. **Arrêt du serveur** : la tâche en cours finit `cancelled` avec `the server stopped` et sa conversation `shutdown` ; celles de la file finissent `cancelled` avec `the server stopped before it started`. Au redémarrage, `Repair` (T03) ne trouve donc rien à réparer, sauf après un crash.
4. **`roles` dépend du Journal et de la phase** : l'Analyste n'est proposé (`roles = {analyst}`, donc `delegate` et `tasks` visibles) que si le Journal est ouvert et la phase `RUNNING` (§2.2 point 2 : « `delegate` vers l'Analyste n'est pas proposé » sans Journal). `submit` le vérifie aussi : `no analyst can take a task: the Journal is unavailable`, `no scout can take a task: there is no scout yet`.
5. **Résultat de `delegate`** : `ok: task T-12 analyst started|queued (…); its report will arrive as a TASK event` au lieu de `task T-12 queued (analyst); …` : le verdict `ok:` comme les autres outils d'action, et le Directeur sait si la tâche a démarré ou attend.
6. **`tasks` a l'effet `TASK`**, comme tout le §9.6 : un `tasks list` réussi compte donc comme une action (`acted`, `Your last actions`, `/narrator why`). C'est rare (la situation montre déjà les tâches en cours) ; un `READ` aurait caché les annulations. À revoir si le bruit gêne.
7. **Traces d'une tâche** : `Caller(analyst, conversationId, turnId = null, taskId)`. Les lignes `llm_calls` (`purpose = worker`) et `tool_calls` d'une tâche ont donc `turn_id` nul ; on les rattache par `conversation_id` → `conversations.task_id`, et au tour du Directeur par `tasks.requested_by_turn`. C'est ce que lit `/narrator trace task` (T21).
8. **Délai** : il couvre le tour de l'Analyste seulement, pas l'attente dans la file ni la construction des outils (`SchemaDoc` : ≈ 100 ms la première fois).
9. **Pas de mémoire du budget entre tâches** : après un 402, les autres tâches en cours échouent à leur propre appel suivant (un 402 ne coûte rien), et celles de la file démarrent puis échouent de même. Le Directeur, lui, se bloque sur son propre 402 (T18).
10. **Pas de plafond sur la longueur de la file** : le design n'en prévoit pas ; le nombre d'étapes par tour du Directeur borne déjà les délégations.
11. **Une instance d'`AgentLoop` pour les assistants**, distincte de celle du Directeur : si la passerelle refusait un jour les messages `system`, chacun découvrirait le refus une fois (écart 7 de T11).
12. **`live/LiveAnalystTest.kt`** est un nouveau fichier de test réel (tag `live`, hors de `build`). Il n'était pas listé dans le design (T22 possède les ajouts de `liveTest` du §17.4) ; il ne touche aucun fichier existant et teste le code de T20.
