## Écarts par rapport au design et décisions

### Écriture : lire sur le pool, écrire en quelques millisecondes

1. **Pas d'`INSERT OR REPLACE … SELECT` sur le rédacteur.** Le §6.1 calculait chaque famille dans le travail d'écriture. Mesuré sur un Journal de 500 heures de jeu (3 millions d'événements, 300 000 positions, 10 joueurs), cela tenait le rédacteur **1,4 s par joueur**, et les paires **37 à 50 s**. Désormais tout est **lu sur le pool SQL** (`journal.read`), puis écrit dans un travail court :

   | Étape | Où | Durée mesurée (machine chargée) |
   |---|---|---|
   | paires (`PairStats.compute`) | lecture | 200 à 330 ms |
   | taux du serveur (`Rates.read`, une fois par recalcul) | lecture | 0,6 s |
   | stats d'un joueur (`SheetStats.compute`) | lecture | 0,5 à 0,7 s |
   | écriture des 16 stats d'un joueur, ou des paires | `Journal.write` | 25 à 100 ms |

   Chaque requête de stats a `setQueryTimeout(30)` (`SheetStats.QUERY_TIMEOUT_SECONDS`).
2. **Valeurs liées par des littéraux, pas par des paramètres ni par une CTE d'une ligne.** Les requêtes écrivent `{player}` et `{now}`, que `SheetStats.bind` remplace par `CAST('<uuid>' AS UUID)` et `CAST('<instant>' AS TIMESTAMPTZ)`. Une CTE `p` croisée dans la requête des paires faisait passer la jointure `ASOF` de 30 ms à 11 s (vérifié, même avec `MATERIALIZED`). Les deux valeurs sont typées (`UUID`, `Instant`), jamais du texte d'un joueur.
3. **Une seule requête par joueur** : les événements (`e`) et positions (`q`) du joueur sont lus une fois (`AS MATERIALIZED`), puis une branche `UNION ALL` par stat.
4. **Pas de `executeBatch` JDBC dans un travail** : le pilote DuckDB ouvre alors sa propre transaction, et le travail échoue (« cannot start a transaction within a transaction »). Une ligne à la fois (`executeUpdate`). À savoir pour toute tâche qui écrit plusieurs lignes dans `Journal.write`.

### Stats de la fiche (§6.1)

5. **Lues par UUID dans `events`**, pas dans les vues par nom de T04 (un joueur renommé garderait ses stats sous l'ancien nom). Jusqu'à `now` inclus.
6. **`detail`** : horodatages en ISO-8601 UTC (`2026-09-25T18:20:00Z`), identifiants sans `minecraft:`. Toutes les stats sont écrites pour tout joueur connu, même vides (`0`, listes vides, `null`).
7. Précisions par stat :
   - `playtime` : `usual_hours` = les 3 heures du jour (fuseau du Journal) les plus jouées, en secondes de jeu, triées ;
   - `deaths.absurd` : `fall`, `lava`, `drown`, `in_wall` (suffocation), `cactus`, `sweet_berry_bush` ;
   - `pvp.last` = `{ts, opponent, won}` (dernier combat gagné ou perdu) ; une mort « par un joueur » = tueur sans `:` (un nom de joueur n'en a jamais, un type d'entité toujours) ;
   - `mining` : sans le mode créatif ; `ores.gold` compte aussi le minerai d'or du Nether ;
   - `travel` : somme des `custom:*_one_cm` en mètres **sans les chutes** (`fall_one_cm`) ; `aviate` est rendu `elytra` ; le détail omet ce qui fait moins d'un mètre ;
   - `exploration` : biomes vus par `biome_enter` **et** par les positions échantillonnées ; `rare_biomes` parmi une liste fixe (`SheetStats.RARE_BIOMES`) ; `nether_at`, `end_at` = première arrivée ou première position dans la dimension ;
   - `gear` : cuir et bois 1 ; pierre, or, cotte de mailles et cuivre 2 ; fer 3 ; diamant 4 ; netherite 5. Arme = épée ou hache ; objets fabriqués ou ramassés ;
   - `economy.emeralds_spent` : émeraudes des deux paiements ;
   - `places` : `base` = case de 32 blocs où il pose le plus, `mine` = case où il casse le plus de minerais (x, z au centre, y moyen), `bed` = lit le plus utilisé ; `value` nulle ;
   - `narrator` : `value` = prières **plus** messages publics avec `to_narrator ≥ 0,6` ; défis gagnés = `won` avec le joueur dans `winners` ; perdus = défis clos où il est dans `players` sans être gagnant.
8. **Indice de chance** : comme le §6.1. La population est l'ensemble des joueurs d'au moins 5 h de jeu qui ont une valeur pour la composante ; `z = 0` sous 3 joueurs, pour un joueur de moins de 5 h, sans valeur (rien miné, rien pêché, aucun défi clos) ou si l'écart interquartile est nul. Quantiles interpolés comme `quantile_cont`. `detail` = les valeurs brutes du joueur : `rare_per_1k_mined` (minerais de diamant, d'émeraude et débris antiques pour 1 000 blocs), `treasure_fish` (part des objets de trésor pêchés : arc, livre enchanté, canne, étiquette, coquille de nautile, selle), `challenges_ratio`, `absurd_deaths_per_h` ; `null` quand la composante n'a pas de valeur.
9. **Style** : mesures par heure de jeu — explorateur : premières visites de biomes et de structures, mètres ; combattant : kills, dégâts infligés ; bâtisseur : blocs posés ; mineur : blocs cassés sous y = 50 hors de l'End ; fermier : récoltes cassées (`SheetStats.CROPS`), reproductions, apprivoisements ; social : messages publics, minutes avec un autre joueur (`pair_stats`, d'où les paires calculées d'abord). Chaque mesure est divisée par la médiane du serveur (joueurs d'au moins 1 h), **par la moyenne quand la médiane est nulle** (sinon le seul fermier de trois joueurs n'aurait aucune part de fermier) ; une mesure nulle pour tous est ignorée ; une activité = la moyenne de ses mesures ; puis ramené à 100 % (entiers arrondis : la somme vaut 99 à 101). **Style nul sous 1 h de jeu** ou pour un joueur qui n'a rien fait.
10. **`signals`** (§6.3) : `value` = nombre de verdicts Jev (`source` commençant par `jev:`) ; les lignes de l'heuristique sont ignorées ; `detail` nul sous 30, sinon `{politeness: {mean, ewma, n}, …}` arrondis à 3 décimales, `ewma` à demi-vie de 100 messages (le plus récent pèse 1).

### Faveur, respect, attention (§6.2)

11. **Faveur** : formule exacte du §6.2 ; `null` sans interaction qui compte. **Tendance** : faveur maintenant moins faveur 5 h de jeu plus tôt, avec les seules interactions connues alors (aucune → 0, l'a priori neutre) ; flèche au-delà de ±5. L'horloge du joueur est lue en SQL (sessions closes + session en cours), comme `DuckPlayClock`.
12. **Respect** : la confiance ≥ 0,6 vaut **pour les deux pôles** (un « respectful » de l'heuristique à 0,4, son ton par défaut, est neutre). Les tons de l'heuristique comptent : seuls les signaux de personnalité sont réservés à Jev. Les interactions `disrespect` non archivées comptent comme deux messages irrespectueux, à leur heure. `null` sous 5 messages adressés (les interactions ne comptent pas dans ces 5).
13. **Attention** : dernière interaction non archivée **ou** dernier appel d'outil `ok` d'effet `speech`/`world` dont `targets` contient **un des noms** que le joueur a portés ; dette = temps de jeu du joueur depuis ; **jamais d'attention → tout son temps de jeu** (`lastAttentionAt = null`).
14. **Lignes de situation** (`Favor.situationLines(readings, attentionMinutes)`) : `Favor: Bartok -5 ↘ · Mimosa +16 ↗` (joueurs qui ont une faveur, dans l'ordre donné) et `Attention: Kelvin has had nothing from you for 50m of play · Mimosa for 30m` (au-delà du seuil, la plus longue d'abord) ; durées par `ToolText.duration` ; noms échappés. Une ligne sans personne est omise.

### Tics, réactions, paires (§6.4, §6.7)

15. **Tics** : 200 dernières répliques du canal `narrator` (pas `operator`). Mots = lettres et chiffres avec leurs élisions (`t'es` est un mot). Amorces : trois premiers mots, 4 répliques au moins. Phrases : 3 à 5 mots qui **ne commencent ni ne finissent** par un mot vide (liste courte dans `Tics`, celle de `FrenchAnalyzer` est privée et sans accents), dans 3 répliques distinctes ; une phrase contenue dans une plus longue vue aussi souvent est retirée ; une phrase identique à une amorce aussi. Points de suspension (`…` ou `...` en fin de phrase) dans plus de 40 % des répliques. Forme montrée = la dernière écrite. Rendu : `« Ministère de la » ×7 (last 2h01m ago)`, `« … » ×3 (60% of lines, last 2h00m ago)`.
16. **Réactions** : une réplique du canal `narrator` vise ses destinataires (réplique privée), sinon les joueurs **qu'elle nomme** (mot entier, sans casse, tous les noms portés). Une réplique adressée à tous sans nom n'a pas de réaction. Ordre : `laughed` (humour Jev ≥ 0,6 ou mot de la section `[laughter]` de l'heuristique) > `annoyed` (ton `hostile`/`disrespectful` de confiance ≥ 0,6) > `replied` > `ignored` (en ligne, silencieux) ; hors ligne : rien. Messages publics et prières du joueur dans les 120 s.
17. **Paires** : chaque minute en ligne d'un joueur prend sa **dernière position échantillonnée à la fin de cette minute dans la même session** (T05 échantillonne au mouvement et au moins toutes les 5 min) ; une minute ensemble = même dimension, distance 3D ≤ 32. Une paire a une ligne dès qu'ils se sont croisés, battus ou « griefés ». `a_uuid < b_uuid` dans l'ordre de DuckDB (ordre du texte de l'UUID, pas celui de `java.util.UUID.compareTo`). Les kills PvP retrouvent la victime par `player_names`.

## Formules pour M3-08 (vues `mem_favor`, `mem_stats`)

Ces vues sont à M3-08. La formule de la faveur ci-dessous est **testée** (`FavorTest` › `the SQL formula given to the mem_favor view gives the same favor` : même valeur que `Favor.read` à 10⁻⁹ près) ; elle y prend l'instant en paramètre, une vue mettra `now()`. Copier aussi le test dans `SqlViewsTest`.

```sql
-- Horloge de chaque joueur : sessions closes + session en cours, en secondes.
WITH clock AS (
    SELECT pl.player_uuid, pl.name, pl.playtime_s + coalesce((SELECT sum(epoch(now() - s.joined_at)) FROM sessions s
        WHERE s.player_uuid = pl.player_uuid AND s.left_at IS NULL), 0) AS played_s
    FROM players pl),
-- Poids d'une interaction qui compte : 0,7 · 2^(−âge/10 h) + 0,3 · 2^(−âge/100 h), âge en temps de jeu du joueur.
w AS (
    SELECT i.player_uuid, i.valence, i.played_s AS at_s, c.played_s,
           0.7 * pow(2, -(c.played_s - i.played_s) / 3600.0 / 10) + 0.3 * pow(2, -(c.played_s - i.played_s) / 3600.0 / 100) AS w
    FROM interactions i JOIN clock c USING (player_uuid)
    WHERE i.counts AND NOT i.archived AND i.played_s <= c.played_s)
SELECT player_uuid, 100 * sum(valence * w) / (3 * (sum(w) + 3)) AS favor FROM w GROUP BY 1
```

- **Tendance** (si la vue la donne) : la même faveur calculée à `played_s − 18000` (5 h de jeu), avec les seules interactions `at_s <= played_s − 18000` et l'âge `played_s − 18000 − at_s` ; 0 sans interaction alors. `trend = favor − favor_5h`, flèche au-delà de ±5.
- Faveur **nulle** (pas de ligne) pour un joueur sans interaction qui compte, comme `Favor.read`.
- Le respect (moyenne mobile sur les messages, interactions comptées double) et l'attention restent dans `Favor.kt` : trop longs pour une vue lisible, et le modèle les lit dans la fiche.
- `mem_stats` : `SELECT p.name AS player, s.stat, s.value, s.detail, s.computed_at FROM sheet_stats s JOIN players p USING (player_uuid)`. Le `detail` est documenté dans la KDoc de `SheetStats` (tableau) et ci-dessus ; le rappeler en une ligne dans le commentaire de la vue (budget de `SchemaDoc`).
