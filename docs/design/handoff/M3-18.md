# Passation M3-18 : assemblage de la mémoire

Tâche M3-18 de `design/M3.md` (§1.1, §17, §19.2). Le serveur tourne maintenant avec la **vraie mémoire** : `createMemory` construit toutes les pièces de M3-02 à M3-17, démarre l'ordonnanceur et rend un `MemoryService`. `DisabledMemory` ne sert plus que quand la mémoire est coupée, sans Journal, sans son schéma, ou quand elle n'a pas pu démarrer. **En cas de contradiction avec `M3.md` ou une passation antérieure, le code et cette passation font foi.**

## Schéma d'assemblage

`NarratorRuntime.wire`, sur le thread serveur, à `SERVER_STARTED` : Journal, bus, joueurs, gardes, Observateur, réflexes, workers, **mémoire**, Directeur. La mémoire existe donc avant le Directeur, comme M3-01 l'avait prévu : rien n'a changé dans l'ordre.

```
createMemory(services)
 ├─ memory.enabled faux ............................ DisabledMemory("memory.enabled is false")      (INFO)
 ├─ Journal indisponible ........................... DisabledMemory("the Journal is unavailable: …") (WARN)
 ├─ schéma : version ≥ 2 et les 17 tables de V2 .... sinon DisabledMemory("the Journal lacks the memory's schema (V2__memory.sql): …")
 └─ assemble
     zone  = journal.timeZone, sinon le fuseau de services.clock ; clock = services.clock dans cette zone
     index = SearchIndex()                                   ← une seule instance : magasin, hygiène, rappel
     store = DuckMemoryStore(journal, index, LatePlayClock, clock, services.trace)
     playClock = DuckPlayClock(store, journal, players)      ← LatePlayClock lié à elle tout de suite
     playClock.load(now)                                     ← thread serveur, avant toute connexion (30 s au plus)
     recall = HybridRecall(journal, index, playClock, clock)
     sheets = DuckPlayerSheets(journal, playClock, players, zone)
     hygiene = Hygiene(store, journal, playClock, index, Decisions(services.trace, clock), zone)
     refresher = StatsRefresher(journal, clock)
     reminiscence = Reminiscence(recall, store, journal, playClock, { config.memory }, clock, services.trace)
     agents = MemoryAgents(services)                         ← une seule : Chroniqueur et Rêveur
     jobs = MemoryJobs(services, store, DuckJobsData(journal), Chronicler(services, agents), Dreamer(services, agents, hygiene),
                       JobHooks(tick/save/worldPlaySeconds = playClock, tidy = hygiene, refreshStats/activeSince = refresher,
                                favorLines = Favor.read + Favor.situationLines, placeReturn/anniversary = reminiscence))
     MemoryService(store, recall, sheets, playClock, jobs, agents,
                   MemoryBriefing(store, recall, sheets, journal, { joueurs en ligne }, zone),
                   WakeAttachments(JoinBrief(store, sheets, journal, zone), reminiscence))   ← la même Reminiscence
     playClock.subscribe(bus)                                ← après load
     jobs.start()                                            ← dans services.scope, pendant STARTING
```

| Méthode de `Memory` | Délègue à |
|---|---|
| `store`, `recall`, `sheets`, `clock`, `jobs` | `DuckMemoryStore`, `HybridRecall`, `DuckPlayerSheets`, `DuckPlayClock`, `MemoryJobs` |
| `briefing(chapter, now)` | `MemoryBriefing.sections` |
| `attachments(signals, chapter, now)` | `WakeAttachments.block` |

| `stop()` | `MemoryJobs.stop` |

## Démarrage et arrêt

- **Démarrage** : deux lectures du Journal sur le thread serveur (`runBlocking`), chacune bornée à 30 s : le schéma, puis l'horloge de jeu (`load`). C'est la seule attente de la base par le thread serveur, au démarrage, comme l'ouverture du Journal juste avant. Elle est nécessaire : l'horloge doit être chargée avant toute connexion, et aucun joueur ne peut se connecter tant que `SERVER_STARTED` n'a pas rendu la main. Une lecture trop longue ou une erreur : `DisabledMemory("it could not start: …")`, avec un `ERROR`. Sur le serveur de GameTest comme au démarrage réel : bien moins d'une seconde.
- **Travaux démarrés pendant `STARTING`** : sans danger. Le premier passage des minuteries a lieu tout de suite, mais tout ce qui touche au Directeur ou lance un modèle attend `Phase.RUNNING` (lot, sieste, rêve, rattrapage, échéances, indices). `RUNNING` n'arrive qu'une fois `memory` et `director` posés : `services.memory` n'est jamais lu avant d'exister.
- **Arrêt**, à `SERVER_STOPPING` (`ShutdownSequence.begin`), dans cet ordre :
  1. `Phase.STOPPING` : aucun travail ne démarre plus ;
  2. **`memory.stop()`** : le travail en cours est annulé et sa ligne `memory_runs` passe `cancelled` (« the server stopped »), sa conversation aussi ; la file est vidée ; l'horloge du monde est sauvée. 11 s au plus (deux écritures de 5 s au plus), d'ordinaire quelques millisecondes (`stopping: memory stopped in 8 ms` sur le serveur de GameTest) ;
  3. puis l'annulation de tout le reste (Directeur, workers…), comme avant.

  La mémoire s'arrête **avant** le reste, pendant que le Journal écrit encore. La clôture du chapitre par le Directeur (`shutdown`), qui vient ensuite, met encore une sieste en file : elle est perdue avec la file, et le rattrapage du prochain démarrage la refait (chapitre `shutdown` sans sieste, M3-12).

## Décisions et écarts

1. **`Memory.stop()` ajouté au contrat** (avec un corps vide par défaut) : `ShutdownSequence` ne connaît que des fonctions, et la façade est ce que le runtime tient. L'autre solution, un transtypage en `MemoryService` dans `NarratorRuntime`, était moins propre. `FakeMemory` et `DisabledMemory` n'ont pas changé.
2. **Dépendance circulaire entre le magasin et l'horloge.** `DuckMemoryStore` veut un `PlayClock` (il date ce qu'il écrit), et `DuckPlayClock` veut le magasin (il garde son état dans `memory_state`). Les passations M3-03 et M3-06 donnaient chacune une construction qui supposait l'autre objet déjà là ; les tests contournaient avec un `FakePlayClock`. `LatePlayClock` (privé, dans `MemoryModule.kt`) est donné au magasin et lié à la vraie horloge dès qu'elle existe, avant toute écriture. Aucune des deux classes n'a changé.
3. **Vérification explicite du schéma** (version ≥ 2 et les 17 tables de `MemorySchema.TABLES`). Si V2 échoue, `DuckDatabase.open` échoue et le Journal est déjà indisponible ; la vérification couvre un Journal ouvert mais abîmé. Elle coûte une lecture au démarrage.
4. **Fuseau** : `journal.timeZone`, sinon celui de `services.clock`. C'est la règle d'`ExchangeLog` et de `DreamInputs`, et le fuseau réel du Journal. Les passations M3-07 et M3-13 écrivaient `services.clock.zone` : c'est le même quand `journal.timeZone` est vide (le cas par défaut). L'horloge passée au magasin, au rappel, à la réminiscence et aux stats est `services.clock` dans ce fuseau (même instant).
5. **Décisions sur `services.trace`** (magasin, réminiscence, hygiène), comme l'ordonnanceur : c'est le Journal en production, la trace des tests sinon. `StatsRefresher` garde les siennes sur le Journal (son constructeur ne prend pas de trace).
6. **`available` reste vrai pendant une panne du Journal** : la mémoire est branchée ; chaque lecture ou écriture échoue alors avec la raison du Journal (outils en `FAILED`, sections du briefing en `(unavailable: …)`), puis remarche à la réouverture. Basculer `available` couperait les outils de mémoire pour tout un chapitre ouvert pendant la panne.
7. **`memory.enabled` n'est lu qu'au démarrage** : `/narrator reload` ne branche ni ne débranche la mémoire (KDoc de `createMemory`).
8. **`MemoryCommandGameTests` exige la mémoire** : le refus de toutes les commandes sans mémoire reste testé en unitaire (`MemoryCommandsTest`). Le test vérifie maintenant la ligne `Memory: available · jobs running · …` de `/narrator status`, la fiche réelle de l'opérateur (`Identity: uuid <son UUID> · first seen …`, lue dans le Journal) et `/narrator memory status` (travaux, horloge, comptes des tables).
9. **`MemoryGameTests`** (nouveau) : la mémoire du serveur de test est un `MemoryService`, le schéma est en version ≥ 2, l'horloge est sauvée dans `memory_state`, les travaux tournent, le jeu d'outils d'un chapitre (construit comme `Chapters` le fait) a les cinq outils de mémoire et aucun outil du Chroniqueur ni du Rêveur, `/narrator memory status` répond.
10. **`DirectorEndToEndTests`** : `ANALYST_TOOLS` reçoit `player_profile` et `recall` (passation M3-09) ; le premier message du vrai Directeur a les cinq outils de mémoire et les six sections, sans `(memory unavailable` ni `(unavailable:`.

## Problèmes d'intégration vus (non corrigés : hors périmètre, à la relecture de M3)

1. **`PairStats.compute` déborde (M3-05)**, `memory/stats/PairStats.kt` ligne 107 : la distance est calculée en `INTEGER` (`(a.x - b.x) * (a.x - b.x) + …`). Dès que deux joueurs sont à plus de 46 340 blocs l'un de l'autre sur un axe, DuckDB lève « Overflow in multiplication of INT32 », et **toutes les paires du serveur** échouent à chaque recalcul (`WARN` « stats: pairs failed … », 58 fois dans le log des GameTests, dont les structures sont à ±9 millions de blocs). Les stats des joueurs sont écrites quand même. Correctif simple : tester d'abord `abs(a.x - b.x) <= 32` sur chaque axe, ou calculer en `BIGINT`/`DOUBLE`. Sans effet tant que les joueurs restent près du point d'apparition, mais à corriger avant un vrai monde.
2. **Construction circulaire magasin ↔ horloge** (point 2 des décisions) : résolue ici sans toucher aux pièces.
3. **`chapterClosed` après `stop()`** (`MemoryJobs`) : la clôture `shutdown` du Directeur arrive après l'arrêt de la mémoire et écrit encore « nap of chapter N … queued as run M ». La sieste n'est jamais lancée (le rattrapage du démarrage suivant la refait) et l'identifiant `M` est perdu. Sans danger, mais le log trompe : `chapterClosed` pourrait ne rien mettre en file quand `stopping` est vrai.
4. **`MemoryJobs.stop` n'est pas borné** sur `cancelAndJoin` : un enfant bloqué dans une requête JDBC (statistiques, 30 s au plus) le retiendrait. `ShutdownSequence` le borne à 11 s ; au-delà, l'horloge n'est pas sauvée, mais rien n'est perdu : le chargement suivant ajoute les sessions jouées depuis la dernière sauvegarde (`world_play_saved_at`, M3-06).
5. **Le modèle scénarisé de `DirectorEndToEndTests` répond aussi au Chroniqueur** : la sieste du chapitre clos par le test reçoit des appels `sql` et `say`, que le Chroniqueur n'a pas (« 2 refused » dans le log). Sans effet sur le test (les requêtes sont filtrées par conversation), mais le scénario pourrait répondre `text` aux conversations `chronicler-`.

## Ce que M3-19 (recette réelle) doit savoir

- **Lignes `[Memory]` d'un démarrage normal** (premier démarrage d'un monde) :
  ```
  [Memory] world play clock recomputed from the sessions: 0s
  [Memory] play clocks loaded: world 0s, 0 players
  [Memory] memory jobs started
  [Memory] the memory is on: 0s of world play, times in Europe/Paris, jobs started
  ```
  puis, à l'arrêt : `[Memory] memory jobs stopped` et `[Narrator] stopping: memory stopped in N ms`. Un monde déjà joué : `world play clock: Ns played since its last save` à la place de la première ligne.
- **Quand les travaux partent** (M3-12) : premier passage au démarrage, puis toutes les 30 s ; le premier lot du chapitre ouvert au premier passage en `RUNNING` s'il y a eu une réplique, puis toutes les `chronicleMinutes` ; une sieste dès qu'un chapitre se clôt ; le rattrapage 30 s après le démarrage ; un rêve après `dreamAfterEmptyMinutes` de serveur vide (ou `dreamMaxHours`), seulement après une sieste réussie. `/narrator memory chronicle` et `/narrator memory dream` les forcent.
- **`runServer` donne la clé LLMGW au serveur** (fichier `.secrets/llmgw.key` du checkout principal, `build.gradle.kts`) : avec le tunnel ouvert, le Directeur, le Chroniqueur et le Rêveur parlent au vrai Claude. Pour un démarrage sans coût, mettre `gateway.baseUrl` sur un port fermé dans `TheServer/config/narrator2/narrator2.json` (ce que j'ai fait pour la vérification ci-dessous).
- **`LiveMemoryCycleTest`** peut appeler `createMemory(services)` sur un `TestServices` réel : voir `MemoryServiceTest` (services en `STARTING` pendant la création, `services.memory` posé avant `RUNNING` grâce à une façade tardive, la même règle que `NarratorRuntime`). Le premier passage des minuteries peut lancer le lot du chapitre ouvert avant une demande d'opérateur : il faut scénariser les réponses du modèle **avant** d'écrire la fenêtre, et ne pas supposer qui a mis le lot en file.
- Le briefing d'un chapitre sur un monde vide : six sections qui disent chacune pourquoi elles sont vides (`(no grimoire yet: …)`, etc.), sans `(unavailable`.
