## Le compilateur (`EcjCompiler`)

```kotlin
class EcjCompiler(
    sdkLoader: ClassLoader = ForgeModule::class.java.classLoader,  // Knot en jeu
    budgetMs: Long = ForgeLimits.COMPILE_MS,                       // 10 s
    stuckMs: Long = ForgeLimits.COMPILER_STUCK_MS,                 // 60 s
    onStuck: (label: String, since: Instant) -> Unit = { _, _ -> },
) {
    suspend fun compile(typeName: String, source: String, label: String = typeName): Compilation
    val stuckSince: Instant?
    fun status(): String          // idle · compiling statues (2s) · stuck since 21:04:10 · stopped
    fun stop()                    // ne bloque jamais
    companion object { const val THREAD_NAME = "narrator2-forge-compiler"; val SDK_PACKAGES; val version: String? }
}
class Compilation(val outcome: Outcome, val classes: Map<String, ByteArray>, val problems: List<SourceProblem>, val millis: Long)
// Outcome : COMPILED, ERRORS, TOO_LONG, STUCK, STOPPED ; ok, errors
data class SourceProblem(error, line, column, start, end, message, id, arguments)
```

- **Ce que voit une source** : une unité sans paquet, `<TypeName>.java`, et, lus **par nom** quand ECJ les demande
  (rien n'est listé d'avance) : les paquets que `java.base` **exporte à tous** (lus dans `jrt:/`, présent sur un JRE)
  et les deux paquets du SDK, lus par `sdkLoader.getResourceAsStream`. **Écart (durcissement)** : `ForgeSamples` et le
  §5.1 prenaient *tous* les paquets de `java.base` (`Any::class.java.module.packages`), donc `jdk.internal.misc.Unsafe`,
  `sun.nio.ch`… se résolvaient ; ici ils « cannot be resolved » (testé). Le témoin compile pareil, **octets
  identiques** à `ForgeSamples.classes` (testé), ainsi qu'un module jetable de 70 lignes qui touche à tout le JDK permis
  (flux, `java.time`, `Collectors.groupingBy`, motifs, records, *text blocks*, atomiques… ; essai hors dépôt, aucune
  erreur « indirectly referenced »). Le chargeur du mod
  n'est jamais interrogé hors du SDK (testé, et en jeu : `net.minecraft.*`, `NarratorRuntime`, `forge.rt`, Fabric ne
  se résolvent pas, alors que Knot les connaît).
- **Options** : celles du §5.1 (25, lignes, fichier source, variables locales ; dépréciation, import inutile, type brut,
  non vérifié ignorés). `useSingleThread = true` posé exprès (aucun fil d'ECJ).
- **`package`** : ECJ le refuse lui-même (`The declared package "x" does not match the expected package ""`) ; une
  classe publique d'un autre nom aussi (`must be defined in its own file`). L'étape 1 du pipeline (M5-10) peut garder
  son contrôle de `package` pour un message plus tôt, ce n'est plus nécessaire à la sûreté.
- **Le fil** : un seul, `narrator2-forge-compiler`, démon, `MIN_PRIORITY`, **pile fixée à 1 Mio** (comme le défaut
  de la JVM, mais indépendante de `-Xss` : la profondeur qu'une source peut atteindre est la même partout). Créé et
  démarré dans le constructeur ; sans ECJ, le constructeur lève `NoClassDefFoundError` (M5-21 : `DisabledForge("ECJ is
  missing: …")`). Une file sans borne, dans l'ordre ; l'appelant suspend (`CompletableFuture.await`), ne bloque jamais ;
  **annuler l'appelant retire sa compilation** (sautée si elle n'a pas commencé, annulée au contrôle suivant sinon).
- **Le budget de 10 s** : l'appelant reçoit `TOO_LONG` **à 10 s pile** (`completeOnTimeout`), même si ECJ ne rend pas
  la main ; ECJ, lui, s'arrête au **contrôle suivant** de sa `CompilationProgress` (entre ses phases : avant/après
  l'analyse, avant/après le traitement de l'unité — pas pendant la résolution, l'analyse de flot ni la génération,
  qui forment une seule phase pour une unité). Puis le fil passe à la suivante.
- **Bloqué (§3.8)** : si la même compilation tourne encore à 60 s, le compilateur est **bloqué jusqu'au redémarrage**
  (collant, même si elle finit ensuite) : les compilations en attente reçoivent `STUCK` aussitôt, les suivantes aussi,
  `onStuck(label, since)` est appelé **une fois**, sur un fil du pool commun, et un `WARN` est écrit. `since` = **le
  début** de la compilation fautive (c'est ce que montre `stuck since 21:04:10`). À M5-10 : `Forge.available` faux et
  la décision `forge stuck` dans `onStuck`.
- **`stop()`** (`SERVER_STOPPING`) : rien ne compile plus ; celle en cours et celles en attente reçoivent `STOPPED`
  aussitôt ; le fil finit après le prochain contrôle d'ECJ (une pilule dans la file, **jamais d'`interrupt`** : un fil
  interrompu pendant une lecture de `jrt:/` pourrait fermer un canal partagé). Ne bloque jamais.
- **Une source qui fait tomber ECJ** : ECJ enregistre son « Internal compiler error », puis relance. Ici :
  `StackOverflowError` (une expression imbriquée trop profond : `a+a+…` 20 000 fois, 40 000 caractères, sous la limite
  de 48 000) → `ERRORS` avec **un** problème à la ligne 0, « the source nests too deeply for the compiler… », et un
  `WARN` sans pile ; toute autre exception → `ERRORS` « the compiler failed on this source (X)… » et un `WARN` avec la
  pile. Le fil continue (testé : le témoin compile juste après). Le message interne d'ECJ (une pile en texte) n'est
  jamais rendu au Forgeron.
- **Contrats d'appel** : un `typeName` qui n'est pas `[A-Z][A-Za-z0-9]*` ou une source de plus de
  `ForgeLimits.SOURCE_CHARS` lèvent `IllegalArgumentException` : c'est l'étape 1 du pipeline (M5-10) qui les vérifie et
  rend `Invalid arguments`. La limite de 32 classes et 256 Kio (étape 3) est à `BytecodeGuard` (M5-03), pas ici.
- **`EcjCompiler.version`** : `3.46.100`, lu dans `org/eclipse/jdt/internal/compiler/batch/messages.properties` du jar
  d'ECJ (`compiler.version = v20260826-1225, 3.46.100`) : pour `ForgeStatus.ecj` (M5-10). Marche en jeu et en tests,
  sans `FabricLoader`.
- **Journal** : `DEBUG` pour chaque compilation (durée, classes, ou premier message d'erreur, ou « dropped by its
  caller ») ; `WARN` pour `TOO_LONG`, le blocage et une chute d'ECJ. La décision `forge compiled|refused|stuck` reste à `ForgeService` (M5-10).
- **Le cache** (§5.1, « 64 au plus ») n'est **pas** dans le compilateur : il garde des classes **réécrites**, c'est le
  `build` de `ForgeService` (M5-10, `ForgeServiceTest` › cache). Le compilateur ne garde rien entre deux sources.

## Les diagnostics (`Diagnostics`)

```kotlin
data class Diagnostic(kind: Kind /* ERROR, REFUSED, FAULT */, where, message, line = 0, column = 0, length = 0, also = [], hints = [])
object Diagnostics {
    fun compilation(typeName: String, source: String, problems: List<SourceProblem>): List<Diagnostic>   // erreurs seules
    fun refused(typeName: String, line: Int, message: String): Diagnostic                                // la garde (M5-03)
    fun fault(where: String, message: String, line: Int = 0): Diagnostic                                 // le banc (M5-08)
    fun render(diagnostics: List<Diagnostic>, source: String?, maxChars: Int = ForgeLimits.TEST_REPORT_CHARS): String
}
```

- **Format** : `[n] kind where: message`, la ligne sans son indentation (coupée à 100 caractères autour de la colonne,
  avec `…`), le soulignement, `also at` (les autres places du **même message**, 5 au plus), puis les indices. 20
  entrées au plus (`ForgeLimits.DIAGNOSTICS`) et `maxChars` (6 000 par défaut, `TEST_REPORT_CHARS`), le reste compté :
  `… 7 more not shown`. Les avertissements ne sont jamais rendus.
- **Indices** (lus dans l'`id` et les `arguments` d'ECJ, et dans la source) :
  - méthode absente ou inapplicable sur un type du SDK : ses surcharges, sinon les noms proches (distance d'édition
    *optimal string alignment*, une transposition compte 1 ; ou un nom contenu dans l'autre) ; sinon le même nom
    **ailleurs dans le SDK** (`ctx.spawn` → `Acts`, `say(…)` dans la classe du module → `Acts.say`) ; chaque type est
    suivi de son chemin depuis le contexte (`Acts (ctx.acts())`) et chaque argument du SDK de ses fabriques
    (`— Spawn.of(int)`) ;
  - constructeur absent d'un type du SDK : ses fabriques puis ses constructeurs ;
  - champ ou nom absent : les membres proches du type qualifiant (`Limits.MAX_ACT` → les constantes, **avec leur
    valeur**), sinon les membres du SDK à distance 1 ;
  - type introuvable : la règle enfreinte (jeu, mod, JDK hors `java.base`), l'**équivalent SDK** des classes du jeu
    qu'un modèle cherche d'abord (`ServerPlayer`, `Player`, `BlockPos`, `Vec3`, `Entity`/`Mob`…, `Level`/`ServerLevel`,
    `ItemStack`, `Block`/`BlockState`, `EntityType`, `Component`, `MobEffect`…, `ServerTickEvents`), l'import qui manque
    (`import java.util.List;`, `import io.github.clemsix6.narrator2.forge.api.*;`), ou les types du SDK proches
    (`PlayerInf` → `PlayerInfo`) ;
  - import introuvable : les mêmes règles, et rien pour une faute de frappe dans un paquet permis (`java.util.Lis`) ;
  - `package` : « a module has no package: delete this line » ; classe mal nommée : son nom attendu.
- Une **règle** (`GAME_RULE`, `MOD_RULE`, `JDK_RULE`) n'est écrite qu'une fois par rapport ; un indice sur un membre
  l'est à chaque entrée qui en a besoin.
- **Écart : pas de noms de paramètres** pour les interfaces du SDK (`Pending spawn(String, String, Spawn)`, et non
  `spawn(String type, String near, Spawn how)` comme dans l'exemple du §5.3) : `javac` compile le SDK sans
  `-parameters`, et ajouter ce drapeau toucherait aussi les mixins (`compileJava` est un seul lot). Les constructeurs
  des records ont leurs noms (les composants). **Proposition au superviseur** : `-parameters` sur `compileJava` (une
  ligne dans `build.gradle.kts`) ; `Diagnostics` montre alors les noms sans autre changement (`Parameter.isNamePresent`
  n'est pas encore lu : à ajouter dans `parameters(…)`, une ligne). Le Forgeron a de toute façon les noms dans `sdk.md`.
- **L'index du SDK** est fait par réflexion sur le SDK lui-même (racines `ForgeModule`, `Bench`, `Sdk`, `Limits`,
  `Text`, `ModuleInfo`, `ParamList`, `ForgeRefusal`, puis les signatures publiques, les types membres et les sous-types
  permis) : rien à tenir à jour. `DiagnosticsTest` vérifie qu'il connaît **chaque type public des deux paquets** (54
  aujourd'hui) : un type que rien n'atteint fait échouer le test, il suffit de l'ajouter aux racines.

## Ce que les tâches suivantes doivent savoir

- **M5-03 (garde)** : les refus se rendent par `Diagnostics.refused(typeName, line, "java.lang.Thread: threads are
  not allowed in a module (use ctx.timers())")` : votre motif complet dans le message ; la ligne vient de la table des
  lignes (0 si inconnue). `Compilation.classes` a des **noms binaires avec des points** (aucun paquet ici : `TagGame`,
  `TagGame$1Rank`). « À soi » = `compilation.classes.keys`. Le compilateur voit moins que `ForgeSamples.compile` : un
  cas de test qui nomme `jdk.internal.*` ne compile qu'avec `ForgeSamples` (gardez-le pour fabriquer ces cas).
- **M5-05 (hôte)** : `fault(where, message, line)` pour une faute ; la ligne du premier cadre du module.
- **M5-08 (banc)** : idem pour les fautes et les scénarios ratés (`fault("scenario x", "check failed: …", line)`).
- **M5-10 (service)** :
  - l'étape 1 vérifie le nom, la taille, et peut garder `package` ; puis `compile(Manifest.mainClass(name), source,
    label = name)` ; `Compilation.classes` va tel quel à `Manifest.read(name, classes)` (M5-09 : noms binaires, avant la
    réécriture) ; les problèmes du manifeste (un par ligne) peuvent devenir des
    `Diagnostic(Diagnostic.Kind.ERROR, "$typeName.java", problème)` pour le même rendu ;
  - `COMPILED` → étapes 3 à 6 ; `ERRORS` → `Diagnostics.render(Diagnostics.compilation(typeName, source,
    c.problems), source)` dans le rapport (`TestReport.text`, l'en-tête à vous) ; `TOO_LONG` →
    `ForgeRejected(null, "the compilation took too long", failed = true)` ; `STUCK` → la Forge indisponible
    (`compiler stuck`) ; `STOPPED` → le serveur s'arrête ;
  - un seul `EcjCompiler` pour le service, `onStuck` → décision `forge stuck` et `available = false` ;
    `ForgeStatus(EcjCompiler.version, compiler.status())` ; `Forge.stop()` → `compiler.stop()` ;
  - le **cache des versions construites** (§5.1) est à vous ;
  - le budget de 10 s tient pour l'appelant ; mais le fil reste pris tant qu'ECJ n'a pas atteint son contrôle suivant :
    une compilation suivante attend (jusqu'au blocage à 60 s, qui la libère avec `STUCK`).
- **M5-18 (batterie)** : la famille « Noms » (`package`) est arrêtée par le compilateur ; les cas `jdk.internal.misc.Unsafe`
  et `sun.misc.Unsafe` aussi (« compilateur ou garde » au §16.2). Une source **pathologique pour ECJ** (inférence
  explosive) qui dépasse 10 s n'a pas été trouvée ni écrite : si vous en trouvez une, elle doit donner `TOO_LONG` à
  10 s et, si elle tient 60 s, le blocage (les deux sont testés ici avec un chargeur qui retient ECJ).
- **M5-21 (assemblage)** : `EcjCompiler()` lève `NoClassDefFoundError` sans ECJ : c'est le cas `DisabledForge("ECJ is
  missing: …")`.
