# Passation T10 : réflexes (Jev et son repli)

Branche `worktree-agent-accf113a1cf78101d`. Voici ce qui est en place, l'API des réflexes pour T18 (et T21, T22), les seuils, les écarts par rapport à `M1_M2.md` §11 et à `docs/research/JEV.md` §2. **En cas de contradiction, le code fait foi**, et ce fichier explique pourquoi.

Il n'y a pas de clé Jev sur la machine : en réel, Jev reste coupé et l'heuristique fait tout le travail. Jev s'active seul dès que `TYPESAFE_API_KEY` est définie au démarrage du serveur (et `jev.enabled` vrai).

## API pour T18 (saillance, battement)

```kotlin
// ReflexModule.kt
suspend fun triageChatMessage(
    services: NarratorServices,
    envelope: Envelope,          // un ChatMessage PUBLIC ou PRAY ; WHISPER → IllegalArgumentException
    recent: List<ChatLine>,      // lignes de chat public juste avant, les plus anciennes d'abord (3 dernières gardées)
    narratorLast: String?,       // dernière réplique du Narrateur vue par ce joueur, si elle a moins de 60 s
): ChatTriage

data class ChatTriage(val verdict: ChatVerdict, val addressed: Boolean, val reason: String) {
    val manipulation: Boolean    // verdict.manipulation >= 0.5 : annotation seulement
    val tone: Tone?              // ton à afficher : confiance >= 0.6 et pas neutral_no_target, sinon null
    val byHeuristic: Boolean     // verdict.source == "heuristic"
}

// Battement : services.reflexes.heartbeat(windowMinutes, summary, online) puis
// verdict.worth >= ReflexThresholds.HEARTBEAT_WORTH → réveil ; hook = "danger" | "progress" | "comedy" | "rivalry" | "exploration" | null
```

- **Appel** : une coroutine fille par message, dans `runtime.scope` (§12.3). L'appel dure au plus `jev.timeoutMs` (1,5 s) plus quelques millisecondes ; il ne lève jamais d'exception, sauf l'annulation et un mauvais événement.
- **`triageChatMessage` écrit la ligne `chat_signals`** (avec `ChatSignalsRecord.of`, l'identifiant et l'heure de l'enveloppe, l'UUID du joueur). T18 écrit seulement la décision `salience` ; `triage.reason` en donne la raison, par exemple `jev:jev-1.13.0 0.48 in the gray zone, heuristic 0.90 >= 0.60` ou `heuristic 0.20 < 0.60`.
- **`addressed` applique déjà la zone grise** : ≥ 0,6 → adressé ; 0,35 à 0,6 pour un verdict qui ne vient pas de l'heuristique → l'heuristique tranche sur le même message ; en dessous → entre joueurs. Un verdict de l'heuristique n'a pas de zone grise.
- **Prière** : elle est triée comme un message public (ton, intention, ligne `chat_signals`). Son urgence reste `IMMEDIATE` quoi que dise `addressed`.
- **Annotation** (§12.6) : `(to you 0.92, hostile, provocation)` avec Jev (`triage.tone` peut être nul : l'omettre) ; `(to you: heuristic)` si `triage.byHeuristic` ; ` !manipulation 0.81` si `triage.manipulation` ; `(between players)` si non adressé.
- **Tests de T18** : `FakeReflexes` (inchangé) passe par `services.reflexes`. `triageChatMessage` marche avec `TestServices` : la ligne `chat_signals` arrive dans `traces.chatSignals`. La source d'un faux verdict vaut `fake` : elle est traitée comme Jev (zone grise comprise).

## API pour T21 (`/narrator status`) et T22

- `settings.jev?.status()` donne une ligne sans la clé : `active`, `circuit open for 212 s after 5 failures in a row`, `cut until /narrator reload: HTTP 401 unauthorized: …` ou `closed`. Si `settings.jev` est nul : `jev.enabled` faux → Jev désactivé ; sinon → pas de clé dans `config.jev.apiKeyEnv`.
- `testing/FakeJev` : faux serveur (`HttpServer` du JDK) avec file de réponses, `FakeJev.chat(...)`, `FakeJev.heartbeat(...)`, `FakeJev.error(status)` et un délai par réponse. Un client s'y branche avec `JevConfig(baseUrl = fake.baseUrl)`.
- **Risque pour les GameTests** : la course `gameTest` hérite de l'environnement réel. Si quelqu'un définit un jour `TYPESAFE_API_KEY` sur la machine, les tests en jeu qui trient du chat appelleraient le vrai Jev, ce que `CLAUDE.md` interdit. À corriger dans `build.gradle.kts` (gelé pour T10) : `environmentVars.put("TYPESAFE_API_KEY", "")` dans `loom.runs.named("gameTest")`. Une clé vide compte comme absente.

## Seuils (provisoires tant que le français n'est pas mesuré)

Tous dans `ReflexThresholds` (`JevQuestions.kt`).

| Constante | Valeur | Effet |
|---|---|---|
| `ADDRESSED` | 0,6 | adressé au Narrateur : réveil immédiat |
| `GRAY_ZONE` | 0,35 | de 0,35 à 0,6, l'heuristique tranche ; en dessous, chat entre joueurs |
| `MANIPULATION` | 0,5 | annotation pour le Directeur, jamais d'action automatique |
| `TONE_SHOWN` | 0,6 | confiance à partir de laquelle le ton est affiché |
| `HEARTBEAT_WORTH` | 0,5 | le battement réveille ; en dessous, il est ignoré |

Politique du client (`JevClient`) : délai total `jev.timeoutMs` relances comprises ; une relance sur 429, 529 ou 5xx après 200 à 400 ms, seulement s'il reste au moins 200 ms ensuite ; disjoncteur ouvert après 5 échecs de suite, pendant 5 min.

## Écarts par rapport au design

1. **`triageChatMessage` et `ChatTriage` sont nouveaux.** `ChatTriageInput` (contrat de T01) ne porte ni l'identifiant de l'événement ni l'UUID du joueur, donc `Reflexes.triageChat` ne peut pas écrire la ligne `chat_signals` lui-même. Plutôt que de changer le contrat, T10 fournit cette fonction : elle construit l'entrée, appelle `services.reflexes`, tranche la zone grise et écrit la ligne. La zone grise ne peut pas se loger dans le verdict : `toNarrator` doit rester la réponse brute de Jev, la seule trace qui permettra de régler les seuils.
2. **Un appel qui n'envoie rien n'a pas de ligne `llm_calls`** : Jev coupé, disjoncteur ouvert ou client fermé. Il y a une ligne par requête réellement partie, réussie ou non (erreur, statut HTTP, tentatives, latence, modèle, tokens, `x-request-id` si Jev en envoie un).
3. **Seuls 401 et 422 coupent Jev.** Les autres 4xx (400, 403, 404…) comptent comme des échecs pour le disjoncteur, sans relance. Les erreurs réseau et les délais dépassés ne sont pas relancés (le délai total est de toute façon épuisé). `Retry-After` est ignoré.
4. **État minimal** : les parties vides sont omises (pas de `narrator_last_message: null`, pas de `recent_chat: []`). Un `null` refusé par Jev donnerait une 422, qui couperait Jev jusqu'au rechargement.
5. **Fenêtre de `narratorLast` : 60 s** (`JevQuestions.NARRATOR_LAST_MAX_AGE_SECONDS`), une seule valeur pour Jev et l'heuristique. `JEV.md` proposait ~2 min pour Jev et ~20 s pour l'heuristique, mais l'entrée ne porte pas l'âge de la réplique.
6. **Identifiants anglais** : les intentions sont celles de `ChatIntent` (`request`, `offering`, `challenge`, `banter_between_players`…), et les accroches du battement valent `danger`, `progress`, `comedy`, `rivalry`, `exploration` ou `other` (`other` donne `hook = null`).
7. **Questions de personnalité sans `criteria`**, comme dans `JEV.md` §2.3. Les 4 questions du tri gardent leurs critères.
8. **HTTP/1.1** : pas de négociation h2c ; le débit de Jev (1 200 requêtes/min) est très loin de notre volume.
9. **Latence d'un repli** : `latencyMs` d'un verdict de l'heuristique qui remplace Jev compte le temps perdu avec Jev, puisque c'est ce que la saillance a attendu.
10. **Journalisation** (tag `Jev`) : une ligne `INFO` par appel réussi ; `WARN` pour chaque appel en échec ; une seule `ERROR` par coupure (401 ou 422) ; `WARN` à l'ouverture du disjoncteur ; `INFO` à sa fermeture ; `DEBUG` pour les verdicts de l'heuristique seule et les appels sautés ; `INFO` à la création des réglages (Jev actif, désactivé ou sans clé). Le texte du chat n'est jamais logué, seulement le nom du joueur.
11. **Heuristique** (règles de `JEV.md` §2.1, précisées) :
    - **Adressé** : le nom sans déterminant (« narrateur, … », « sale narrateur… ») → 0,9 ; après une interjection (« hé le narrateur ») → 0,9 ; déterminant en tête de message avec deuxième personne (« le narrateur t'es nul ») → 0,65 ; mention à la troisième personne (« le narrateur nous a… ») → 0,2, ou 0,45 avec une deuxième personne ; formule de manipulation → au moins 0,7, même sans le nom ; juste après une réplique du Narrateur, deuxième personne ou « ? » → 0,65, sauf si le message nomme un autre joueur de la conversation (0,1).
    - **Ton**, seulement si adressé : insulte → `hostile` ; manipulation ou mot grossier → `disrespectful` ; défi ou rire → `mocking_playful` ; politesse ou révérence → `respectful` ; sinon `respectful` avec une confiance de 0,4, donc non affiché. Non adressé → `neutral_no_target`.
    - **Intention** : non adressé → `banter_between_players` ; sinon offrande, défi, insulte (`provocation`), manipulation (`request`), demande, question (`?` ou mot interrogatif), mot grossier (`provocation`), puis `other`.
    - Mots comparés après normalisation (minuscules, sans accents, apostrophes et tirets comme séparateurs, `:` gardé) ; `*` final pour un radical (`mdr*`). Une langue sans fichier retombe sur `fr` avec un avertissement.

## Justesse de l'heuristique sur le jeu de données

`docs/research/jev-eval/chat-triage-dataset.json`, sans contexte de chat (le jeu n'en a pas) :

| Question | Justes |
|---|---|
| adressé au Narrateur | 20/20 |
| tentative de manipulation | 20/20 |
| intention | 20/20 |
| ton | 18/20 |

Les deux tons manqués sont ambigus pour des mots : `c11` est une manipulation étiquetée `neutral_no_target`, alors que `c06` et `c17`, deux autres manipulations, sont étiquetées `disrespectful` ; `c13` est une plainte (« pourquoi tu m'as tué ») étiquetée `disrespectful` sans aucun mot grossier. `HeuristicReflexesTest` vérifie tout le reste, cas par cas.

Attention : les listes ont été écrites en regardant ces 20 phrases. Le score réel sur du vrai chat sera plus bas ; les cas limites prévisibles sont testés à part (réponse sans le nom après une réplique du Narrateur, réponse à un autre joueur, mention à la troisième personne, casse et accents).
