# Passation T08 : cadre des outils

Commit `8f8abfc`, puis celui de cette passation. Voici ce qui est en place, les écarts par rapport à `M1_M2.md` §8 et la façon de déclarer un outil. **En cas de contradiction, le code fait foi**, et ce fichier explique pourquoi.

## Ce qui est en place

Tout est dans le paquet `tool`. Aucun contrat de T01 n'a été touché.

| Fichier | Contenu |
|---|---|
| `ToolSchema.kt` | `ToolSchema.definition(tool): ToolUnion` (définition SDK) et `ToolSchema.of(descriptor, where): JsonObject` (schéma d'entrée) |
| `ToolArgs.kt` | `ToolArgs.decode(serializer, input): Decoded<A>` (`Ok(args)` ou `Invalid(problem)`) et `ToolArgs.json`, le `Json` strict du §8.3 |
| `ToolSet.kt` | `ToolSet.of(tools)` : outils triés par nom, avec leurs définitions générées |
| `ToolRunner.kt` | `ToolRunner(services, clock = services.clock) : ToolExecutor` |
| `ToolCatalog.kt` | `toolSetFor(role, env, services)` : outils du rôle, filtrés par `isAvailable`, triés, avec la décision `tool_catalog` |

- `ToolSet.of` est une extension de `ToolSet.Companion`. Hors du paquet `tool`, il faut l'importer : `import io.github.clemsix6.narrator2.tool.of`.
- Le schéma et le décodage lisent **le même descripteur** : ils ne peuvent pas diverger.
- **Octets stables** : les outils sont triés par nom, les propriétés gardent l'ordre de déclaration, et le SDK garde cet ordre à la sérialisation. `ToolSchemaTest` le vérifie sur les octets réellement envoyés (deux constructions, ordres d'entrée différents).
- **Pas de `strict`** dans les définitions. Seul `additionalProperties: false` est ajouté.

## Écarts par rapport au design

1. **Les messages d'erreur sont écrits par `ToolArgs`, pas repris de kotlinx.**
   - Les messages de kotlinx citent le nom des classes Kotlin et donnent des conseils au développeur (« Use 'ignoreUnknownKeys = true'… »), ce qui n'aide pas le modèle.
   - `ToolArgs` parcourt donc l'entrée avec le descripteur avant de décoder, et renvoie **tous** les problèmes d'un coup, séparés par `; `. Les chemins suivent la forme `enchantments[1].level`. Formes :
     - `text is required`
     - `unknown argument "colour" (expected: text, to)`, ou `(this tool takes no arguments)`
     - `text must not be null`, ou `… (leave it out to use the default)` si l'argument a une valeur par défaut
     - `seconds must be an integer (got "ten")` ; `a string`, `a number`, `true or false`, `a list`, `an object`
     - `shape must be one of: small_ball, star (got "circle")`
     - `seconds must be between 1 and 900 (got 1200)`
     - `text is longer than 300 characters (got 412)` : des caractères, pas des unités UTF-16
     - `to must have 1 to 8 items (got 9)`
     - `count is too large (got 3000000000)`, pour un `Int` sans `@Range`
   - La valeur citée après `got` est coupée à 40 caractères.
   - Ensuite, kotlinx décode en mode strict. Ses rares messages restants sont renvoyés sur leur première ligne, comme ceux d'un `require` placé dans le `init` de la classe d'arguments.
2. **Une propriété nullable est facultative**, même sans `= null`. Cela suit `explicitNulls = false`, où une propriété absente vaut `null`. On garde quand même la convention `= null`.
3. **Sur une liste, `@Range` et `@MaxLen` bornent chaque élément.** `@Items` borne la liste elle-même. Exemple pour `give_book` : `@Items(1, 10) @MaxLen(600) val pages: List<String>`.
4. **Noms en snake_case obligatoires**, pour les propriétés comme pour les valeurs d'énumération. Sinon, la construction échoue et le message demande `@SerialName`.
   - Échouent aussi : une annotation mal placée (par exemple `@MaxLen` sur un `Int`), un `@Range` inversé, les `Map`, le polymorphisme, les types `@Contextual`, les classes inline, `Char` et la récursion.
   - L'erreur nomme l'outil et l'argument : `give_item.enchantments[]: …`.
5. **Délai dépassé** : `TIMEOUT` pour un outil `READ`, et `UNKNOWN` pour **tous** les autres effets (`SPEECH`, `WORLD`, `TASK`, `ENGINE`). Tous ont un effet de bord qui a pu partir.
   - Textes : `TIMEOUT: <tool> did not finish within <ms> ms`
   - et `UNKNOWN: <tool> did not finish within <ms> ms; the action may or may not have happened`.
6. **Deux troncatures** :
   - 8 000 caractères pour le modèle (`ToolRunner.MODEL_RESULT_MAX_CHARS`, §8.4) ;
   - 2 000 caractères pour l'audit (`ToolCallRecord.RESULT_MAX_CHARS`).
   - Le suffixe est `… (truncated, N chars)`, où N est la longueur complète. Le texte coupé fait exactement la limite, et aucun caractère n'est coupé en deux.
7. **Annulation de l'appelant pendant un outil** (arrêt du serveur) :
   - la ligne `tool_calls` est quand même écrite : `UNKNOWN: cancelled while running, the server is stopping; the action may or may not have happened`, ou `FAILED: cancelled…` pour une lecture ;
   - puis l'annulation se propage, et les appels suivants ne tournent pas.
   - Une `CancellationException` levée par l'outil lui-même, alors que l'appelant est encore actif, donne `FAILED` pour cet appel seulement.
8. **Exceptions** :
   - Les `Error` donnent `FAILED` elles aussi (un `TODO()`, une classe absente après une mise à jour du jeu), sauf `VirtualMachineError`.
   - `ServerThreadTimeoutException` et `ServerStoppedException` sont loguées en `WARN` sans la pile ; les autres en `ERROR` avec la pile.
   - Si l'exception n'a pas de message, c'est le nom de sa classe qui est renvoyé.
9. **Outil inconnu** : `Invalid arguments: unknown tool "x"; your tools are: …`. La ligne d'audit porte `effect = read`, puisque rien n'a tourné.
10. **Résultat vide** : le modèle reçoit le statut (`ok`), jamais un `tool_result` vide.
11. **`is_error`** n'est posé que sur une erreur ; il est absent pour `OK`.
12. **Décision `tool_catalog`** :
    - `decision = built`, `subject` = le rôle, `reason = "N tools; not wired, left out: a, b"` ;
    - `detail = {tools, left_out, journal_available, worker_roles}` ;
    - `conversation_id` est nul, car le `ToolSet` est construit avant la conversation.
13. **Rôles** :
    - le Directeur a tous les outils ;
    - l'Analyste a les 7 noms du §9.7 (`sql`, `list_players`, `inspect_player`, `player_stats`, `area_info`, `scan_area`, `locate`) ;
    - les autres rôles n'ont aucun outil pour l'instant.
    - Un nom de l'Analyste absent des familles est ignoré : aujourd'hui, toutes les familles sont vides.
14. **Surcharge de test** : `internal toolSetFor(role, env, tools, decisions)` applique les mêmes règles à une liste donnée.
15. **Journalisation** :
    - `tool_calls.args` contient l'entrée du `tool_use`, resérialisée par le SDK et jamais tronquée, puisque la colonne est en JSON.
    - Le log a une ligne `INFO` par appel, `WARN` si le statut est `FAILED`, `TIMEOUT` ou `UNKNOWN`.
    - Les arguments complets sont logués en `DEBUG`.

## Déclarer un outil (T13 à T17, T20)

Exemple minimal complet. Il a été compilé, et son schéma généré, dans un fichier temporaire supprimé depuis. Les signatures de Minecraft ont été vérifiées avec javap.

```kotlin
package io.github.clemsix6.narrator2.tool.speech

import io.github.clemsix6.narrator2.runtime.NarratorServices
import io.github.clemsix6.narrator2.tool.Doc
import io.github.clemsix6.narrator2.tool.Items
import io.github.clemsix6.narrator2.tool.MaxLen
import io.github.clemsix6.narrator2.tool.NarratorTool
import io.github.clemsix6.narrator2.tool.ToolContext
import io.github.clemsix6.narrator2.tool.ToolEffect
import io.github.clemsix6.narrator2.tool.ToolResult
import kotlinx.serialization.Serializable
import net.minecraft.network.chat.Component

@Serializable
data class ActionbarArgs(
    @Doc("Text shown above the hotbar, one line.") @MaxLen(100) val text: String,
    @Doc("Names of online players; everyone online when left out.") @Items(1, 8) @MaxLen(16) val to: List<String>? = null,
)

class ActionbarTool : NarratorTool<ActionbarArgs>(
    name = "actionbar",
    description = "Shows a short line above the hotbar of some players, or of everyone online.",
    args = ActionbarArgs.serializer(),
    effect = ToolEffect.SPEECH,
) {
    override suspend fun run(ctx: ToolContext, args: ActionbarArgs): ToolResult {
        val online = ctx.players.online
        val targets = if (args.to == null) {
            online
        } else {
            args.to.map { name ->
                ctx.players.byName(name)
                    ?: return ToolResult.invalid("$name is not online; online: ${online.joinToString { it.ref.name }}")
            }
        }
        val shown = ctx.onServer { server ->
            targets.filter { live ->
                val player = server.playerList.getPlayer(live.ref.uuid) ?: return@filter false
                player.sendOverlayMessage(Component.literal(args.text))
                true
            }.map { it.ref }
        }
        return ToolResult.ok("ok: shown to ${shown.size} players", targets = shown)
    }
}

fun speechTools(services: NarratorServices): List<NarratorTool<*>> = listOf(ActionbarTool())
```

Règles :
- **Nom** : en snake_case, 32 caractères au plus, vérifié par `NarratorTool`. LLMGW préfixe les noms de 52 caractères au plus : la marge est large.
- **Description** : en anglais, statique, sans nombre qui dépende du chaos ou de la config. Les plafonds vont dans les messages d'erreur.
- **Arguments** :
  - une classe `@Serializable`, ou `NoArgs` ;
  - `@SerialName("snake_case")` pour tout nom Kotlin en camelCase ;
  - types acceptés : `String`, `Int`, `Long`, `Double`, `Float`, `Boolean`, une énumération (`@SerialName` en snake_case sur chaque valeur), `List<T>` (ou `Set<T>`) et une classe `@Serializable` imbriquée ;
  - un argument facultatif prend une valeur par défaut ; un argument nullable, `= null`.
- **Bornes** : `@Range`, `@MaxLen` et `@Items` sont appliquées avant `run`. `run` reçoit donc des arguments déjà vérifiés. Une règle qui porte sur plusieurs arguments (par exemple « exactement un de `multiply` ou `add` ») va dans `init { require(…) { "give exactly one of multiply or add" } }` de la classe d'arguments : le message arrive tel quel au modèle, dans `Invalid arguments: …`.
- **Validation propre à l'outil** (identifiants de registre, joueurs en ligne, plafonds) : elle se fait dans `run`, avec `ToolResult.invalid(...)` ou `ToolResult.denied(verdict)`. Le message **donne la solution**.
- **Monde** :
  - passe par `ctx.onServer { server -> … }`, avec le délai de l'outil ;
  - `run` ne bloque jamais un thread : pas de réseau ni de JDBC en direct, on passe par les API suspendues ;
  - les outils sont bornés par construction (rayons, nombre de résultats).
- **`timeoutMs`** : 5 s par défaut. Le design prévoit 8 s pour `locate` et 12 s pour `teleport`.
- **`effect`** : c'est lui qui choisit entre `TIMEOUT` et `UNKNOWN`, et qui renseigne `tool_calls.effect`. T11 s'en sert aussi pour dire si un tour a agi.
- **`targets`** : `ToolResult.ok(text, targets)` pour l'audit (joueurs touchés).
- **`isAvailable(env)`** sert quand un outil dépend d'un composant : `sql` exige `env.journalAvailable`, et `delegate` un rôle d'assistant présent dans `env.workerRoles`.
- **Construction de la famille** :
  - `fun xTools(services): List<NarratorTool<*>>` est appelé à chaque `toolSetFor`, donc une fois par conversation ;
  - elle ne doit ni toucher `services.server` ni lire le monde.
  - `ToolCatalogTest` construit toutes les familles avec `TestServices()` (sans serveur Minecraft, Journal désactivé) et génère tous les schémas. Un outil mal déclaré y casse le build.
- **Tests** : les aides de `src/test/.../tool/TestTools.kt` (`TestTool`, `noArgsTool`, `toolUse(id, name, inputJson)`) et `ToolArgs.decode(MyArgs.serializer(), json)` servent à vérifier les messages sans serveur.

## Pour chaque tâche

- **T11** :
  - `ToolRunner(services)` est le `ToolExecutor`. Il ne lève jamais d'exception, sauf la `CancellationException` de son appelant.
  - Le `ToolSet` d'une conversation passe à la requête par `tools(toolSet.definitions)`.
  - Pour `acted`, on regarde `tools[name]?.effect` et l'absence de `is_error` sur le résultat.
- **T13, T14, T15, T16** : voir « Déclarer un outil » ci-dessus.
- **T17** :
  - la description de `sql` est le `SchemaDoc` et doit être déterministe, pour garder les mêmes octets d'une conversation à l'autre avec le même schéma ;
  - `sqlTools(services)` doit se construire avec un `DisabledJournal` ;
  - `isAvailable` vaut `env.journalAvailable`.
- **T19 et T20** :
  - appeler `ToolCatalog.toolSetFor(role, env, services)` une seule fois par conversation, et garder le résultat ;
  - `ToolEnv(journalAvailable = services.journal.available, workerRoles = …)`.
- **T20** :
  - l'énumération des rôles de `delegate` ne liste que les rôles câblés (`analyst` en M2) ;
  - `isAvailable` exige que le rôle soit dans `env.workerRoles`.
- **T22** : `PromptToolMentionsTest` peut appeler `ToolCatalog.toolSetFor(role, ToolEnv(true, setOf(Role.ANALYST)), TestServices())`.
