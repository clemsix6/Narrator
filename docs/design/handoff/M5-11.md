# Passation M5-11 : le moteur des modules

Vague C de M5 (`design/M5.md` §6.4 à §6.7, fiche M5-11 au §17.2). Les modules déployés tournent dans **une partie de
plus** du moteur des mécaniques de M4 : `ModuleEngine` (une `MechanicPart`) les mène, `ModuleBook` (le `ModuleControl`)
les déploie, les arrête et tient le coupe-circuit, `RunContext` est le `ModuleContext` de chacun, assemblé des vraies
pièces du SDK (M5-06, M5-07) et donné au module par l'hôte (M5-05). **Rien n'est encore câblé** dans le serveur :
`MechanicsService` et `ForgeSetup` sont à M5-21 (câblage exact plus bas). **En cas de contradiction avec `M5.md`, le
code et cette passation font foi** (`M5.md` a un encart « Passation M5-11 » et son §6.4, étape 8, est corrigé).

## Le moteur (`ModuleEngine`)

```kotlin
class ModuleEngine(
    services: NarratorServices, store: StateStore,
    threads: ModuleThreads,                 // un pour tout le moteur (M5-05) ; un seul appelant : le thread serveur
    runner: ActRunner,                      // EngineActRunner(actions) : les actes du moteur, outils des modules compris
    challenges: ChallengeControl,           // ceux du moteur (les défis jugés qu'un module arbitre)
    server: ModuleServer = GameModuleServer(services),
    clock: Clock = services.clock,
    leakWatch: LeakWatch = LeakWatch(clock),
    noteFault: (ModuleRun, Fault) -> Unit = { _, _ -> },   // la faute notée sur la version de l'arsenal
    area: (Entity) -> Boolean = { true },                  // les créatures dont il s'occupe (un GameTest donne sa zone)
) : MechanicPart
```

- **Un déploiement** = sa file d'actes (`ActQueue`) et ses créatures (`CreatureControl`) dès sa création, puis, une fois
  sa version là, son `RunContext` et son `ModuleHost` (`label` = `C-70 orbiting_chickens`, `onFault` → décision
  `mechanic fault` et `noteFault`). Tout appel du code du module passe par `queue.invocation(what) { … }` (ses actes
  partent ensemble, un acte du moteur) et par l'hôte : le constructeur et `start` par `ModuleHost.start(context)` (le
  contexte derrière les mandataires, jamais nu), `stop` par `ModuleHost.stop`, faits, minuteurs et rappels par
  `ModuleHost.call`. Pour que les actes du constructeur, de `start` et de `stop` soient regroupés comme les autres, le
  déploiement passe à la file une opération de l'hôte (`hosted`) que son `ModuleCall` exécute **à la place** d'un appel
  du corps : `ActQueue` n'a pas changé.
- **Après chaque appel** : `host.disabled` non nul → fin `disabled` ; `context.endAsked` non nul → fin `fulfilled`
  (`stop(ENDED)`), une fois l'appel rendu.
- **Chaque tick** (`everyTick`), déploiement par déploiement dans l'ordre de déploiement : les constructions de
  redémarrage revenues démarrent ; puis faits en file (`FactQueue.drain`, un appel par livraison), minuteurs dus
  (`Scheduler.advance` puis `next`, un appel chacun), rappels (`ActQueue.deliver`). Le travail d'un déploiement s'arrête
  dès qu'il finit. Tous les modules au-delà de `ForgeLimits.TICK_MS` (10 ms) dans un tick : un `WARN` par minute au plus,
  qui nomme le plus lent et compte les ticks lents depuis le précédent.
- **Chaque seconde** (`everySecond`) : échéance → `expired` ; `host.second()` (lenteur) ; `CreatureControl.sweep()` → faits
  `CreatureGone` aux déploiements abonnés ; la note en attente au Directeur ; `Storage` et compteurs (`acts`, `faults`)
  recopiés dans l'état **s'ils ont changé** ; faits perdus (`FactQueue.takeDropped`) → décision `facts_dropped` une fois
  par minute au plus ; la jauge d'**un** déploiement (chacun une fois par minute, toutes les 10 s quand ses appels ne
  mesurent pas l'allocation) avec les racines `handlers() + tasks() + callbacks()` ; `LeakWatch.check()` → décision
  `forge leak` (sujet : le libellé) ; et, si `threads.lost.stuck`, chaque déploiement est désactivé (faute `STUCK`,
  « stuck in second: the Forge is stuck: too many module threads were lost »).
- **Faits** (`onEvent`, sur le fil du bus) : `Facts.of` une seule fois, puis `offer` à chaque déploiement qui veut sa
  classe. `onMobLoad` : `ModuleCreatures.onMobLoad` (une créature d'un déploiement vivant lui revient, sinon elle est
  rendue), puis `Facts.appeared` seulement si un déploiement veut `CreatureAppeared`. `allowDeath` :
  `ModuleCreatures.allowDeath` (un passant est sauvé).
- **Situation** : `Modules: C-70 orbiting_chickens law Bartok (until 20:40) · C-77 statues plan referees C-75 (until
  21:20)`, 400 caractères (`ForgeLimits.MODULES_LINE`), `(+2 more)` au besoin ; les joueurs sont les valeurs des
  paramètres `PLAYER`/`PLAYERS` (inconnus tant qu'un redémarrage construit, la ligne dit alors `, starting again`).
- **Vues** (`views`, tout fil) : `ModuleView` avec `acts` (ceux d'avant le redémarrage + `queue.asked`), `faults`,
  `msPerSecond` (le temps de ses appels dans la dernière seconde, en ms, `Double`), `line` = sa ligne de situation.

### Les fins (§6.6)

`finish` (thread serveur) puis `close` (coroutine de `services.scope`, ou la coroutine de l'appelant pour `stop` et
`halt`) :

1. le `stop` du module, quand il a démarré et n'est pas désactivé, avec la raison de la fin (`context.stopping()` d'abord :
   ses actes `dropped`, ni minuteur ni abonnement, ni `end` ni note) ;
2. le contexte fermé (toutes les pièces : la file rend `dropped` ce qui attend) ;
3. hors de l'état ; ses créatures rendues (`releaseAll`) ; son chargeur lâché (`unload`) et surveillé (`LeakWatch`) ;
4. le canon résolu par `Source.ENGINE` (le tour et la conversation de qui l'a demandé), **puis** la décision
   `mechanic module_ended` (`detail.ending`), **puis** la ligne `MODULE` quand elle existe.

| Fin (`ModuleEnding`) | `stop` | Canon loi / plan, note | Ligne `MODULE` |
|---|---|---|---|
| `expired` | `EXPIRED` (sauf échu pendant l'arrêt : pas de `stop`) | `retired` / `expired`, `its time ran out` | `C-70 orbiting_chickens ended: its time is up (212 acts, 0 faults)` |
| `fulfilled` | `ENDED` | `retired` / `fulfilled`, le `why` du module (200) ou `it ended by itself` | `C-71 tag ended by itself: « … » (12 acts, 0 faults)` |
| `removed` | `STOPPED` | `retired` / `cancelled`, la note | opérateur : `C-70 orbiting_chickens ended: stopped by operator Clement (3 acts, 0 faults); « … »` ; Directeur : aucune |
| `disabled` | non | `retired` / `cancelled`, `disabled: <fault.text>` | `C-72 gravity_storm disabled: limit in timer: time budget at GravityStorm.java:41; ask the forger to fix it` ; au déploiement : aucune |
| `forge_off` | `FORGE_OFF` (sauf au démarrage) | `retired` / `cancelled`, `the Forge was switched off by an operator` | une pour tous : `the Forge was switched off by an operator: C-70, C-73 stopped` (ou `no module ran`) ; au démarrage : `the Forge is switched off (by Clement): C-70 did not start again` |
| `restart_failed` | non | `retired` / `cancelled`, `could not restart: <raison>` | `C-74 hot_cold could not restart: <raison>` |

Raison de la décision (et `ModuleView.line` rendue par `stop`) : `C-70 orbiting_chickens law expired, canon retired:
212 acts, 0 faults; « its time ran out »`, avec ` by operator Clement` / ` by the director (turn 43)` quand quelqu'un l'a
demandé. Les compteurs sont ceux d'**après** le `stop` du module (un acte demandé dans `stop` compte, mais ne part pas).

### Le redémarrage (§6.7)

- `started` : chaque `ModuleRun` de l'état devient un déploiement (file et créatures prêtes : les créatures déjà
  chargées lui reviennent dès ce moment, `ModuleCreatures.onMobLoad` sur toutes les entités de la zone) ; ceux qui ne sont
  ni échus ni sous coupe-circuit sont **construits à nouveau** (`Forge.build(module, version)`, hors du thread serveur).
- Au tick qui suit le retour : empreinte comparée (`built.entry.hash == run.hash`, sinon `restart_failed` : « the
  source of x v1 no longer matches the one deployed »), puis démarrage avec `restarted() == true` et son `Storage` ;
  décision `restarted` (`C-70 keeper v1 started again after a restart: 3 keys in its storage, 1 creatures of its own`).
- Construction refusée (`ForgeRejected`, `broken`…), paramètres illisibles, chargeur qui refuse : `restart_failed`.
  Une **faute** de son constructeur ou de `start` : `disabled` (c'est une faute du module, pas du redémarrage).
- Échu pendant l'arrêt, ou coupe-circuit posé dans l'état : fin à la **première seconde**, sans construction ni `stop`.
- L'arrêt du serveur (`stopping`) : `stop(SERVER_STOPPING)` de chaque module (ses écritures du `Storage` gardées), l'état
  gardé avec son `Storage` et ses compteurs, les actes en file perdus et comptés dans **une** décision `mechanic
  skipped` (`the server stops: 3 modules stopped until the restart (C-1, C-2, C-3), 0 acts in their queues dropped`),
  les chargeurs lâchés (pas surveillés), les créatures **laissées** dans le monde ; les coroutines des files annulées.
- `dropped(ids)` (la réconciliation) : le retrait sans `stop` ni canon ni décision.

## Le livre (`ModuleBook`)

`ModuleBook(services, store, engine, clock = services.clock)`, un verrou (déploiements, arrêts et coupe-circuit un à
un). **Ordre des refus** de `deploy` (le premier levé, `MechanicRejected`), textes testés :

1. Forge indisponible : `DENIED (forge_off): the Forge is unavailable: <raison>` ; coupe-circuit : `DENIED (forge_off): the
   Forge was switched off by Clement: <raison>` ; moteur arrêté : `DENIED (mechanics_off): the mechanics are unavailable:
   the engine is stopped`.
2. Version : `Invalid arguments: no module ducks in your arsenal; ready: …` ; `… has no version 7; its versions: v1
   ready` ; `DENIED (awaiting_approval): statues v2 waits for an operator's approval (/narrator forge approve statues 2)` ;
   `FAILED: lava v1 no longer compiles: <ArsenalEntry.problem>` ; `Invalid arguments: tag v1 was rejected by an operator;
   deploy another version`. Sans version : la dernière `ready`, sinon la raison de la plus récente.
3. Paramètres : `ParamCheck.check(entry.params, spec.params, server.params(caller))` (M5-06), ses textes.
4. Défi : `Invalid arguments: C-99 is not a running judged challenge` ; `… C-75 is refereed by C-70 (tag) already`.
5. Limite : `DENIED (module_limit): 4 modules run (C-70, …); stop one first` (`module runs` pour 1).
6. `Forge.build` : un `ForgeRejected` devient un `MechanicRejected` de mêmes règle, texte et `failed`.
7. Canon : `CanonDraft(LAW|PLAN, statement, quote, players = les joueurs des paramètres, importance 5, ACTIVE, mechanic =
   MODULE)` en `Source.DIRECTOR` (tour et conversation du `Caller`).
8. État et démarrage **dans une seule tâche du thread serveur** (écart : pas « au tick suivant », pas d'attente d'une
   seconde). Une faute au démarrage : fin `disabled` (canon résolu, décision, pas de ligne) et `FAILED: C-70 failed to
   start: exception in start: IllegalStateException: boom at Boom.java:7`. Un serveur qui s'arrête entre-temps : canon
   résolu `it never took effect: the server was stopping`, l'exception remonte (comme `RuleBook`).
9. Décision `mechanic started` : `C-70 greeter v1 law until 18:10: player bartok` (+ `; referees C-75`), le tour du
   `Caller`. La vue rendue a cette ligne.

`stop(ref, note, author)` : `Invalid arguments: C-70 is not a running module; running: …` sinon la fin `removed`.
`halt(reason, operator)` : refusé s'il est déjà posé ; pose `forgeHalt` **avant** d'arrêter quoi que ce soit (dans la
même tâche du thread serveur), finit chaque déploiement `forge_off`, écrit les canons et décisions, **une** ligne
`MODULE`, la décision `forge halted` (sujet : l'opérateur), et rend les vues arrêtées : rien ne tourne au retour.
`resume(operator)` : refusé sans coupe-circuit (`the Forge is not switched off: nothing to lift`) ; décision `forge
resumed` ; les modules arrêtés ne repartent pas.

## Le contexte (`RunContext`)

- Après `close`, **toute** méthode lève `ForgeRefusal` (« the deployment has ended… »), comme chaque pièce fermée.
- `log` : `INFO` au journal du tag `Forge`, `C-70 orbiting_chickens: <ligne échappée, 200>` ; 20 par minute (fenêtre fixe) ;
  les perdues comptées dans la ligne suivante (`(5 lines dropped before)`). Pas de décision (le volume).
- `tellDirector` : la première tout de suite, puis une toutes les 5 minutes ; la dernière en attente remplace les
  autres, comptées (`« note trois » (1 earlier note dropped: one every 5 minutes)`). Chaque note remise : une ligne
  `MODULE` `C-73 simon_says says: « … »` **et une décision `mechanic notified`** (le Chroniqueur la lit, comme le
  `notify` d'une règle : écart, ajout au §15). Une note pendant `stop` est perdue (sa fin est dite).
- `end(why)` : la première seule, ignorée pendant `stop` ; sans texte : `it ended by itself`.
- `random()` : `java.util.Random` semé par le déploiement (`id`, `createdAt`), le même après un redémarrage.

## Écarts et décisions

1. **Démarrage dans la tâche du serveur** du déploiement (ci-dessus) : `ForgeLimits.START_WAIT_MS` n'est pas utilisé.
2. **`ModuleServer`** : une petite interface (exécuter sur le thread serveur, y attendre un bloc, le `World`, la dimension
   d'un joueur, la vérification des paramètres) que le serveur implémente (`GameModuleServer`) et que les tests unitaires
   remplacent (ils n'ont pas de serveur). C'est le patron de `RuleTags`/`RuleIds` de M4.
3. **Les fins sont au moteur** (canon, décision, ligne), le livre ne fait que valider, déployer et commander : le moteur
   finit seul la plupart des déploiements (échéance, fin, faute, redémarrage), sans référence circulaire.
4. **Une seule décision par fin** (`module_ended`) ; pas de `mechanic disabled` séparée (le §3.7 en parlait) : la
   désactivation est la fin `disabled`, précédée de ses décisions `fault`.
5. **Pas de `stop`** pour un déploiement qui n'a pas démarré pendant ce passage du serveur (échu pendant l'arrêt,
   coupe-circuit au démarrage, construction ratée) ; le tableau du §6.6 disait `EXPIRED` « arrêt du serveur compris ».
6. **Forge bloquée** : traitée par le moteur à sa seconde (tous désactivés) ; M5-21 n'a qu'à rendre la Forge
   indisponible et écrire `forge stuck`.
7. **`noteFault`** : un paramètre du moteur, `(ModuleRun, Fault) -> Unit`, sans effet par défaut, faute de méthode dans
   l'interface `Arsenal` (M5-09) ; M5-10 tranche où elle vit, M5-21 la branche (voir plus bas). Le texte à noter est
   `fault.text` (`limit in timer: time budget at TagGame.java:41`).
8. **Jauge** : un déploiement par seconde, au plus tôt 10 s après son démarrage, puis toutes les minutes si ses appels
   rapportent une allocation (`Called.allocated >= 0`), sinon toutes les 10 s.
9. **Décision `skipped`** à l'arrêt du serveur (comme le moteur des règles) pour compter les actes perdus.
10. Le texte de `halt` déjà posé : `the Forge is already switched off (by Clement): /narrator forge on lifts it` (la
    commande ne l'appelle pas dans ce cas, M5-14).

## Ce que les tâches suivantes doivent savoir

### M5-21 (l'assemblage) : le câblage attendu

Dans `MechanicsService` :

```kotlin
// la Forge (M5-10) expose le LostThreads commun au moteur et au banc, et la note des fautes
val moduleThreads = ModuleThreads(lost = <le LostThreads de la Forge>)
private val moduleParts = ModuleEngine(
    services, store, moduleThreads, EngineActRunner(actions), challenges /* le ChallengeControl de ce service */, clock = clock,
    noteFault = { run, fault -> <la Forge>.noteFault(run.module, run.version, fault.text) },
)
override val modules: ModuleControl = ModuleBook(services, store, moduleParts, clock)
// les parties : challenges, duels, bets, bars, rules, puis moduleParts
// TOOLS / engineTools : + moduleOnlyTools() (hud, place_blocks, creature_attack) ; les outils qu'un module appelle sont
//   say, show_title, hud, play_sound, particles, fireworks, lightning, explosion, apply_effect, set_attribute, launch,
//   teleport, spawn, punish, place_blocks, creature_attack (passation M5-07)
// stop() : engine.stop() (les modules s'arrêtent : SERVER_STOPPING), puis moduleThreads.close()
```

- **Gardez la partie des modules même avec `forge.enabled = false`** (ou la Forge en panne) : les déploiements de l'état
  y finissent `restart_failed` (`the Forge is unavailable: …`), leurs créatures sont rendues et leurs lignes du canon
  résolues. Sans partie, `Reconcile` garde désormais leurs lignes ouvertes (leurs ids sont dans l'état) et rien ne les
  fermerait.
- `LostThreads(onStuck = …)` : rendre la Forge indisponible, décision `forge stuck`, message aux opérateurs ; le moteur
  désactive lui-même les modules à sa seconde suivante.
- `ModuleHost.preload()` au démarrage de la Forge, hors du thread serveur (M5-05).
- `ModuleControl.leaks` vient du `LeakWatch` du moteur (une instance par moteur).
- Démarrage réel (votre critère) : un module qui redémarre retrouve ses créatures **dès** `started` (avant d'être
  reconstruit) ; ses minuteurs repartent de zéro (`restarted()`).

### M4-LEFTOVERS (fusionné) et les créatures des modules

Le moteur ne lit jamais la marque `NarratorMob.SPAWN` : il s'appuie sur `ModuleCreatures` (cibles, `allowDeath` d'un
passant) et sur l'exception de `CreatureShield.bound` (une créature qui porte la marque d'un module n'est liée à aucun
joueur, même si `spawn` l'a marquée `spawn`). Les créatures retrouvées au redémarrage portent leur tag de module (tag
persistant) : l'exception vaut pour elles dès leur chargement. Entre la naissance d'une créature hostile d'un `spawn` et
son adoption par le module (le règlement de l'acte, au tick suivant), elle est celle du joueur visé, comme toute
créature de `spawn`.

### M5-15 à M5-17 (l'arsenal de départ)

- Les minuteurs comptent les **ticks du moteur** ; `ctx.now()` est l'horloge du moteur.
- Finir après une victoire : `game().win(…).then(o -> ctx.end(…))` (passation M5-07 : `end` ferme la file, une fin de défi
  encore en file serait `dropped`).
- `restarted()` : `Storage` rendu, créatures revenues (`creatures().own()` dès `start`), ni abonnements ni minuteurs.
- `log` : 20 lignes par minute ; `tellDirector` : une note toutes les 5 minutes, la dernière gardée.
- Un appel qui dépasse 20 ms deux fois en dix minutes, ou qui est abandonné, désactive le module ; plus de 50 ms de code
  par seconde cinq secondes de suite aussi.

### M5-18 (la batterie)

- Déjà couverts ici : boucle sans fin dans un minuteur (deux fautes *limite* → `disabled`, sans `stop`), lenteur sur cinq
  secondes, appel abandonné (hachage de L1) → `disabled` et `forge leak` tant que le fil perdu tient ses classes, Forge
  bloquée, faits au-delà de 256 par tick (`facts_dropped`), journal en rafale, `tellDirector` en rafale.
- À attaquer : un module qui appelle `end` puis lève (la fin `fulfilled` gagne-t-elle sur la faute ? aujourd'hui la
  faute est regardée d'abord), un `stop` qui boucle (une faute de `stop` compte, la fin a lieu quand même).

### M5-12, M5-14

- `ModuleView.line` : la ligne de situation (`list`), la ligne du déploiement (`deploy`), la raison de la fin (`stop`).
- `halt` pose l'interrupteur et arrête tout avant de rendre ; `resume` le lève ; décisions `forge halted`/`resumed`.
