## `run_command` : le chemin d'une commande

Tout se passe sur le thread serveur, dans un seul `ctx.onServer { }` :

1. `/` en tête retiré (`Commands.trimOptionalPrefix`) ; `as_player` doit être en ligne, sinon `INVALID` avec la liste des joueurs en ligne.
2. **Source** : `CommandSourceStack(capture, point d'apparition, Vec2.ZERO, findRespawnDimension(), GAMEMASTER, "Narrator", server)`, comme `createCommandSourceStack()` mais au niveau gamemaster (javap). La sortie va dans `CapturingSource` (`shouldInformAdmins() = false`, jamais `withSuppressedOutput()`). Avec `as_player` : `withEntity`, `withPosition`, `withRotation`, `withLevel` du joueur. La permission reste gamemaster, jamais celle du joueur. Un `withCallback` compte chaque exécution (une par entité d'un `execute as …`).
3. **Analyse** avec cette même source (`dispatcher.parse`).
4. **`CommandPolicy.check(parse)` d'abord**, comme le demande T09b : une commande interdite est dite interdite, même mal formée (`fill three`). Le refus écrit une décision `guard denied` (sujet `run_command`, `detail = {rule, command}`), comme `GuardsImpl.hostile`.
5. **Syntaxe** : commande inconnue (aucun nœud reconnu), puis `Commands.getParseException` **et** `ContextChain.tryFlatten` (une commande incomplète passe le premier test). Erreur → `INVALID` avec le message, la position (`at character N: …<--[HERE]`) et l'usage exact (`getSmartUsage` du nœud le plus profond atteint, derrière `execute … run` compris), 20 lignes au plus.
6. **Limite de 6 commandes par tour**, comptée seulement ici : une commande refusée ou invalide ne compte pas. Clé `(conversationId, turnId)`, dans l'instance de l'outil (un `ToolSet` par conversation).
7. **Exécution** par `server.commands.performCommand(parse, texte)`, hors de tout contexte de commande, donc immédiate (vérifié : les rappels et la sortie sont là au retour).

## Écarts par rapport au design

1. **`command_help` fait plus que `getSmartUsage`** :
   - il accepte un début de commande quelconque, arguments compris (`execute as @a run particle`), comme `/help` : l'usage est celui du dernier nœud analysé, et ce qui n'a pas été compris est signalé ;
   - **commande vide** : la liste des commandes que `run_command` accepte (visibles pour la source et permises par la politique). En 26.3 et sans autre mod : 16 commandes ;
   - une commande ou une branche interdite est dite telle : `DENIED (forbidden_command)` pour la commande demandée, ` (forbidden)` en fin de ligne pour une branche littérale interdite (`execute store`, `execute summon`, `execute if function`) ;
   - commande inconnue : `INVALID` avec les 5 commandes acceptées les plus proches.
2. **Suggestions** : pour une commande inconnue, `run_command` comme `command_help` ne proposent que des commandes acceptées (`closestIds` de T14 sur la liste ci-dessus), jamais une commande interdite.
3. **La limite de 6 par tour ne compte que les exécutions** : une commande invalide ou refusée ne consomme rien, pour que le modèle puisse corriger sa syntaxe. Règle `command_limit` (`RunCommandTool.LIMIT_RULE`).
4. **Statuts** : une commande qui a tourné et dont toutes les exécutions ont échoué donne `FAILED` (le texte donne les lignes d'erreur du jeu) ; une réussite au moins donne `ok`. Un `execute as …` qui ne trouve personne donne `ok: ran for nothing …`. La sortie est plafonnée à 20 lignes (`… (+N lines)`), puis à 8 000 caractères par `ToolRunner`.
5. **Décision `guard denied`** pour chaque refus de `CommandPolicy` (suggestion de T09b). Pas de décision pour la limite par tour.
6. **`sql`** :
   - description = **`SchemaDoc.text` exactement**, sans phrase ajoutée (test) ;
   - `max_rows` : 1 à 200, 50 par défaut ;
   - délai de l'outil = `(max(journal.sqlTimeoutSeconds, 15) + 3) s`, pris à la construction (une fois par conversation). À l'exécution, le délai SQL est `journal.sqlTimeoutSeconds` pour tout rôle sauf l'Analyste (15 s), **plafonné** à ce que la construction a prévu : un `/narrator reload` qui augmente le délai du Directeur ne vaut qu'à la conversation suivante ;
   - `Rows` → `ok`, `Rejected` → `INVALID`, `Failed` → `INVALID` si le Journal est ouvert (erreur de la requête), `FAILED` sinon, `TimedOut` → `TIMEOUT: the query did not finish within N s: aggregate, filter or add LIMIT`.
7. **`remind_me`** : plafond appliqué par l'outil sur `director.status().reminders` avant `scheduleReminder` ; règle `reminder_limit` (`RemindMeTool.LIMIT_RULE`). La note est rognée ; une note vide est `INVALID`. Un échec de `scheduleReminder` (serveur qui s'arrête, Directeur désactivé) donne `FAILED: no reminder set: <raison>`. L'heure affichée est calculée par l'outil (`clockTime`, fuseau de l'horloge du moteur) ; elle peut différer de quelques millisecondes de l'échéance du Directeur.
8. **Textes de 26.3** vérifiés en jeu : `execute if entity` répond `Test passed. Count: 1` (point, majuscule), `execute if block` `Test passed` / `Test failed`.

## Limites

- **Commandes d'autres mods** : une commande inconnue de la politique est acceptée (règle de T09b) ; un alias qui appelle `dispatcher.execute(…)` au lieu d'une redirection échappe à l'analyse.
- **`particle`** reste sans borne sur `count` (T09b, écart 6) ; je ne l'ai pas bornée : la limite de 6 commandes par tour borne déjà la répétition.
- **`recipe give @a *`** est accepté (revue de T09b) : il débloque toutes les recettes des joueurs, sans retour possible. C'est un choix de la politique, pas de l'outil ; à revoir si le propriétaire le juge gênant.
- Un GameTest de T09b (`the_narrators_zombie_never_breaks_adoor`) a échoué une fois sur quatre lancements pendant cette tâche (« the ordinary zombie breaks its door on tick 1202 », pour une limite de 1 200) : c'est un test sensible au temps, sans lien avec T17. Les lancements suivants sont verts.
