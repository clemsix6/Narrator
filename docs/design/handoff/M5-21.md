## Le câblage

### La Forge (`createForge`)

```
createForge(services, tellOperators)                  thread serveur, SERVER_STARTED, après la mémoire, avant les mécaniques
 ├─ forge.enabled faux                → DisabledForge("forge.enabled is false")            (INFO)
 ├─ ForgeService(services) lève
 │   ├─ LinkageError (NoClassDefFoundError : ECJ absent du class path)
 │   │                                → DisabledForge("ECJ is missing: <classe>")           (ERROR)
 │   └─ Exception                     → DisabledForge("it could not start: <message>")      (ERROR)
 ├─ forge.start() lève                → forge.stop(), DisabledForge("it could not start: …")
 └─ sinon le ForgeService, démarré (ForgeService.start dans services.scope : arsenal lu, ModuleHost.preload sur
    Dispatchers.IO, modules de départ construits, puis versions forgées vérifiées en tâche de fond), et son guet
```

- **Le guet** (`watch`, **remplacé depuis par le rappel `onUnavailable` de `ForgeService` : voir « Après M5-LOAD »**) : une coroutine de `services.scope` regarde `forge.available` une fois par seconde ; quand la
  Forge tombe (compilateur bloqué, ou trop de fils des modules perdus : `LostThreads` de la Forge), elle écrit un `WARN`
  et envoie **une fois** aux opérateurs en ligne la ligne jaune `[Narrator] the Forge is unavailable until the server
  restarts: <raison>` (`NarratorRuntime.tellOperatorsOnline`, la même que les pannes du Journal). Rien quand elle tombe
  parce que le serveur s'arrête (phase `STOPPING`). La décision `forge stuck` et l'indisponibilité sont déjà le fait de
  `ForgeService` (M5-10) ; la désactivation des modules, celui du moteur à sa seconde (M5-11).
- **La ligne `ready`** (`forgeState`) : `forge on` ; `forge switched off by Clement` quand le coupe-circuit est posé dans
  l'état du monde ; `forge off (<raison>)` (et `, switched off by …` s'il y a les deux). La Forge démarrant hors du
  thread serveur, la ligne `the Forge is ready in 672 ms: ECJ 3.46.100, 7 of 7 built-in modules built, 0 forged
  versions` vient juste après (moins d'une seconde).

### Les mécaniques (`MechanicsService`)

```kotlin
class MechanicsService(
    services, store, ids, tags = ServerRuleTags(services), clock = services.clock,
    lostThreads: LostThreads = (services.forge as? ForgeService)?.lostThreads ?: LostThreads(),   // M5-10
    moduleServer: ModuleServer = GameModuleServer(services),                                      // les tests unitaires donnent le leur
)
internal val actions = EngineActions(services, engineTools(services))      // TOOLS : règles, enjeux, punish, + hud, place_blocks, creature_attack
override val challenges: ChallengeControl = object : ChallengeControl { … } // déclaré avant la partie des modules, qui le reçoit
internal val moduleThreads = ModuleThreads(lost = lostThreads)             // nom narrator2-module-N, un pour tout le moteur
internal val moduleParts = ModuleEngine(
    services, store, moduleThreads, EngineActRunner(actions), challenges, server = moduleServer, clock = clock,
    noteFault = { run, fault -> services.forge.noteFault(run.module, run.version, fault.text) },
)
internal val engine = Engine(services, store, [challenges, duels, bets, bars, rules, moduleParts], clock)
override val modules: ModuleControl = ModuleBook(services, store, moduleParts, clock)
stop()     : engine.stop() (les modules : stop(SERVER_STOPPING), état gardé), puis moduleThreads.close(), puis isDueling
starting() : un démarrage raté arrête aussi moduleThreads
```

- **La partie des modules est là quelle que soit la Forge** (exigence de M5-11) : avec un `DisabledForge`, chaque
  déploiement de l'état finit `restart_failed` à son premier tick (`could not restart: the Forge is unavailable:
  forge.enabled is false`), canon résolu, créatures rendues ; `deploy_module` est refusé `DENIED (forge_off): the Forge
  is unavailable: …` par le `ModuleBook`. Testé (`MechanicsServiceTest`).
- **Fils** : le `ModuleThreads` du moteur partage le `LostThreads` du `ForgeService` (le banc aussi) : un seul plafond de
  deux fils perdus pour toute la Forge. Sans `ForgeService`, un `LostThreads` à lui (aucun module ne se construit de
  toute façon). Au déchargement d'un module, `ModuleHost.unload` renouvelle le fil (`ModuleThreads.renew`, FLAKY-4) ;
  à l'arrêt, `MechanicsService.stop` le ferme (le fil né du dernier `renew` mourrait sinon parqué : vérifié par mutation).
- **Outils des actes** : `TOOLS` = `RuleTargets.ALLOWED` + les outils des récompenses + `punish` + `moduleOnlyTools()`
  (noms). `engineTools` construit aussi `moduleOnlyTools()` ; `ForgeService.engineDryCheck` (le banc) déduplique, il
  vérifie donc exactement le même ensemble que le moteur. Testé : chaque outil d'acte du banc (`BenchImpl.TOOLS` moins
  `game`) est un outil du moteur.
- **Ce qui n'a rien demandé** : `Workers` offre le Forgeron dès que la Forge est disponible (M5-13), `Chapters` et le
  briefing lisent `forgeAvailable` (M5-12), les commandes (`ForgeCommands`) lisent `services.forge` et
  `mechanics.modules` (M5-14), le gardien du moteur coupé rend déjà les créatures des modules (M4-FIX-H, M5-07).

### Ordre de démarrage et d'arrêt

```
SERVER_STARTED (thread serveur, NarratorRuntime.wire)
  Journal → bus → états des joueurs → garde-fous → Observateur → réflexes → travailleurs → mémoire
  → Forge   createForge : ForgeService construit, start() lancé dans services.scope (hors du thread serveur), guet lancé
  → mécaniques  createMechanics : MechanicsService (6 parties) puis Engine.start :
                 Reconcile.startup, started de chaque partie — ModuleEngine.begin : chaque déploiement de l'état devient
                 un Deployment, sa construction lancée (Forge.build attend la fin du démarrage de la Forge), les
                 créatures déjà chargées rendues à leur déploiement — puis l'abonné du bus
  → Directeur
  → ligne « ready … · forge on|switched off by …|off (…) »
  … au tick qui suit chaque construction revenue : le module redémarre (restarted(), Storage), décision restarted

SERVER_STOPPING (ShutdownSequence.begin, inchangée depuis M5-01)
  phase STOPPING → mécaniques (MechanicsService.stop : Engine.stop → ModuleEngine.stopping : stop(SERVER_STOPPING) de
  chaque module, Storage et compteurs gardés dans l'état, créatures laissées, décision skipped ; puis
  moduleThreads.close()) → Forge (ForgeService.stop : compilateur arrêté, démarrage et bancs annulés) → mémoire →
  travail en cours annulé (le guet et le démarrage de la Forge compris) → abonnements du Directeur
SERVER_STOPPED : Observateur, bus, Journal, clients
```

## Décisions et écarts

1. *(remplacé, voir « Après M5-LOAD »)* **Le message aux opérateurs passe par un guet** (une coroutine, une lecture de `forge.available` par seconde) dans
   `ForgeSetup.kt`, et non par un rappel dans `ForgeService` : `ForgeService.kt` est à M5-LOAD pendant cette tâche. Il
   couvre les deux chutes (compilateur, fils perdus). Si l'on veut un rappel direct, ajouter un `onUnavailable` au
   constructeur de `ForgeService` et retirer le guet.
2. **`lostThreads` par défaut** : `(services.forge as? ForgeService)?.lostThreads` dans le constructeur de
   `MechanicsService` (l'interface `Forge` n'expose pas ses fils, et ne le doit pas).
3. **La ligne `ready`** dit aussi le coupe-circuit (`forge switched off by Server`) : c'est l'état réel après un
   `forge off` et un redémarrage.
4. **Un GameTest, dans un lot à lui** (`forge_assembly`) : il tire l'interrupteur du serveur, que lisent les outils du
   Forgeron des tests du lot `forge` (`ForgeServiceGameTests`) ; et le gardien d'un moteur coupé du lot `assembly` rend
   au chargement les créatures des modules. Un seul test, séquentiel, parce que les tests d'un lot tournent ensemble et
   que l'interrupteur change le nombre d'outils.
5. **`ForgeContractsGameTests`** perd son test « Forge coupée, 44 outils » : il ne pouvait plus passer, et le nouveau
   GameTest vérifie l'inverse.
6. **`abandon()`** (un démarrage du Narrateur raté à mi-chemin) arrête la Forge si elle a été créée : son fil de
   compilateur ne reste pas jusqu'à la fin de la JVM.
7. **`createForge(…, make)`** : la fabrique du service est un paramètre, pour tester les trois refus sans retirer ECJ.

## Après M5-LOAD (M5-21b, 21/10/2026)

`git merge main` (`a1a2b74`, M5-LOAD fusionné ; avance rapide). Puis, à la demande du superviseur :

1. **Le guet est remplacé par le rappel de la Forge** : `createForge` passe `onUnavailable` au constructeur de
   `ForgeService` (`make: (services, onUnavailable) -> ForgeService`). `ForgeService` l'appelle **une fois**, avec la
   raison, quand la Forge devient indisponible pendant le jeu (compilateur bloqué, trop de fils perdus, arsenal illisible au
   démarrage), **jamais** à `stop()`. Le message ne change pas : `WARN` au journal `Forge` et ligne jaune
