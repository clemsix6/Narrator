## 2. Runtime et cycle de vie (point 8 de la relecture de M0)

### 2.1 Trois durées de vie

| Vit avec… | Composants | Créé / détruit |
|---|---|---|
| **le mod** (JVM) | enregistrement des hooks Fabric, des commandes et des types de pièces jointes (Data Attachments) | Une fois, dans `Narrator2.onInitialize`. Les hooks renvoient vers `NarratorRuntime.current` et ne font rien s'il est nul ou arrêté. |
| **le serveur** (`NarratorRuntime`) | `EventBus`, `Journal`, `PlayerStates`, état de l'Observateur (échantillonneur, agrégateurs), `Guards`, `Reflexes`, `Director`, `Workers`, `ToolCatalog`, `runtime.scope` | `SERVER_STARTED` → `SERVER_STOPPED`. **Jamais reconstruits par `/narrator reload`.** |
| **les réglages** (`Settings`) | `NarratorConfig`, `Prompts`, `UiTexts`, `ClaudeClient`, `JevClient` | Remplacés **atomiquement** par `/narrator reload` (`SettingsHolder.swap`). |

`NarratorRuntime` garde son nom (M0 et les GameTests l'utilisent) mais change de rôle : il ne contient plus la config,
il tient un `SettingsHolder`. Il implémente l'interface `NarratorServices` (T01, `runtime/NarratorServices.kt` :
`server`, `scope`, `phase`, `clock`, `dataDir`, `settings`, `bus`, `journal`, `trace`, `transcripts`, `players`,
`guards`, `reflexes`, `director`, `workers`), que consomment les outils, l'`AgentLoop` et les tests : aucun composant
ne dépend de la classe concrète, et les tests unitaires montent de faux services. `trace` est un `TraceSink` (§5.5) :
en production c'est le `Journal` lui-même, dans les tests un sink en mémoire.

```kotlin
/** Life cycle of the Narrator on a server. */
enum class Phase {
    STARTING,   // components are being created
    RUNNING,    // everything runs
    STOPPING,   // no new work: no wake-up, no task, no tool call; facts are still journaled
    STOPPED,    // everything is closed
}
```

`Phase` (T01, `runtime/NarratorServices.kt`) n'a que ces quatre valeurs : pas de distinction entre un M0 « démarré »
et un M1/M2 « en service », le passage `RUNNING` se fait une seule fois au §2.2 point 5.

```kotlin
/** Everything reloadable. Immutable; replaced as a whole by /narrator reload. */
class Settings(
    val config: NarratorConfig,
    val prompts: Prompts,
    val ui: UiTexts,
    val claude: ClaudeClient?,   // null when NARRATOR_LLMGW_KEY is missing: the Director stays asleep
)

class SettingsHolder(initial: Settings) {
    fun get(): Settings                       // volatile read, any thread
    /** Installs [next]; the previous clients are closed once their calls in flight are over. */
    fun swap(next: Settings): Settings
}

object SettingsLoader {
    /** Loads and validates config, prompts and UI texts; builds the clients. Throws on invalid input. */
    fun load(configDir: Path, env: (String) -> String? = System::getenv, transcripts: Transcripts): Settings
}
```

`Settings` livré par T01 (`runtime/Settings.kt`, squelette repris par T02) n'a pas encore de champ `jev` : T10 l'ajoute
(`val jev: JevClient?`, nul quand `jev.enabled = false` ou que `TYPESAFE_API_KEY` est absente) en même temps que
`reflex/JevClient.kt`. `SettingsLoader` reste à écrire par T02 ; `SettingsHolder.swap` rend bien les anciens réglages
sans fermer leurs clients, comme prévu.

Règles de lecture : un composant lit `settings.get()` **au moment où il s'en sert** (jamais de copie longue durée),
sauf la conversation du Directeur, dont le prompt système et les outils sont figés pour le chapitre (§12.10).

### 2.2 Démarrage (`SERVER_STARTED`)

1. `SettingsLoader.load`. En cas d'échec : log `ERROR`, réglages **par défaut** pour le Journal et l'Observateur, et
   Directeur désactivé (`director.state = DISABLED`) jusqu'à un `/narrator reload` réussi. **Les faits sont toujours
   journalisés**, même avec une config cassée.
2. `Journal` : ouverture synchrone de DuckDB (quelques centaines de ms, au démarrage seulement ; ce n'est pas du jeu),
   migrations, vues, amorçage des identifiants (§5.4). Échec → `DisabledJournal` (qui ne fait que logger) et les outils
   qui en dépendent (`sql`, `delegate` vers l'Analyste) ne sont pas proposés au modèle (§8.6).
3. `EventBus(firstEventId = journal.nextIdSeed(EVENT))`, abonnement asynchrone du Journal.
4. `PlayerStates`, état de l'Observateur, `Guards` (abonnés synchrones), `Reflexes`, `Workers`, `Director` (lancé en
   état `IDLE`, ou `DISABLED` sans client Claude ; aucun chapitre n'est ouvert : le premier s'ouvre au premier réveil).
5. `phase = RUNNING`.

### 2.3 Rechargement (`/narrator reload`)

1. `SettingsLoader.load` s'exécute dans `runtime.scope` (`Dispatchers.IO`), jamais sur le thread serveur ; la réponse
   revient à l'opérateur par `server.execute`.
2. Si le chargement échoue, les anciens réglages restent actifs et l'erreur est renvoyée à l'opérateur.
3. Sinon `swap`. Les appels en cours finissent sur l'ancien `ClaudeClient`, qui est fermé quand son compteur d'appels en
   vol tombe à zéro (`closeWhenIdle()`, ajouté par T02).
4. `director.onSettingsChanged(old, new)` : si le texte du prompt du Directeur ou de l'Analyste a changé, ou si
   `director.operatorChannel` a changé, le chapitre courant est **marqué à clore** au prochain moment calme (§12.10).
   Les autres réglages (chaos, délais, seuils) s'appliquent immédiatement puisqu'ils sont lus à l'usage.
5. Décision `engine_decisions(kind = 'reload')`.

### 2.4 Arrêt ordonné

`SERVER_STOPPING` se déclenche **avant** que le serveur sauve et déconnecte les joueurs ; `SERVER_STOPPED` **après**
(`OBSERVER_API.md` §1.5). D'où deux étapes :

**`SERVER_STOPPING` → `runtime.beginShutdown()`**
1. `phase = STOPPING`. Plus aucun travail nouveau : le Directeur n'accepte plus de réveil, `Workers` refuse les tâches,
   `ToolRunner` répond `FAILED: server is stopping` sans exécuter.
2. Annulation de la coroutine du Directeur et des assistants (`Job.cancel()`), puis `joinAll` avec un délai de 2 s.
   `ClaudeClient` ferme les flux (acquis M0 n°3) : **rien n'est ajouté** aux conversations. Le tour en cours est
   enregistré `outcome = 'cancelled'` et le chapitre `end_reason = 'shutdown'`, sans résumé (pas d'appel réseau à
   l'arrêt ; le briefing suivant compense, §12.11).
3. Désabonnement de la saillance. Le Journal, `PlayerStates` et l'Observateur **restent abonnés** : les `LEAVE`
   déclenchés par `PlayerList.removeAll()` doivent être journalisés.

**`SERVER_STOPPED` → `runtime.finishShutdown()`**
1. L'Observateur vide ses agrégateurs (dégâts, ramassages, artisanat, explosions) et publie les lignes en attente.
2. `bus.close()` : toute publication ultérieure est ignorée (et comptée).
3. `journal.close(10 s)` : vidage de la file, `flush` des appenders, sessions encore ouvertes fermées avec
   `end_reason = 'server_stop'`, `CHECKPOINT`, fermeture des connexions puis de la base. Au-delà de 10 s, le reste est
   perdu et compté dans le log.
4. Fermeture de `ClaudeClient` et `JevClient`, `scope.cancel()`, `phase = STOPPED`, `NarratorRuntime.current = null`.

Au démarrage suivant, le Journal répare ce qui est resté ouvert après un crash : sessions sans `left_at`
(`end_reason = 'recovered'`, `left_at` = dernier événement du joueur), tours et conversations sans fin
(`outcome = 'interrupted'`, `end_reason = 'interrupted'`).

## 3. Modèle d'événements (contrat partagé M1, M2, M4, M5)

Paquet `io.github.clemsix6.narrator2.event`, fichiers `Refs.kt`, `GameEvent.kt`, `EventCatalog.kt` (T01).

### 3.1 Principes
- Un événement est un **fait immuable** construit sur le thread serveur à partir de valeurs simples : jamais de
  référence à un `ItemStack`, une `Entity`, un `ServerPlayer` ou un `BlockState` (`OBSERVER_API.md` §1.1).
- **Identité** : un joueur est un `PlayerRef(uuid, name)` ; le nom est celui du moment. Tout est indexé par UUID.
- **Lieu** : `Pos(dim, x, y, z)` en coordonnées de bloc, `dim` = identifiant complet (`minecraft:the_nether`).
- **Identifiants de jeu** : chaînes complètes (`minecraft:diamond_ore`), obtenues par les helpers de
  `observer/GameIds.kt` (T01) qui reprennent `OBSERVER_API.md` §1.4.
- L'`id`, l'horodatage et le temps de jeu sont posés par le bus dans l'**enveloppe**, pas par l'Observateur.
- Une seule source par type d'événement (`OBSERVER_API.md` §1.6).

```kotlin
data class PlayerRef(val uuid: UUID, val name: String)
data class Pos(val dim: String, val x: Int, val y: Int, val z: Int)
/** Another entity: a mob (type, optional custom name) or a player. */
data class EntityRef(val type: String, val uuid: UUID?, val name: String?, val player: PlayerRef? = null)
data class ItemCount(val item: String, val count: Int)

/** Assigned by the bus: global monotonic id, wall-clock epoch millis, overworld game time. */
data class Envelope(val id: Long, val ts: Long, val gameTime: Long, val event: GameEvent)

sealed interface GameEvent {
    /** Journal type, e.g. "block_break" (see EventCatalog). */
    val type: String
    /** The acting player, if any. */
    val player: PlayerRef?
    val pos: Pos?
}
```

## 4. Le bus d'événements

Fichier `event/EventBus.kt` (T01).

```kotlin
class EventBus(
    private val clock: Clock,
    private val gameTime: () -> Long,      // TickClock.gameTime, a volatile updated at END_SERVER_TICK
    firstEventId: Long,
) : AutoCloseable {
    /** Stamps and delivers [event]. Never blocks. Returns null once the bus is closed. Any thread. */
    fun publish(event: GameEvent): Envelope?

    /** Inline delivery on the publishing thread (the server thread in practice). Handlers must take < 0.1 ms. */
    fun subscribeSync(name: String, owner: String, filter: (GameEvent) -> Boolean, handler: (Envelope) -> Unit): Subscription

    /** Buffered delivery: the subscriber drains [AsyncSubscription.events] at its own pace. */
    fun subscribeAsync(name: String, owner: String, capacity: Int, filter: (GameEvent) -> Boolean): AsyncSubscription

    /** Removes every subscription of [owner] (a Forge module, a mechanic, a test). */
    fun unsubscribeOwner(owner: String)

    fun stats(): List<SubscriberStats>     // name, owner, delivered, dropped, failures, queued
    override fun close()
}

interface Subscription : AutoCloseable { val name: String; val owner: String }
interface AsyncSubscription : Subscription { val events: ReceiveChannel<Envelope> }
data class SubscriberStats(val name: String, val owner: String, val delivered: Long, val dropped: Long, val failures: Long, val queued: Int)
```

Règles :
- **Identifiants** : `AtomicLong` amorcé par le Journal (`max(id) + 1` sur `events`, `chat` et `private_messages`,
  §5.4). Les messages de chat et les messages privés partagent la séquence des événements.
- **Ordre** : l'ordre de publication est conservé pour chaque abonné (le thread serveur publie presque tout).
- **Filtre** : évalué sur le thread de publication ; il doit être trivial (`is`, comparaison de type).
- **Synchrone** : le gestionnaire s'exécute dans `publish`. Une exception est capturée, comptée et loguée au plus une
  fois par minute et par abonné ; elle n'interrompt ni la publication ni les autres abonnés. Utilisateurs en M2 :
  `PlayerStates` (mort, connexion) et `Guards` (attribution des morts). En M4, le moteur de mécaniques ; en M5, les
  modules de la Forge qui n'ont besoin que de faits.
- **Asynchrone** : `Channel(capacity)` avec `trySend`. File pleine → l'événement est **perdu pour cet abonné seulement**,
  compteur `dropped`, `WARN` au plus une fois par minute, et décision `journal_health` au bilan suivant. Capacités :
  Journal 65 536, saillance 8 192.
- **Désabonnement** : `Subscription.close()` ou `unsubscribeOwner(owner)` ; un canal asynchrone fermé est vidé puis
  abandonné par son consommateur.
- **Fermeture** : `close()` ferme tous les canaux ; `publish` renvoie `null` et incrémente `closedDrops`.
- **Ce que le bus n'est pas** : un mécanisme d'interception. Annuler des dégâts ou modifier un projectile avec les objets
  du jeu relève des crochets de la Forge (M5, `ARCHITECTURE.md` §10.2.3), qui auront leur propre contrat. Le bus ne
  transporte que des faits.

Tests (T01) : ordre, identifiants croissants depuis l'amorce, filtre, abonné synchrone qui lève une exception, file
pleine (compte des pertes, les autres abonnés reçoivent), `unsubscribeOwner`, publication après `close`.

## 5. Le Journal (M1)

### 5.1 Fichier et ouverture

- Base unique : `world/narrator2/narrator.duckdb` (+ `.wal`). Le Journal, les traces et, en M3, la mémoire y vivent.
- Ouverture par `journal/DuckDatabase.kt` (T01, partagé par T03 et T04), avec ces propriétés JDBC, toutes vérifiées

| Propriété | Valeur | Effet |
|---|---|---|
| `enable_external_access` | `false` | `read_csv`, `glob`, `ATTACH`, `COPY` : « file system operations are disabled by configuration » |

> fichiers hors de portée du modèle (§6.1, accès `MODEL`), pas la configuration de DuckDB.
| `autoinstall_known_extensions` / `autoload_known_extensions` | `false` | Aucun téléchargement ; `json` est déjà intégré au jar (`json_serialize_sql`, `->>` fonctionnent) |
| `memory_limit` | `journal.memoryLimitMb` (512) | Sinon 80 % de la RAM (25 Gio mesurés sur cette machine) |

| `jdbc_stream_results` | `true` | Les résultats sont lus en flux : 60 premières lignes d'un `SELECT` de 50 M lignes en 6 ms |

  Puis, sur la connexion d'écriture : `SET TimeZone = '<journal.timeZone ou zone de la JVM>'`, migrations, vues
  (`views.sql`), **`SET lock_configuration = true`** (plus aucun `SET` possible ensuite, vérifié), enfin deux
  connexions de lecture par `DuckDBConnection.duplicate()`, qui héritent du fuseau (vérifié).
- Migrations : fichiers `resources/narrator2/sql/V<n>__<nom>.sql` appliqués dans l'ordre, table `schema_version`.
  `views.sql` est réexécuté à chaque démarrage (`CREATE OR REPLACE`) : les vues et macros suivent toujours le code.
  **`journal/DuckDatabase.kt` (T01) applique lui-même ces migrations**, depuis sa propre liste `MIGRATIONS` (une
  entrée par fichier, dans l'ordre), chacune dans sa propre transaction avec sa ligne `schema_version`. C'est cette
  liste qui pilote la migration : un module `journal/Migrations.kt` séparé n'est pas nécessaire pour ça (le fichier
  prévu au §18.2 pour T03 sous ce nom).

### 5.2 Ce qui ne va pas dans DuckDB : l'état cohérent avec le monde

Ce qui doit rester **cohérent avec l'état du monde** vit dans le monde, sous forme de pièces jointes Fabric persistantes
(`AttachmentRegistry.create(id) { it.persistent(codec) }`, `copyOnDeath()` **(javap)**), sauvegardées avec le tronçon
ou le joueur, dans la même écriture que lui :
- index des blocs posés (pièce jointe de tronçon, §7.5) ;
- lieux déjà visités (pièce jointe de joueur, §7.4) ;
- état des garde-fous : modificateurs d'attributs, confiscations, mort protégée, quota de morts (pièce jointe de
  joueur, §10.2) ;
- échéance des créatures du Narrateur (pièce jointe d'entité).

Ainsi un crash ne peut jamais laisser un inventaire vidé sans trace de la confiscation, ni une mort protégée sans sa
marque : les deux sont sauvés ensemble. DuckDB garde l'**historique** (Journal et traces) ; il n'est jamais la source
d'un état de jeu.

### 5.4 Identifiants

`nextId(kind)` distribue des `Long` croissants pour `EVENT` (`events`, `chat` **et `private_messages`**),
`SESSION`, `TURN`, `TASK`, `LLM_CALL`, `TOOL_CALL`, `DECISION`. Un identifiant existe donc avant que sa ligne soit
écrite : un résultat d'outil peut citer `turn 42`, une décision peut citer l'événement qui l'a déclenchée.

**Réservations** (lot J, `journal/IdReservations.kt`, `handoff/M2-fix-J.md`) : un identifiant déjà cité (résultat d'outil,
log, transcription) ne doit jamais être redistribué après un crash qui a perdu sa ligne. Le fichier
`world/narrator2/narrator.ids`, à côté de la base, garde pour chaque type une borne au-delà de tout ce qui a été
distribué, et **un identifiant n'est distribué qu'une fois couvert par ce fichier**. À l'ouverture, chaque séquence repart
au-delà du `max(id)` de sa table **et** de ce fichier (lecture synchrone au démarrage).
- Réservation par blocs (1 000, et 100 000 pour les événements), le bloc suivant réservé en arrière-plan à mi-bloc ;
  l'appelant n'attend le disque que si une rafale vide le bloc d'abord. Écriture atomique (fichier temporaire forcé
  sur le disque, puis déplacé). Sous Windows, un fichier ouvert par un autre programme (antivirus, sauvegarde,
  lecture) ne peut pas être remplacé : le déplacement est retenté pendant 63 ms au plus (`handoff/FLAKY-1.md`). Les
  bornes en mémoire ne suivent que ce que le fichier contient : une écriture ratée ne réserve rien.
- Fermeture propre : le fichier reçoit exactement ce qui a été distribué, sans trou. Après un crash, les identifiants
  sautent d'un bloc au plus.
- Les `EVENT` sont distribués par le bus : le Journal s'y abonne **en premier** (abonné synchrone `journal_ids`), et
  chaque événement est réservé avant qu'un autre composant le voie.
- Fichier impossible à écrire : les identifiants sont distribués quand même, l'erreur est loguée, l'écriture retentée
  en arrière-plan au plus une fois par seconde.
- Une base en mémoire (tests) ne réserve rien et repart de `max(id) + 1`. `DisabledJournal` amorce à l'heure courante
  (`Clock.millis()`) pour que les identifiants des logs restent uniques.

**`nextId` est déclaré sur `TraceSink` (§5.5), pas sur `Journal`** : `Journal` en hérite (`interface Journal :
TraceSink, AutoCloseable`), ce qui permet de monter un `TraceSink` en mémoire dans les tests sans DuckDB (c'est lui
que `NarratorServices.trace` expose, §2.1).

### 5.5 Interface

```kotlin
interface Journal : TraceSink, AutoCloseable {
    val available: Boolean
    fun nextIdSeed(kind: IdKind): Long                 // used once by the bus
    /** Starts draining the bus subscription on the writer thread. */
    fun attach(bus: EventBus)
    /** Completes once every record handed over before the call is committed. */
    suspend fun barrier()
    /** Runs [query] on a read connection of the SQL pool; throws JournalUnavailableException or JournalTimeoutException. */
    suspend fun <T> read(timeoutMs: Long, query: (Connection) -> T): T
    fun checkpointAsync()
    fun health(): JournalHealth
    fun close(timeout: Duration)

    companion object {
        val DEFAULT_CLOSE_TIMEOUT: Duration = Duration.ofSeconds(10)

        /** Tables the model must never read, even through the `sql` tool: those of EventCatalog whose EventTable.visibleToModel is false. */
        val HIDDEN_FROM_MODEL: Set<String> = EventTable.entries.filterNot { it.visibleToModel }.map { it.sqlName }.toSet()  // = {"private_messages"}

        /** DuckDB functions that run SQL given as a string, which could read a hidden table: refused in model queries (§6.1). */
        val SQL_FROM_STRING_FUNCTIONS: Set<String> = setOf("query", "query_table")
    }
}
enum class IdKind { EVENT, SESSION, TURN, TASK, LLM_CALL, TOOL_CALL, DECISION }
data class JournalHealth(
    val available: Boolean, val queued: Int, val droppedEvents: Long, val rowsPerMinute: Long,
    val lastFlushMs: Long, val lastFlushRows: Int, val fileBytes: Long, val walBytes: Long, val lastError: String?,
)

/**
 * Implemented by the Journal: every trace is queued for the writer thread, never written on the caller's thread.
 * Also implemented by an in-memory sink for unit tests (`NarratorServices.trace`, §2.1), which is why [nextId]
 * lives here rather than on [Journal]: a test can hand out ids without a DuckDB database.
 */
interface TraceSink {
    /** A new id of [kind], strictly greater than every id handed out before, restarts included. */
    fun nextId(kind: IdKind): Long

    fun llmCall(r: LlmCallRecord)
    fun toolCall(r: ToolCallRecord)
    fun decision(r: DecisionRecord)
    fun turn(r: TurnRecord)                 // insert, then update with the same turn_id
    fun conversation(r: ConversationRecord) // insert, then update with the same conversation_id
    fun task(r: TaskRecord)                 // insert, then update with the same task_id
    fun chatSignals(r: ChatSignalsRecord)
}
```

Les `*Record` sont des `data class` qui reprennent colonne pour colonne les tables du §5.3 (T01, `trace/TraceRecords.kt`).
`Decisions` (T01, `trace/Decisions.kt`) est un petit helper qui écrit à la fois la ligne `engine_decisions` et une ligne
de log `[<tag>] <decision> <subject>: <reason>`.

**Vie privée (T01)** : `Journal.HIDDEN_FROM_MODEL` et `Journal.SQL_FROM_STRING_FUNCTIONS` (ci-dessus) sont la base de
la deuxième barrière du §6.1 (`SqlRunner`, T04) : toute requête qui nomme une table cachée ou appelle une des
fonctions listées est rejetée avant exécution. `JournalUnavailableException` et `JournalTimeoutException` (T01,
`journal/Journal.kt`) sont les deux exceptions typées de `read` citées ci-dessus. `DisabledJournal` (T01, même
fichier) est l'implémentation de repli du §2.2 point 2 : elle ne fait que compter et loguer (`DEBUG`) ce qu'elle ne
peut pas écrire, et échoue toute lecture avec `JournalUnavailableException`.

### 5.6 Le rédacteur par lots (`JournalWriter`, T03)

- Un thread `narrator2-journal`, seul propriétaire de la connexion d'écriture et des appenders.
- File d'entrée : l'abonnement asynchrone au bus (`Channel`, capacité `journal.queueCapacity`) **et** une file
  `ConcurrentLinkedQueue<TraceItem>` pour les traces et barrières (les traces ne passent pas par le bus : ce ne sont pas
  des faits de jeu).
- Boucle : toutes les `journal.flushIntervalMs` (1 000 ms), vider les deux files (au plus 50 000 éléments par tour),
  puis :
  1. tables en ajout seul (`events`, `positions`, `chat`, `private_messages`, `chat_signals`, `llm_calls`,
     `tool_calls`, `engine_decisions`) : un `DuckDBAppender` par table, `beginRow/append/endRow`, puis `flush()` ;
  2. tables mises à jour (`players`, `player_names`, `sessions`, `stat_totals`, `turns`, `conversations`, `tasks`) :
     requêtes préparées `INSERT … ON CONFLICT DO UPDATE` ou `UPDATE`, **jamais** par appender (une mise à jour ne
     verrait pas les lignes encore dans un appender) ;
  3. compléter les `barrier()` servies par ce tour.
- `session_id` des lignes `events`/`positions` : le rédacteur tient la table « UUID → session courante », alimentée
  par `PlayerJoined` / `PlayerLeft` dans l'ordre du flux.
- Une erreur SQL sur une ligne est loguée avec la ligne fautive (tronquée) et cette ligne seule est abandonnée ; une
  erreur sur la connexion (disque plein, fichier corrompu) passe le Journal en état dégradé (`available = false`,
  décision `journal_health`) et les enregistrements suivants sont comptés comme perdus.
- `checkpointAsync()` : `CHECKPOINT` au tour suivant. Appelé après chaque `ServerLifecycleEvents.AFTER_SAVE`
  (sauvegarde automatique du monde, toutes les 5 min environ) **(javap)** : le fichier DuckDB est alors à jour quand les
  sauvegardes du monde le copient.
- Bilan de santé toutes les 5 min : ligne de log `INFO` (lignes/min, taille de file, durée du dernier flush, pertes,
  taille des fichiers) et décision `journal_health`.
- Fermeture : voir §2.4.

### 5.7 Volume, taille et rétention

| Source | Volume estimé (`OBSERVER_API.md` §9) |
|---|---|
| `events` | 2 000 à 8 000 lignes par heure et par joueur actif |
| `positions` | 150 à 600 lignes par heure et par joueur (plafond 1 200) |
| `chat`, `chat_signals` | 10 à 100 par heure et par joueur |
| traces | ≈ 30 `llm_calls`, 60 `tool_calls`, 300 `engine_decisions` par heure de jeu actif |

À 25-40 octets par ligne compressée, 500 heures-joueur (quelques centaines d'heures à plusieurs) représentent 1 à
4 millions de lignes, soit **40 à 160 Mo** ; un serveur de 5 joueurs à 3 h par jour produit 0,4 à 1,8 Go par an.
DuckDB agrège ces volumes en moins d'une seconde.

**Rétention : rien n'est supprimé** (`MEMOIRE.md` §1.1). Aucune purge en M1/M2 ; supprimer ne rendrait d'ailleurs pas la
place sans reconstruire le fichier. `/narrator status` affiche la taille, et un `WARN` apparaît au démarrage au-delà de
`journal.warnSizeMb` (4 096). Les transcriptions (`logs/conversations/<date>/`, ≈ 0,4 Mo par heure active) ne sont pas
tournées non plus ; le propriétaire peut archiver les vieux dossiers de dates, la base n'y fait référence que par chemin.
La politique sera revue après une semaine de mesures réelles (§20).

## 6. Lecture SQL (M1)

### 6.1 `SqlRunner` (T04, `journal/SqlRunner.kt`)

```kotlin
data class SqlLimits(val maxRows: Int, val timeoutSeconds: Int, val maxCellChars: Int = 120, val maxChars: Int = 8_000)

sealed interface SqlOutcome {
    data class Rows(val text: String, val shown: Int, val total: Long?, val elapsedMs: Long) : SqlOutcome
    data class Rejected(val reason: String) : SqlOutcome      // validation: never executed
    data class Failed(val message: String) : SqlOutcome       // DuckDB error at execution
    data class TimedOut(val seconds: Int) : SqlOutcome
}

class SqlRunner(private val journal: Journal, private val clock: Clock) {
    suspend fun query(sql: String, limits: SqlLimits): SqlOutcome
}
```

**Validation, dans l'ordre** (tout échec → `Rejected`, rien n'est exécuté) :
1. Texte non vide, au plus 4 000 caractères ; un `;` final est retiré.
2. `SELECT json_serialize_sql(?)` avec la requête **en paramètre** (jamais concaténée). Vérifié **(essai)** :
   `{"error":true,"error_message":"Only SELECT statements can be serialized to json!"}` pour `INSERT`, `PRAGMA`,
   `COPY`, `ATTACH` et pour `SELECT 1; DROP TABLE t` ; une erreur de syntaxe donne aussi `error: true` avec le message
   du parseur, renvoyé tel quel au modèle.
3. `statements` doit contenir **exactement une** instruction (`SELECT 1; SELECT 2` en donne deux).
4. Fonctions interdites pour tous (`UNSAFE_FUNCTIONS`) : celles qui modifient la base ou lisent la mémoire brute
   (`nextval`, `setval`, `checkpoint`, `force_checkpoint`, les bascules de log/profil, `arrow_scan`).

> **La signature réelle a un second paramètre `access` (T04) et va plus loin que ce §, sur décision du superviseur.**
> `query(sql, limits, access = SqlAccess.MODEL)`. L'opérateur (`OPERATOR`, §6.6) lit tout ; seul le modèle (`MODEL`,
> outil `sql`) subit les barrières ci-dessous. Constat 19 du lot H : `enable_external_access` ne suffit pas, DuckDB
> garde ses propres fichiers lisibles (§5.1). Le modèle est donc filtré **deux fois** :
>
> - **sur l'arbre syntaxique** (`json_serialize_sql`) : aucune table de `Journal.HIDDEN_FROM_MODEL` (sous toute forme,
>   casse, `SUMMARIZE`/`DESCRIBE`, chaîne passée à une fonction) ; aucune fonction qui exécute du SQL en texte
>   (`query`, `query_table`, `json_execute_serialized_sql`, `json_serialize_plan`) ; aucun élément du catalogue
>   (`duckdb_*`, `pragma_*`, `pg_*`, `sqlite_*`, `information_schema`, `pg_catalog`, `SHOW TABLES`) ; **aucune fonction
>   de fichier ni de réglage** (`read_*`, `parquet_*`, `glob`, `sniff_csv`, `current_setting`) ; tout nom de table,
>   schéma ou catalogue doit être un nom simple et le schéma doit être `main` — un chemin ou un nom de fichier entre
>   guillemets (`FROM '…/narrator.duckdb'`) est un **scan de remplacement**, refusé ; en `FROM`, seules `range`,
>   `unnest` et les macros de table du Journal sont acceptées comme fonctions ;
> - **sur le plan** (`EXPLAIN (FORMAT JSON)`), quelles que soient les vues et macros traversées : une **liste blanche**.
>   Chaque parcours (`Table`) doit viser une table visible ; chaque fonction de table du plan doit être `range`,
>   `unnest` ou `duckdb_columns` (atteinte seulement par `columns_of`) ; tout autre opérateur doit appartenir à
>   `PLAN_OPERATORS` (jointures, agrégats, fenêtres, tris, CTE… qui ne lisent rien). Un lecteur de fichier caché
>   derrière une vue est ainsi arrêté (testé avec des vues et une macro piégées, et sur une vraie base sur disque :
>   `SqlFileAccessTest`). Un plan illisible est refusé.

**Exécution** : sur une connexion de lecture, `Statement.setQueryTimeout(limits.timeoutSeconds)` (vérifié : coupe une
requête de 100 milliards de lignes à 1 001 ms avec « INTERRUPT Error »). Lire au plus `maxRows` lignes, puis continuer à
compter avec `next()` jusqu'à 10 000 (au-delà : total inconnu, affiché `>10000`). Aucune réécriture de la requête : son
`ORDER BY` est respecté.

**Messages d'erreur** : le pilote préfixe les erreurs par « Invalid Input Error: Attempting to execute an unsuccessful or
closed pending query result / Error: » ; `SqlRunner` garde la partie utile (`Binder Error: …`, `Permission Error: …`,
ligne et curseur compris). Pour le modèle, tout chemin absolu du serveur en est retiré (`[path]`) et les `<` `>` y
deviennent `‹` `›` : une erreur de DuckDB peut citer une valeur d'origine joueur.

**Cellules et noms de colonnes (constat 27, lot H).** Le format compact (§6.2) échappe `<` `>` en `‹` `›` dans chaque
cellule et chaque nom de colonne, via l'échappement commun `core/ModelText`, pour qu'un texte d'origine joueur (chat,
pseudo, valeur qu'un `PIVOT` transforme en colonne) ne puisse pas imiter une balise du moteur (`<engine>`, `<operator>`).

### 6.2 Format compact des résultats

```
now 09-25 21:44:10 · 3 rows · 12 ms
player|diamonds|last_seen
Bartok|41|09-25 21:40:02
Mimosa|3|09-24 22:10:45
clemsix6|0|NULL
```
- Colonnes séparées par `|` sans alignement ; `|` et retours à la ligne dans une valeur sont remplacés par `¦` et `⏎`.
- Horodatages en heure locale `MM-dd HH:mm:ss` (année ajoutée si ce n'est pas l'année courante) ; l'en-tête donne
  `now` pour que le modèle calcule les écarts.
- Nombres à virgule : au plus 2 décimales ; JSON compacté ; `NULL` écrit tel quel.
- Cellule tronquée au-delà de `maxCellChars` : `…(+N)` ; texte total tronqué à `maxChars` en fin de ligne.
- Pied si incomplet : `50 of 1234 rows shown — aggregate or add LIMIT` (ou `50 of >10000 rows shown …`).

### 6.6 `/narrator sql <requête>` (T04, `command/SqlCommand.kt`)

Opérateurs seulement (niveau 2, comme toute la racine `/narrator`). Même `SqlRunner`, plafonds du §6.3, accès
`SqlAccess.OPERATOR`. La requête est lancée dans `runtime.scope`, la réponse revient par `server.execute` : une ligne
grise par ligne de résultat, erreurs en rouge. Si le Journal est indisponible : message d'erreur explicite.

> **Confidentialité de la décision (constat 20, lot H).** Un opérateur lit tout, messages privés compris ; la décision
> `operator` est écrite dans `engine_decisions`, **que le modèle lit**. Elle ne garde donc **ni la requête, ni l'erreur
> de DuckDB, ni le nombre de lignes** (une requête sur `private_messages`, ou une erreur qui cite une valeur, les livrerait
> au modèle). Elle garde seulement une **empreinte** de la requête (HMAC-SHA256 à clé tirée au démarrage, 16 hex — une clé
> pour qu'on ne puisse pas la recalculer avec le `sha256()` de DuckDB), sa **taille** en caractères et son **statut**
> (`ok`/`refused`/`failed`/`timed_out`) : `detail = {query_hash, query_chars, status}`, même chose dans la raison. La
> requête complète ne va que dans le log du serveur, avec son empreinte. Le masquage de l'événement `command` de
> `/narrator sql …` (l'Observateur) reste du ressort du lot CD.

## 8. Le registre d'outils (M2)

### 8.1 Définition d'un outil

```kotlin
/** Documentation of a tool argument; also used for the JSON schema. */
@OptIn(ExperimentalSerializationApi::class) @SerialInfo @Target(AnnotationTarget.PROPERTY)
annotation class Doc(val text: String)
@SerialInfo @Target(AnnotationTarget.PROPERTY) annotation class Range(val min: Double, val max: Double)  // numbers
@SerialInfo @Target(AnnotationTarget.PROPERTY) annotation class MaxLen(val chars: Int)                   // strings
@SerialInfo @Target(AnnotationTarget.PROPERTY) annotation class Items(val min: Int, val max: Int)        // lists

enum class ToolEffect { READ, SPEECH, WORLD, TASK, ENGINE }
enum class ToolStatus { OK, INVALID, DENIED, FAILED, TIMEOUT, UNKNOWN }

data class ToolResult(val status: ToolStatus, val text: String, val targets: List<PlayerRef> = emptyList()) {
    val isError: Boolean get() = status != ToolStatus.OK

    companion object {
        fun ok(text: String, targets: List<PlayerRef> = emptyList()): ToolResult
        fun invalid(problem: String): ToolResult              // "Invalid arguments: <problem>": the model should fix and retry
        fun denied(rule: String, text: String): ToolResult    // "DENIED (<rule>): <text>"
        fun denied(verdict: Verdict.Denied): ToolResult        // = denied(verdict.rule, verdict.message)
        fun failed(reason: String): ToolResult                 // "FAILED: <reason>"
        fun timeout(text: String): ToolResult                  // "TIMEOUT: <text>", a read tool that did not finish in time
        fun unknown(text: String): ToolResult                  // "UNKNOWN: <text>", a world tool that did not finish in time
    }
}

data class Caller(val role: Role, val conversationId: String, val turnId: Long?, val taskId: Long?)

/**
 * What is wired when a conversation's tools are chosen: a tool whose [NarratorTool.isAvailable] answers false for
 * this [ToolEnv] is not sent to the model at all (§8.6).
 */
data class ToolEnv(val journalAvailable: Boolean, val workerRoles: Set<Role>)

abstract class NarratorTool<A : Any>(
    val name: String,                      // snake_case, ≤ 32 chars (LLMGW prefixes names ≤ 52 chars), checked at construction
    val description: String,               // English, static: no chaos-dependent numbers (§8.6)
    val args: KSerializer<A>,
    val effect: ToolEffect,
    val timeoutMs: Long = 5_000,
) {
    /** Whether the model may see this tool at all, given what is wired right now. */
    open fun isAvailable(env: ToolEnv): Boolean = true
    abstract suspend fun run(ctx: ToolContext, args: A): ToolResult
}

class ToolContext(
    val services: NarratorServices,        // implemented by NarratorRuntime; faked in unit tests
    val caller: Caller,
    val clock: Clock,
    private val timeoutMs: Long,
) {
    /** Runs [block] on the server thread (onServerThread with this tool's timeout). */
    suspend fun <T> onServer(block: (MinecraftServer) -> T): T
    val guards: Guards get() = services.guards
    val players: PlayerStates get() = services.players
    val settings: Settings get() = services.settings.get()
}

/**
 * The tools of one conversation, in the order sent to the model, with their SDK definitions (§8.6). Built once per
 * conversation (`ToolCatalog.toolSetFor`) and never changed afterwards.
 */
class ToolSet(val tools: List<NarratorTool<*>>, val definitions: List<ToolUnion>) {
    val names: List<String>
    /** The tool called [name]; null when this conversation does not have it. */
    operator fun get(name: String): NarratorTool<*>?
    companion object { val EMPTY: ToolSet }
}

/** Implemented by ToolRunner (T08); consumed by AgentLoop (T11), which can therefore be tested with a fake. */
interface ToolExecutor {
    suspend fun runAll(calls: List<ToolUseBlock>, tools: ToolSet, caller: Caller, llmCallId: Long): List<ToolResultBlockParam>
}
```

Un outil sans argument utilise `object NoArgs` sérialisable. Les arguments optionnels ont une valeur par défaut Kotlin ;
les nullables ont `= null`. **`ToolSet` est défini dans `tool/Tool.kt` (T01), avec le reste de ce contrat, et non dans
un fichier séparé** : `ToolExecutor.runAll` en a besoin dans sa signature, et `ToolExecutor` doit lui-même vivre à côté
de `NarratorTool` pour que `AgentLoop` (T11) puisse dépendre du contrat sans dépendre de `ToolRunner` (T08). Le
fichier `tool/ToolSet.kt` du §18.2 (T08) ne sert donc qu'à **construire** un `ToolSet` (`ToolCatalog.toolSetFor`), pas
à définir la classe.

### 8.2 Schéma JSON généré (`tool/ToolSchema.kt`)

Le schéma est **généré** depuis le `SerialDescriptor` des arguments et les annotations : une seule source pour le
schéma et le décodage, donc aucune dérive possible.
- `String` → `string` ; `Int`/`Long` → `integer` ; `Double`/`Float` → `number` ; `Boolean` → `boolean` ;
  `enum class` → `string` + `enum` (noms sérialisés, en `snake_case` via `@SerialName`) ; `List<T>` → `array` ;
  classe `@Serializable` imbriquée → `object`.
- Chaque objet : `properties` dans l'ordre de déclaration, `required` = propriétés sans valeur par défaut,
  `additionalProperties: false`.
- `@Doc` → `description` ; `@Range` → `minimum`/`maximum` ; `@MaxLen` → `maxLength` ; `@Items` →
  `minItems`/`maxItems`. Ces mots-clés servent d'indication au modèle ; ils sont **appliqués par le code** (§8.3).
- Types non gérés (`Map`, polymorphisme, récursion) : erreur à la construction du registre, détectée par
  `ToolCatalogTest`, qui construit tous les outils.
- **Pas de `strict: true`.** Les sorties structurées limitent le nombre d'outils stricts par requête et d'options
  facultatives, refusent `minimum`/`maximum`/`maxLength`, et leur passage par LLMGW n'est pas vérifié. La validation côté
  serveur donne de toute façon des erreurs précises que le modèle corrige.
- Définition SDK : `Tool.builder().name().description().inputSchema(...)` avec
  `putAdditionalProperty("additionalProperties", JsonValue.from(false))`. Sérialisation déterministe (outils triés par
  nom, propriétés dans l'ordre de déclaration) : le préfixe mis en cache ne bouge pas.

### 8.3 Validation des arguments (`tool/ToolArgs.kt`)

1. Entrée du `tool_use` (`JsonValue` du SDK) → texte JSON → `Json { ignoreUnknownKeys = false; isLenient = false;
   coerceInputValues = false; explicitNulls = false }.decodeFromString(args, ...)`. Les messages de kotlinx
   (« Encountered an unknown key 'x' », « Field 'y' is required ») sont renvoyés tels quels, préfixés
   `Invalid arguments: `.
2. Parcours des annotations : `seconds must be between 1 and 900 (got 1200)`, `text is longer than 300 characters`,
   `players must have 1 to 8 items`.
3. Validation propre à l'outil (identifiants de registre, joueurs en ligne, plafonds du chaos) dans `run`, avec des
   erreurs qui **donnent la solution** : liste des joueurs en ligne, identifiants proches (`unknown effect "speedy";
   did you mean "speed"?`), plafond en vigueur (`max 6 at chaos 3`).

Toute erreur → `ToolResult.invalid` → `tool_result` avec `is_error: true`.

### 8.4 Exécution (`tool/ToolRunner.kt`)

```kotlin
class ToolRunner(private val services: NarratorServices, private val clock: Clock) : ToolExecutor {
    /** Runs the tool_use blocks of one assistant message, in order; returns one tool_result per block, same order. */
    override suspend fun runAll(calls: List<ToolUseBlock>, tools: ToolSet, caller: Caller, llmCallId: Long): List<ToolResultBlockParam>
}
```
- Les `tool_use` parallèles d'une même réponse sont exécutés **séquentiellement, dans l'ordre** : décisions des
  garde-fous déterministes, et un seul message `user` rend tous les résultats (§12.6).
- Outil inconnu (ne devrait pas arriver, les outils sont figés) → `INVALID`.
- `phase != RUNNING` → `FAILED: server is stopping`, sans exécution.
- Délai : `withTimeout(tool.timeoutMs)` autour de `run`. Pour un outil qui touche le monde, un dépassement donne
  `UNKNOWN: the action may or may not have happened` (la tâche planifiée sur le thread serveur n'est pas annulable,
  `ORACLE_ACTIONS_API.md` §2.1) ; les outils sont donc **bornés par construction** (rayons, nombres de résultats).
- Exception → `FAILED` avec le message, log `ERROR` avec la pile.
- Résultat tronqué à 8 000 caractères (`… (truncated, N chars)`).
- **Audit** : une ligne `tool_calls` par appel (arguments, statut, résultat tronqué à 2 000 caractères, durée, joueurs
  touchés, effet) et une ligne de log `[Tool] <role> <tool> <status> <ms>ms targets=[…] <résumé 80 caractères>`.

### 8.5 Format des résultats

Texte anglais, compact, première ligne = verdict :
- `ok: Bartok gets slowness II for 60s (until 21:41:10)`
- `DENIED (no_pile_on): Bartok died 2m ago; hostile actions against him are refused until 21:44 (in 3m).`
- `Invalid arguments: seconds must be between 1 and 600 (got 900)`
- Lectures (Oracle, `sql`) : bloc multiligne, une information par ligne, sans prose.

### 8.6 Outils figés et outils réellement branchés

- `ToolSet` = liste ordonnée de `NarratorTool` + définitions SDK, construite **une fois par conversation** par
  `ToolCatalog.toolSetFor(role, env)` et stockée dans la `Conversation`. Elle ne change jamais pendant un chapitre ou une
  tâche (cache et réflexion préservée).
- `ToolEnv` décrit ce qui est branché au moment de la construction : Journal disponible, rôles d'assistants actifs,
  réflexes. Un outil dont `isAvailable(env)` est faux **n'est pas envoyé au modèle** (par exemple `sql` quand le Journal
  n'a pas pu s'ouvrir, ou `delegate` si aucun rôle d'assistant n'est actif). L'`enum` des rôles de `delegate` ne contient
  que les rôles réellement câblés (`analyst` en M2).
- Si un composant tombe en panne en cours de chapitre, l'outil reste déclaré et répond `FAILED` avec la cause.
- Les descriptions sont statiques : aucun nombre qui dépend du chaos ou de la config, sinon un `/narrator reload`
  changerait les outils. Les plafonds apparaissent dans les messages d'erreur.
- Décision `tool_catalog` à chaque construction (rôle, noms des outils, outils écartés et pourquoi).

## 10. Les règles du moteur (`ARCHITECTURE.md` §17), appliquées par le code

Paquet `guard` (Kotlin) et `mixin.guard` (Java), tâches T09a (registres, mort protégée) et T09b (politiques). Aucune de ces règles ne dépend du prompt : le modèle peut
demander n'importe quoi, le code refuse ou borne.

### 10.1 Qui applique quoi

| Règle (§17.4) | Composant | Mécanisme |
|---|---|---|
| Les constructions ne sont jamais détruites définitivement | **absence d'API** + `CommandPolicy` + `ExplosionGuard` + `SpawnPolicy` | En M2, **aucun outil n'écrit de bloc**. `run_command` refuse toute commande qui modifie des blocs (§10.6). Les explosions attribuées au Narrateur ne touchent aucun bloc et n'allument aucun feu (mixin, §10.7) ; l'outil `explosion` utilise `NONE`. La foudre est toujours visuelle. Les créatures qui modifient des blocs ne sont pas invocables ; les zombies du Narrateur ne cassent pas les portes. La restauration de blocs arrive avec le premier outil qui en modifie (M4, §10.8). |
| Un objet n'est jamais perdu définitivement | `ItemLedger` + `DeathGuard` + `CommandPolicy` + `ExplosionGuard` | `take_item` = confiscation temporaire inscrite avant retrait et rendue automatiquement. Mort causée par le Narrateur = inventaire conservé. `clear`, `item`, `loot`, `give`, `enchant`, `kill` refusées. Les explosions du Narrateur épargnent les objets au sol et les décorations. |
| Au plus une mort directe par heure jouée (chaos 3), inventaire conservé | `DeathGuard` + mixins `keepInventory` | §10.3. |
| Le PvP n'est jamais forcé | `CommandPolicy` | Pas d'outil de duel en M2 ; `team` et `gamerule` refusées (tir ami, règle PvP). Les duels (M4) exigeront l'acceptation des deux joueurs. |
| Pas d'acharnement | `TargetingPolicy` | §10.3 : mort depuis moins de 5 min, ou châtiment d'un tour précédent encore actif → action hostile refusée. |
| Commandes d'administration interdites | `CommandPolicy` | Source niveau `GAMEMASTER` (les commandes de niveau 3-4 sont invisibles à l'analyse) + liste codée en dur + ajouts de la config. |
| Plafonds | `Caps` (par niveau de chaos), `SpeechLimiter`, `NarratorMobs` | §10.4. |
| Attributs réappliqués après la mort | `AttributeLedger` | Registre persistant, réapplication à `JOIN` et `AFTER_RESPAWN`. |

### 10.2 L'état des garde-fous vit sur le joueur

Pièce jointe persistante de joueur `narrator2:guard_state`, `copyOnDeath()`, codec `RecordCodecBuilder` (T09a) :

```kotlin
data class GuardState(
    val modifiers: List<LedgerModifier> = emptyList(),
    val effects: List<LedgerEffect> = emptyList(),        // effects put on the player by the Narrator (EffectLedger)
    val confiscations: List<Confiscation> = emptyList(),
    val episode: OpenEpisode? = null,                     // last punishment opened against the player, rebuilt at reconnection
    val armedUntil: Long = 0,                             // PLAY_TIME stat (ticks) until which the death guard is armed
    val protectedDeath: Boolean = false,          // died under the death guard, awaiting respawn
    val narratorKills: List<Long> = emptyList(),  // PLAY_TIME stat (ticks) at each narrator kill, last hour only
    val lastDeathAt: Long? = null,                // last death, whatever the cause, epoch ms; kept 5 min (T09c)
    val perils: Map<String, Long> = emptyMap(),   // Peril id (fall, fire, drowning, magic, hunger, any) → PLAY_TIME until which it is armed (M2-fix-A)
    val rescues: List<Long> = emptyList(),        // epoch ms of each rescue beyond the quota, last 10 min only (M2-fix-A2)
)
data class LedgerModifier(val attribute: String, val amount: Double, val operation: String,
                          val expiresAt: Long, val harmful: Boolean, val turnId: Long?)
data class LedgerEffect(val effect: String, val level: Int, val expiresAt: Long, val harmful: Boolean, val turnId: Long?)
data class Confiscation(val id: Long, val items: List<String> /* SNBT */, val what: String /* readable, e.g. "6x minecraft:diamond" */,
                        val takenAt: Long, val returnAt: Long, val reason: String?, val turnId: Long?)
```

Toujours remplacée par une **nouvelle instance** (`setAttached`), jamais modifiée en place. L'inventaire et cet état sont
écrits dans le même fichier joueur, à la même sauvegarde : un crash ne peut pas les désynchroniser.

- **`AttributeLedger`** : un modificateur transitoire par attribut, identifiant `narrator2:mod/<attribut>`
  (`addOrUpdateTransientModifier`). Échéances en **temps réel** (le joueur lit « 5 minutes »), vérifiées chaque seconde ;
  à `JOIN` et `AFTER_RESPAWN` : retrait des modificateurs `narrator2:*` absents du registre, réapplication des autres.
  Décisions `ledger applied/expired/reapplied`. L'ancien modificateur est retiré avant le nouveau : la mise à jour du jeu
  garde celui d'une autre opération sous le même identifiant (M2-fix-A). Un sauvetage de la garde de mort (§10.3) retire
  les modificateurs nuisibles (`resetHarmful`, décisions `ledger removed`).
- **`EffectLedger`** : distingue un effet posé par le Narrateur d'une potion bue par le joueur — le jeu garde l'effet
  lui-même (sauvé avec le joueur, perdu à la mort), le registre n'en garde que la trace. Sans lui, `remove_effect …
  all_narrator` et la ligne « effets posés par le Narrateur » d'`inspect_player` seraient impossibles. Une entrée
  disparaît dès que l'effet n'est plus sur le joueur (expiré, lait, mort, retiré), contrôlé chaque seconde et à chaque
  connexion et réapparition. Un sauvetage (§10.3) retire les effets nuisibles du Narrateur (`removeHarmful`), oubliés
  avant le retrait : une lévitation levée ainsi ne pose pas de coussin et n'arme rien.
- **`ItemLedger`** : sur le thread serveur, dans le même tick : copier et sérialiser les piles visées
  (`ItemStack.CODEC` + `registryAccess`, SNBT), **inscrire la confiscation**, puis retirer de l'inventaire et
  `broadcastChanges()`. **Rien ne tombe jamais au sol** : la restitution, à l'échéance (joueur en ligne et vivant) ou à
  la connexion, insère dans l'inventaire (`ItemLedger.insert`, qui ne détruit jamais ce qui ne rentre pas, contrairement
  à `Inventory.add` pour un joueur en créatif) ; ce qui ne rentre pas **reste dans le registre** — ce qui est dû attend
  là — et revient dès qu'il y a de la place (contrôle chaque seconde), le joueur étant prévenu une seule fois par
  confiscation (clé d'UI `items.no_room`). Rien n'est rendu à un joueur mort : ce sera fait à la réapparition. Une
  pile qui ne se désérialise plus (objet disparu du jeu) reste elle aussi dans le registre, `ERROR` au log et message
  aux opérateurs : jamais d'effacement silencieux.
- **`NarratorMobs`** : les créatures invoquées portent le tag `narrator2` et une pièce jointe d'entité persistante
  `narrator2:mob` (échéance, joueur visé, châtiment, emplacements d'équipement qui lui sont propres). Registre en mémoire
  tenu par `ServerEntityEvents.ENTITY_LOAD` / `ENTITY_UNLOAD` **(javap)** ; chaque seconde, les créatures échues sont
  retirées (`discard()`), après avoir rendu ce que les joueurs leur ont confié (`Belongings`, T09c). Une créature qui se
  convertit ou se divise transmet sa pièce jointe et sa cible (`MOB_CONVERSION`, T09c). Le plafond compte les créatures
  chargées. Elles ne blessent ni ne ciblent un joueur protégé ou mort depuis moins de 5 min (`CreatureShield`, T09c).

### 10.3 Anti-acharnement et mort protégée

**Actions hostiles** (classification objective, jamais déclarée par le modèle) : effets de catégorie `HARMFUL`, tout
`set_attribute` sauf direction bénéfique (§10.5), `launch`, `take_item`, `teleport` à plus de 32 blocs, `spawn` d'un
type `MONSTER` ou avec `target`, `lightning` avec dégâts, `explosion` à moins de 8 blocs d'un joueur.

**`TargetingPolicy.check(target, caller)`**, dans l'ordre :
1. joueur protégé (`safety.protectedPlayers` ou `/narrator protect`) → `DENIED (protected)` ;
2. chaos 0 → `DENIED (chaos_0)` ;
3. mort depuis moins de 5 min (`PlayerStates.lastDeathAt`, ou `GuardState.lastDeathAt` qui survit à une reconnexion)
   → `DENIED (no_pile_on)` avec l'heure de fin ;
4. **épisode** hostile actif ouvert par un **autre tour** → `DENIED (already_punished)` avec l'échéance.
   Un épisode naît à la première action hostile d'un tour contre un joueur ; les actions hostiles du **même** tour s'y
   ajoutent (un châtiment = plusieurs actions coordonnées) ; il se termine quand tous ses effets sont échus
   (effets, modificateurs, confiscations, créatures). Il est reconstruit à la connexion depuis `GuardState`.

Sont hostiles aussi (M2-fix-A) : remplacer un effet bénéfique plus long ou plus fort par un plus court ou plus faible,
et un `jump_strength` au-delà de 0,6.

**`DeathGuard`** (révisé par M2-fix-A puis M2-fix-A2, voir `handoff/M2-fix-A.md` et `handoff/M2-fix-A2.md`) :
- **Armement** par toute action **nuisible**, pour un **péril** (`Peril` : `fall`, `fire`, `drowning`, `magic`,
  `hunger`, `any`), ce qu'elle peut plausiblement tuer : `launch` (15 s, chute), `explosion` et `lightning` (5 s),
  `spawn` hostile (durée de vie des créatures), effet nuisible (durée + 30 s, péril de l'effet), retrait d'un bienfait
  (30 s, péril du bienfait), `set_attribute` défavorable (durée + 30 s, péril de l'attribut ; un changement favorable
  n'arme rien), `take_item` (15 s), toute `teleport` (30 s). Sans péril, `armDeathGuard` couvre `any`. À la fin d'une
  lévitation du Narrateur (expirée, lait, retirée), la chute est amortie (`fall_damage_multiplier` × 0 par
  l'`AttributeLedger`, 30 s plus la durée d'une chute jusqu'au bas du monde) et la garde armée d'autant pour une chute.
- **Attribution** d'une mort au Narrateur : entité source ou directe qui est une créature du Narrateur ou ce qu'elle
  possède (`CreatureShield.isNarratorsDoing` : un vex, une flèche), **ou** garde armée pour un péril qui couvre la cause
  de la mort. Deux règles la resserrent :
  - un **`/kill` d'opérateur** (`generic_kill`) n'est **jamais** attribué ni empêché ;
  - un coup porté par **un autre joueur** n'est **jamais** attribué au Narrateur, garde armée ou non : sinon un effet
    nuisible du Narrateur rendrait sa victime intuable en PvP.
- **`ServerLivingEntityEvents.ALLOW_DEATH`**, mort attribuée, avant le totem :
  - quota disponible (morts du Narrateur dans la dernière heure de **temps joué**, mesuré par la stat vanilla
    `PLAY_TIME` **(javap)**, inférieures au plafond du chaos) → mort autorisée, `protectedDeath = true`. Le quota n'est
    **pas encore compté** ici : `ALLOW_DEATH` passe avant le totem, et un totem qui sauve le joueur ne doit pas lui
    coûter son quota ;
  - quota épuisé → mort **refusée** (`false`), **à chaque fois**, et joueur **sauvé** (M2-fix-A2), quelle que soit la
    cause (lave, feu, noyade, chute, vide, créature…) :
    1. vie remise à 1 avant tout déplacement (Fabric ne remet pas la vie du joueur, vérifié en bytecode) ;
    2. effets et modificateurs **nuisibles du Narrateur** retirés par les registres (`removeHarmful`, `resetHarmful`) ;
       ceux des autres sources restent ;
    3. ramené à son **point de réapparition** tel que le jeu le trouve (lit ou ancre sans consommer de charge, sinon le
       point d'apparition du monde), à défaut sur le sol sûr de sa colonne (`Teleports.landing`) ;
    4. chute arrêtée, **éteint**, **air** rendu, nourriture portée à 6 s'il mourait de faim, **aucun dégât de chute
       pendant 30 s** (`fall_damage_multiplier` × 0 par l'`AttributeLedger`, une faveur), **6 PV** (3 cœurs) ;
    5. éteint de nouveau à la fin du tick (`GuardsImpl.tick` → `DeathGuard.afterTick`) : ce qui l'a enflammé peut agir
       encore après le coup, dans le même tick (un second bloc de lave traversé) ;
    6. décision `death_guard rescued` (cause, `rescued_by`, `rescued_to`, ce qui a été retiré, `recent_rescues`).

    **Un sauvetage n'arme rien** : les armements des actions continuent tels quels, une nouvelle mort attribuée pendant
    ce temps est un nouveau sauvetage, et la boucle d'un joueur qui remourrait sur place est impossible, puisqu'il n'y est
    plus. Il n'y a jamais de mort du Narrateur au-delà du quota. **Borne anti-abus** : au-delà de 3 sauvetages en 10 min
    (temps réel, `GuardState.rescues`), chaque nouveau sauvetage est écrit au niveau `WARN` pour les opérateurs ; le
    joueur est quand même sauvé.
- **`AFTER_DEATH`**, une fois la mort survenue : c'est seulement là, pour une mort marquée, que **le quota est compté**
  (`narratorKills` reçoit le `PLAY_TIME` courant) et que la décision `death_guard counted` est écrite. Une marque posée
  à `ALLOW_DEATH` puis sauvée par un totem entre-temps n'atteint jamais `AFTER_DEATH` : elle est effacée à la mort
  suivante ou à la connexion, sans avoir consommé le quota.
- **Inventaire conservé** : les deux mixins `@WrapOperation` de `ORACLE_ACTIONS_API.md` §5.3
  (`PlayerKeepInventoryMixin` sur `dropEquipment` et `getBaseExperienceReward`, `ServerPlayerKeepInventoryMixin` sur
  `restoreFrom`) interrogent `DeathGuard.keepsInventory(uuid)`, qui lit la marque **sur le joueur** (`GuardState`,
  §10.2) — sur le joueur mourant, puis sur l'ancien objet joueur à la réapparition — jamais un ensemble en mémoire.
- **Redémarrage entre la mort et la réapparition** : `protectedDeath` est dans `GuardState`, sur disque avec le reste
  de l'état des garde-fous : rien à reconstruire en mémoire. À `JOIN`, seule une marque restée sur un joueur qui n'est
  plus mourant (un totem l'a sauvé entre-temps) est effacée, car périmée. À `AFTER_RESPAWN`, la marque est retirée :
  l'inventaire a été reporté.
- `deathAttribution(victim, source)` renvoie `narrator` et `keptInventory` à l'Observateur pour l'événement `PlayerDied`.

### 12.2 Boîte de réception et urgences

```kotlin
enum class Urgency {
    IMMEDIATE,  // wakes after the chat debounce
    SOON,       // wakes after a short grouping
    NEXT,       // never wakes; delivered with the next wake or between two tool calls
    BATCH,      // never delivered as such; summarised by ActivityDigest (heartbeat, situation)
}

sealed interface DirectorSignal {
    // Inbox items
    data class Event(val envelope: Envelope, val urgency: Urgency, val annotation: String?) : DirectorSignal
    data class TaskDone(val taskId: Long, val role: Role, val status: TaskRecord.Status, val result: String, val at: Long) : DirectorSignal
    data class ReminderDue(val id: Long, val note: String, val setAt: Long, val at: Long) : DirectorSignal
    data class OperatorWhisper(val from: String, val text: String, val at: Long) : DirectorSignal
    // Control
    data object Pause : DirectorSignal
    data object Resume : DirectorSignal
    data class CloseChapter(val reason: ConversationRecord.EndReason) : DirectorSignal
    data class SettingsChanged(val old: Settings, val new: Settings) : DirectorSignal
}

/** States of the Director (§12.5); T01, `director/DirectorControl.kt`. */
enum class DirectorState { DISABLED, IDLE, WAITING, RUNNING, CLOSING, PAUSED, BACKOFF, BLOCKED, STOPPED }

interface DirectorControl {                 // contract in T01; used by tools and commands
    fun post(signal: DirectorSignal)        // any thread, never blocks
    fun scheduleReminder(inSeconds: Int, note: String, caller: Caller): Result<Long>
    fun status(): DirectorStatus            // state, chapter, context tokens, queue sizes, blocked until…
}
```

`TaskDone.status` et `CloseChapter.reason` sont **typés** dès T01 (`TaskRecord.Status` et
`ConversationRecord.EndReason`, §5.5, `trace/TraceRecords.kt`), pas de simples `String` : moins d'erreurs de frappe
entre ce que poste la Délégation (§13) ou le §12.10 et ce que lit le Directeur. `DirectorStatus` (contrat en T01,

c'est lui que l'outil `remind_me` (§9.5) consulte pour appliquer son plafond de 5 rappels en attente.

Tout passe par un `Channel<DirectorSignal>` (capacité 4 096 ; au-delà, les `Event` `NEXT` les plus anciens sont
abandonnés et comptés, jamais le chat adressé ni les signaux de contrôle). La coroutine du Directeur est **la seule** à
lire ce canal et à toucher son état : aucun verrou.

### 12.3 Saillance (`Salience.kt`)

Abonné asynchrone au bus (capacité 8 192), dans `runtime.scope`. Il classe chaque événement et poste un
`DirectorSignal.Event`, ou alimente seulement `ActivityDigest` (`BATCH`). Le tri du chat appelle `Reflexes` dans une
coroutine fille par message (≤ 1,5 s) pour ne pas retarder les autres événements.

| Événement | Urgence |
|---|---|
| `ChatMessage(PRAY)` | `IMMEDIATE` + indicateur pour l'auteur, dans le budget de son auteur (ci-dessous), sinon `SOON` |
| `ChatMessage(PUBLIC)` adressé (≥ 0,6, ou zone grise tranchée par l'heuristique) | `IMMEDIATE` + indicateur pour l'auteur, dans le budget de son auteur, sinon `SOON` |
| `ChatMessage(PUBLIC)` non adressé | `NEXT` : il ne réveille jamais le Directeur (relecture de M2, constat 26) ; il part avec le réveil suivant, battement compris, ou entre deux appels d'outils |
| `ChatMessage(WHISPER)` | **jamais** transmis au Directeur (message privé entre joueurs, journalisé seulement) |
| `NarratorSpoke(OPERATOR)` (`/narrator say`) | `NEXT` : le Directeur apprend ce qu'on lui a fait dire |
| `PlayerDied`, `EntityKilled(pvp)`, `HealthCritical` | `SOON` |
| `PlayerJoined`, `PlayerLeft` | `SOON` |
| `AdvancementEarned` de cadre `goal`/`challenge`, ou dans la liste `NOTABLE_ADVANCEMENTS` (diamants, Nether, End, élytres, débris antiques, netherite…) | `SOON` |
| `StructureEntered` : première visite, ou structure de `NOTABLE_STRUCTURES` (ancient city, stronghold, end city, fortress, bastion, trial chambers, mansion, monument, temples) | `SOON` |
| `BiomeEntered` première visite d'un biome de `RARE_BIOMES` / première visite d'un autre biome | `SOON` / `NEXT` |
| Casse de blocs posés par un autre joueur | agrégée par (casseur, propriétaire) sur 10 s → un `SOON` « GRIEF » |
| `ExplosionHappened` hors Narrateur touchant des blocs de joueur ou près d'un joueur | `SOON` |
| `BlockBroken` de `diamond_ore`, `deepslate_diamond_ore`, `ancient_debris`, `emerald_ore` ; `LootChestOpened` ; `Teleported` ; `DimensionChanged` ; `PlayerRespawned` | `NEXT` |
| Tout le reste | `BATCH` |

Regroupement (`WakeScheduler.kt`) : `IMMEDIATE` → réveil `director.chatDebounceMs` (1 500 ms) après le dernier message
de chat, au plus 4 s après le premier ; `SOON` → 3 s après le dernier, au plus 10 s après le premier ; `TaskDone`,
`ReminderDue` → comme `SOON` ; `OperatorWhisper` → comme `IMMEDIATE`. Les `NEXT` ne réveillent jamais. Chaque réveil et
chaque classement `SOON` ou `IMMEDIATE` → décision `wake` / `salience` avec la raison. Les `BATCH` ne produisent pas de
décision individuelle.

**Budgets** (relecture de M2, constats 14 et 26 ; `handoff/M2-fix-EF.md` fait foi) :
- **par joueur** : un joueur réveille le Directeur à l'immédiat 6 fois au plus par fenêtre glissante de 10 min
  (`Salience.IMMEDIATE_PER_PLAYER`), chat adressé et prières confondus ; au-delà, son message est posté en `SOON`
  (annotation gardée) et la décision est `salience throttled` ;
- **global** : `director.turnsPerHour` (défaut 30, de 1 à 600) tours **commencés** par heure glissante, tous
  déclencheurs confondus (`TurnBudget`, `WakeScheduler.kt`). Une fois le budget atteint, seuls les éléments `IMMEDIATE`
  réveillent (chat adressé, prières dans le budget de leur auteur, consignes d'opérateur) ; un événement saillant est
  posté en `SOON` avec la décision `salience throttled` et attend qu'un tour sorte de l'heure (réexamen toutes les 60 s)
  ou part avec le prochain réveil ; les battements sont sautés (`salience throttled`, sujet `heartbeat`), sans consommer
  leur fenêtre d'activité. En mémoire : un redémarrage remet les budgets à zéro. `/narrator status` affiche les tours de
  l'heure et ce qu'il en reste (`DirectorStatus.turnsThisHour`, `turnsPerHour`, lot G).

**Battement** : tant qu'au moins un joueur est en ligne et que le Directeur est `IDLE`, prochain battement à un instant
tiré dans `director.heartbeatMinutes` **après la fin du dernier tour** (un tour récent vaut un battement). Sa valeur
(`WakeScheduler.heartbeatWorth`) :
- sans Jev (l'heuristique dit toujours 1,0) : ce que valent les éléments saillants **qui attendent depuis le dernier
  tour** : 0,125 par ligne de chat entre joueurs (4 réveillent), 0,25 par autre événement `NEXT` (2 réveillent), 1 pour
  un élément qui réveille seul ; plafond 1 ;
- avec Jev : son verdict, mais jamais en dessous de ce qui attend (Jev ne lit que le résumé d'activité, pas le chat) ;
- un résumé d'activité vide n'est pas un saut si des éléments saillants attendent : le bloc `<heartbeat>` est alors
  vide et les éléments partent dans `<events>`.

`worth` < 0,5 → ignoré (décision `worth 0.25 by 1 salient item waiting`…), sinon réveil `trigger = heartbeat`.

### 12.4 `ActivityDigest`

Agrégateur en mémoire, alimenté par **tous** les événements (pas seulement `BATCH`), par joueur et par tranches d'une
minute sur 10 min : blocs cassés (5 premiers types, minerais avec plage de y), blocs posés (3 premiers types et lieu),
kills par type, dégâts reçus et causes, morts, distance parcourue (d'après `PositionSampled`), biomes et structures
visités, part du temps sous terre, minutes d'inactivité, artisanat et échanges notables. Deux lectures :
`recent(player, 5 min)` pour la situation et `list_players`, `sinceLastHeartbeat()` (puis remise à zéro) pour le
battement. Une ligne anglaise par joueur, ≤ 200 caractères.

### 12.5 Machine à états

| État | Sens | Sorties |
|---|---|---|
| `DISABLED` | pas de config valide ou pas de clé LLMGW | `SettingsChanged` avec client → `IDLE` |
| `IDLE` | rien à faire | signal réveillant → `WAITING` ; battement dû → `RUNNING` ; chapitre à clore et moment calme → `CLOSING` |
| `WAITING` | réveil programmé (regroupement) | échéance → `RUNNING` |
| `RUNNING` | tour en cours | fin de tour → `IDLE`, `WAITING` (signaux en attente) ou `CLOSING` ; erreurs → `BACKOFF` / `BLOCKED` |
| `CLOSING` | résumé de fin de chapitre | fin → `IDLE` (sans chapitre ouvert) |
| `PAUSED` | `/narrator pause` (le tour en cours finit d'abord) | `Resume` → `WAITING` (réveil `resume`) |
| `BACKOFF` | échec transitoire | échéance → `WAITING` |
| `BLOCKED` | budget épuisé (jusqu'à `resetAt`) ou clé refusée (jusqu'au rechargement) | échéance ou `SettingsChanged` → `WAITING` |
| `STOPPED` | arrêt du serveur | – |

Pendant `PAUSED`, `BACKOFF` et `BLOCKED`, la boîte continue de se remplir : le chat adressé est gardé en entier, le reste
est résumé par `ActivityDigest` ; au réveil suivant, une note moteur dit combien de temps le Narrateur a été muet et
pourquoi.

### 12.6 Messages envoyés au modèle

Anglais, compact, **horodatage relatif** à l'instant `now` de l'en-tête. Le texte des joueurs est une citation :
guillemets, `"` échappé, retours à la ligne remplacés par un espace, 300 caractères au plus, et **`<` `>` remplacés par
`‹` `›`** pour qu'aucun joueur ne puisse fabriquer une balise `<operator>` ou `<engine>`. Identifiants sans
`minecraft:` ; dimensions `overworld`, `the_nether`, `the_end` ; durées `36s`, `4m05s`, `1h12m`, `2d4h` (`tool/ToolText.kt`, lot G).

**Message de réveil** (un seul bloc de texte ; au premier tour d'un chapitre, précédé du briefing, §12.11) :

Pour un battement, le bloc `<events>` est remplacé ou complété par :


**Événements injectés entre deux appels d'outils** : dans le message `user` qui rend les `tool_result`, **après tous les
blocs `tool_result`** (l'API exige qu'ils viennent en premier), un bloc de texte :

```
<new_events now="21:33:02">
[-4s] CHAT Mimosa (to you 0.88, mocking_playful, question): "et moi alors ?"
</new_events>
```

Seuls les signaux `IMMEDIATE`, `SOON` et `NEXT` arrivés depuis la requête précédente sont injectés ; pas de situation
ni de résumé en cours de tour. Les identifiants injectés vont dans `turns.injected_events`.

` !manipulation 0.81` ajouté si ≥ 0,5 ; `(between players)` pour un message non adressé.

### 12.7 Consignes du moteur et de l'opérateur (`OperatorChannel`)

```kotlin
data class OperatorNote(val source: String /* "operator:<name>" | "engine" */, val text: String)
```

`OperatorChannelMode` (`SYSTEM_MESSAGE`, `USER_TAG`) est défini en T01 dans `config/NarratorConfig.kt`, pas dans
`agent/` : c'est un type de la configuration (`director.operatorChannel`, §15), pas de la conversation, et
`config/NarratorConfig.kt` en a besoin dès sa validation (`DirectorConfig.channelMode`). `agent/OperatorChannel.kt`
(T11) l'importe pour rendre les notes ci-dessous ; il ne le redéfinit pas.

- `SYSTEM_MESSAGE` (défaut) : les notes d'un envoi forment **un** message `role: system` (`MessageParam.Role.SYSTEM`
  existe dans le SDK 2.65.0 **(javap)**) placé **juste après** le message `user` de l'envoi, en dernière position de la
  requête. C'est la seule place autorisée : un message `system` en cours de conversation doit suivre un message `user` et
  être le dernier ou suivi d'un tour `assistant`. Contenu : `Operator Clement: …` / `Engine: …`, une note par ligne.
  **Vérifié par `liveTest` (25/09/2026, §0 n°14 et §20 n°1)** : un message `system` placé ainsi est accepté et
  suivi par `claude-opus-5-5` derrière le serveur LLMGW du propriétaire (pas de 400), ce qui confirme ce mode
  comme défaut viable contre ce serveur.
- `USER_TAG` (repli) : les notes deviennent un bloc de texte à la fin du message `user` :
  `<operator from="Clement">…</operator>` ou `<engine>…</engine>`. Le prompt du Directeur dit que ces balises font
  autorité ; l'échappement du §12.6 empêche un joueur de les imiter.
- **Repli automatique** : une 400 dont le message mentionne le rôle `system` bascule le mode en `USER_TAG` pour la durée
  du runtime (décision `operator`, `WARN`) et l'envoi est refait une fois. Le changement de mode ne touche pas
  l'historique déjà validé. Ce repli reste dans la configuration et le code : il ne s'est pas déclenché pendant
  `liveTest` (le mode `SYSTEM_MESSAGE` par défaut passe déjà contre le serveur du propriétaire), il protège contre
  une autre passerelle ou un changement de comportement de celle-ci.
- Notes du moteur utilisées en M2 : consigne opérateur (`/narrator whisper`), reprise après pause, blocage ou refus,
  limite d'étapes, clôture de chapitre. Les refus d'action des garde-fous ne sont **pas** des notes : ils arrivent dans le
  `tool_result`.

### 12.8 Le moteur de conversation (`AgentLoop`, T11)

**Sémantique des envois** (précise l'acquis M0 n°6) :

```kotlin
/** What one request adds after the history. It joins the history only with a successful reply. */
data class Pending(val blocks: List<ContentBlockParam>, val notes: List<OperatorNote>)

// llm/Conversation.kt (T11)
class Conversation(val role: Role, val label: String, val system: List<TextBlockParam>, val tools: ToolSet, val id: String) {
    val messages: List<MessageParam>                     // committed history only
}
// llm/ClaudeClient.kt (T11): the request is history + rendered pending; on a usable reply, the rendered pending
// messages and the reply are appended together; on refusal, truncation, error or cancellation, nothing is.
suspend fun ClaudeClient.send(conversation: Conversation, pending: List<MessageParam>, purpose: String): SendResult
```

Ainsi l'historique ne contient **jamais** de tour `assistant` vide ni de message `user` orphelin, et un envoi refusé peut
être refait avec un contenu différent sans « modifier » l'historique : rien n'en avait été validé. Deux règles de
`FakeAnthropic` strict sont ajustées par T11 : l'ajout seul se vérifie par rapport au **dernier échange réussi** de la
session (pas à la dernière requête), et les messages `system` en cours de conversation respectent la règle de placement.

```kotlin
data class TurnLimits(val maxSteps: Int, val hardSteps: Int = maxSteps + 2)

interface TurnHooks {
    /** Before each follow-up request: text blocks placed after the tool results, and notes. */
    fun afterTools(): Pending = Pending(emptyList(), emptyList())
    fun onReply(reply: Message, stats: CallStats, llmCallId: Long) {}
}

sealed interface TurnOutcome {
    val calls: Int; val toolCalls: Int
    data class Ended(override val calls: Int, override val toolCalls: Int, val acted: Boolean, val finalText: String) : TurnOutcome
    data class Refused(val pending: Pending, val category: String?, override val calls: Int, override val toolCalls: Int) : TurnOutcome
    data class Truncated(val pending: Pending, override val calls: Int, override val toolCalls: Int) : TurnOutcome
    data class Failed(val pending: Pending, val error: GatewayError, override val calls: Int, override val toolCalls: Int) : TurnOutcome
    data class StepLimit(val carry: List<ContentBlockParam>, override val calls: Int, override val toolCalls: Int) : TurnOutcome
    data class Cancelled(override val calls: Int, override val toolCalls: Int) : TurnOutcome
}

sealed interface GatewayError {
    data class Budget(val resetAt: Instant) : GatewayError
    data object Auth : GatewayError                                     // 401, 403
    data class BadRequest(val status: Int, val message: String) : GatewayError   // 400, 413
    data class SystemRoleRejected(val message: String) : GatewayError   // 400 about role "system"
    data object ContextExceeded : GatewayError                          // stop_reason model_context_window_exceeded, "prompt is too long"
    data class Transient(val kind: String, val message: String) : GatewayError   // 429, 529, 5xx, timeout, network, after ClaudeClient retries
}

class AgentLoop(services: NarratorServices, executor: ToolExecutor) {
    suspend fun runTurn(conv: Conversation, opening: Pending, caller: Caller, limits: TurnLimits, hooks: TurnHooks): TurnOutcome
}
```

Déroulé d'un tour :
1. Envoi `opening` (rendu par `OperatorChannel`). Chaque réponse → ligne `llm_calls` (résumé de réflexion compris,
   tronqué à 4 000 caractères) et `hooks.onReply`.
2. `stop_reason = tool_use` → `executor.runAll` → message `user` = tous les `tool_result` dans l'ordre + blocs de
   `hooks.afterTools()` ; notes par `OperatorChannel` ; envoi suivant.
3. `end_turn` → `Ended(acted = au moins un outil SPEECH, WORLD ou TASK réussi)`.
4. Après `maxSteps` appels, tout nouvel appel d'outil reçoit `is_error: "not executed: turn step limit reached; end your
   turn now"` et une note moteur ; à `hardSteps`, `StepLimit(carry = ces tool_result)` : le Directeur clôt le chapitre
   (`runaway_turn`) en rendant ces résultats dans la requête de résumé.
5. `refusal`, `max_tokens`, exceptions typées de M0 → `Refused`, `Truncated`, `Failed` avec le `Pending` **non validé**,
   que l'appelant peut renvoyer ou abandonner.

### 12.9 Erreurs de Claude : ce que fait le Directeur

`ClaudeClient` a déjà réessayé (acquis M0 n°7) : le Directeur ne relance jamais un appel dans la foulée, il décide de
l'**après**.

| Cas | Réaction |
|---|---|
| `Refused` sur un message de réveil | Rien n'est validé. Les signaux du réveil reviennent en tête de boîte, marqués `refusedOnce`, décision `refusal` (catégorie). Réveil suivant au plus tôt 30 s après, avec la note moteur « Your previous reply to these events was stopped by a safety filter (category X). Answer differently or stay silent. » Second refus sur les mêmes signaux → les messages de chat concernés sont écartés (décision, `WARN`), les autres gardés. |
| `Refused` en cours de tour (le `Pending` contient des `tool_result`) | Un seul renvoi immédiat : mêmes `tool_result`, nouveaux événements, même note moteur. Second refus → clôture du chapitre (`refusal`) ; les signaux sont remis dans la boîte pour le chapitre suivant. |
| `Truncated` (`max_tokens`) | Comme un refus, note « Your previous reply was cut off (max_tokens). Be much shorter. » |
| `Failed(Transient)` : 429, 529, 5xx, délai, réseau | `BACKOFF` 30 s, puis 60, 120… jusqu'à 10 min. Le `Pending` est gardé et reconstruit au réveil suivant avec les nouveaux événements (les `tool_result` en tête). Indicateur « réfléchit » coupé. Décision `backoff`. |
| `Failed(Budget(resetAt))` (402 `budget_exceeded`) | `BLOCKED` jusqu'à `resetAt` + 5 s. Opérateurs prévenus une fois dans le chat (anglais, `[Narrator] LLMGW budget exceeded until 22:00`), `WARN`, décision `budget`. Les tâches d'assistants en cours échouent (`failed: budget`). Au déblocage : réveil avec tout ce qui attend et la note de silence. |
| `Failed(Auth)` (401, 403) | `BLOCKED` jusqu'au prochain `/narrator reload` ; `ERROR`, opérateurs prévenus. |
| `Failed(SystemRoleRejected)` | Bascule `USER_TAG` (§12.7) et renvoi une fois. |
| `Failed(BadRequest)` | Défaut de construction de la requête : `ERROR` avec l'identifiant de requête (`request-id`, sinon `X-Cpa-Trace-Id` — LLMGW ne relaie pas `request-id`, vérifié par `liveTest`, §0 n°11), clôture du chapitre sans résumé (`bad_request`), signaux remis en boîte ; nouveau chapitre au réveil suivant. |
| `Failed(ContextExceeded)` | Clôture du chapitre sans résumé (`context_exceeded`). |
| `Cancelled` (arrêt du serveur) | Rien n'est validé ; tour `cancelled`, chapitre `shutdown`. |

### 12.10 Chapitres (T19)

- **Ouverture** au premier réveil sans chapitre ouvert : `Conversation(role = director, label = "Chapter N",
  system = [prompt director.md], tools = ToolCatalog.toolSetFor(director, env), id = "director-<8 hex>")`, ligne
  `conversations`, décision `chapter opened`. Le premier message contient le briefing puis le réveil.
- **Figé** : prompt système, outils et mode du canal opérateur ne changent pas pendant un chapitre.
- **Seuils** : `contextTokens` du dernier appel (entrée + lectures + écritures de cache) ≥ `director.chapterTokenLimit`
  (150 000) → clôture au prochain moment calme (`IDLE`, aucun signal réveillant, 20 s depuis le dernier tour) ;
  ≥ `director.chapterHardLimit` (180 000) → clôture dès la fin du tour.
- **Autres clôtures** : serveur vide depuis `director.emptyServerCloseMinutes` (10), `/narrator reload` ayant changé le
  prompt ou le canal (au moment calme), `/narrator chapter close`, erreurs du §12.9.
- **Clôture avec résumé** (`CLOSING`) : un envoi sur la conversation du chapitre (cache chaud : seul le message de
  clôture est nouveau), avec pour note moteur le texte de `prompts/chapter_summary.md` : résumé **factuel, à la troisième
  personne**, sans la voix du Narrateur (`MEMOIRE.md` §1.7), dans la langue de `language`, 400 mots au plus : ce qui s'est
  passé, ce que le Narrateur a dit, promis, infligé et accordé, avec qui, ce qui reste en cours. Si la réponse appelle
  des outils, ils reçoivent `is_error: "tools are disabled while the chapter closes"` et la demande est répétée (deux fois
  au plus). Le texte final va dans `conversations.summary` (4 000 caractères au plus). Échec → résumé nul, clôture
  quand même.
- **Arrêt du serveur** : pas de résumé (§2.4). Le briefing suivant l'indique et compense par le chat et les actions
  récentes, qui sont dans le Journal. La consolidation des chapitres interrompus revient au Chroniqueur (M3).

Premier bloc du premier message d'un chapitre. Sections à budget fixe (M3 y ajoutera Grimoire, fiches, canon et

```
</players_recent>

</your_recent_actions>

```

| Section | Source | Budget |
|---|---|---|
| Chapitres précédents | `conversations` (3 derniers du Directeur) | 3 × 800 tokens |
| Monde | `oracle/WorldSnapshot` (thread serveur) | 1 ligne |
| Joueurs en ligne | `PlayerStates` + `ActivityDigest` | 1 ligne par joueur |
| Joueurs récents | `sessions` des 24 dernières heures | 10 lignes |
| Chat récent | `chat_log`, 30 dernières minutes, 40 lignes au plus, répliques du Narrateur comprises, **jamais les messages privés** (§6.4) | 40 lignes |
| Dernières actions | `narrator_actions`, 20 dernières | 20 lignes |
| État du moteur | `Guards.activeOn`, quotas, `Workers`, rappels | 15 lignes |

Total ≤ 10 000 tokens (estimation 3,5 caractères par token, vérifiée par test). Les lectures de base passent par
`journal.barrier()` puis `journal.read` (le chat de la dernière seconde est donc inclus). **Une source en échec n'est
jamais passée sous silence** : sa section contient `(unavailable: <raison>)` et une ligne `ERROR` est loguée ; une
source vide le dit (`(no chat in the last 30 minutes)`). C'est la leçon de la v1, où le briefing était construit avec
des entrées vides sans que personne ne le voie.

### 12.12 Indicateur « le Narrateur réfléchit »

Quand un réveil contient du chat adressé ou une prière, les auteurs reçoivent dans leur barre d'action le texte
`UiTexts["narrator.thinking"]`, renouvelé toutes les 2 s tant que le tour tourne, et effacé dès qu'une réplique leur
parvient (abonné synchrone à `NarratorSpoke`) ou à la fin du tour. Désactivable (`director.thinkingIndicator`).

## 13. Les assistants (T20)

- **`Workers`** (`agent/Workers.kt`) : file de tâches, `workers.maxConcurrent` (3) en parallèle, chacune dans sa
  coroutine de `runtime.scope`. Identifiant `T-<task_id>`, ligne `tasks` à chaque changement d'état.
- **Conversation d'une tâche** : `Conversation(role, "Task T-12 (analyst)", system = [prompt analyst.md],
  tools = toolSetFor(analyst))`, identifiant de conversation propre (`analyst-<8 hex>`, en-tête
  `X-Narrator-Conversation`) ; l'`X-Session-ID` est celui du rôle (`narrator2-analyst`), commun à toutes les tâches pour
  qu'elles relisent le préfixe en cache (lot G, §20 n° 12). Premier message :
  `<task id="T-12" from="director">brief</task>` + `<context now=… players_online=…/>`. Tour unique par `AgentLoop`
  avec `workers.maxSteps` (15) et une échéance `workers.timeoutSeconds` (180). Le texte final (`Ended.finalText`, 3 000
  caractères au plus) est le résultat.
- **Retour au Directeur** : `DirectorSignal.TaskDone` (urgence `SOON`), rendu `TASK T-12 analyst done in 41s: "…"`
  (résultat complet sur les lignes suivantes, indenté). Échec, délai ou annulation : `TASK T-12 analyst failed: <raison>`.
- **Erreurs** : pas de relance ; refus ou 400 → tâche `failed` avec la raison ; 402 → `failed: budget`.
- **Annulation** : `tasks(cancel)` ou arrêt du serveur → `Job.cancel()` (le flux est fermé, rien d'ajouté).
- **L'Analyste** répond aux questions sur l'historique à partir du Journal et de l'Oracle, en lecture seule ; il rend
  des faits chiffrés et datés, pas de prose dans la voix du Narrateur. L'Éclaireur (`scout`) arrive en M4 avec les
  mécaniques qui en ont besoin (arènes, lieux de pièges) ; il réutilisera ce moteur sans changement.

## 14. Traces et consultation

### 14.1 Le log du serveur

Lignes courtes, anglaises, préfixées par le tag (`core/Log`) ; niveau par tag dans `logging.levels`.

### 14.2 Les transcriptions

`trace/Transcripts` (M0) garde son format ; T11 ajoute :
- le rendu du `Pending` **avant** l'envoi, titré `SENT` ; puis `COMMITTED` avec la réponse, ou `NOT COMMITTED
  (refusal | max_tokens | error | cancelled)` : le fichier montre tout ce qui a été tenté, l'historique réel reste lisible ;
- les messages `system` en cours de conversation, titrés `OPERATOR / ENGINE NOTE`.

T18 et T19 ajoutent des notes (`Transcripts.note`) : déclencheur de chaque tour avec son `turn_id`, ouverture et clôture
de chapitre, bascule du canal opérateur. Le chemin du `.md` est enregistré dans `conversations.transcript`.

### 14.3 Les tables de traces

- `llm_calls` : une ligne par appel Anthropic, construite depuis le `CallStats` enrichi de M0 (identifiant de requête et
  de message, tentatives, TTFT, horodatages, tokens, raison d'arrêt, catégorie de refus, erreur et statut HTTP) plus le
  résumé de réflexion ; une ligne par appel Jev (`provider = 'jev'`).
- `tool_calls` : une ligne par appel d'outil (§8.4).
- `turns`, `conversations`, `tasks` : insertion puis mise à jour (§5.3).
- `engine_decisions`, par `kind` : `wake` et `salience` (réveils, urgences, verdicts de tri), `heartbeat` (réveil ou
  ignoré, score), `guard` (refus avec la règle), `death_guard` (comptée, empêchée), `ledger` (appliqué, expiré, rendu),
  `chapter` (ouvert, marqué, clos, résumé), `budget`, `backoff`, `refusal`, `operator` (pause, reprise, whisper, say,
  protect, sql, bascule du canal), `reload`, `journal_health`, `tool_catalog`.

### 14.4 Consulter : `/narrator trace`, `/narrator why`, `/narrator status`

Toutes ces commandes attendent `journal.barrier()` (au plus une seconde) puis lisent la base : un seul chemin de code,
et le tour qui vient de finir est visible.

```
/narrator trace [n]              # n derniers tours (5 par défaut) :
                                 #   #42 21:32:41 chat Bartok → acted · 3 calls · say, apply_effect · 8.1 s · 61k ctx
/narrator trace turn <id>        # un tour : événements du réveil et injectés (rendus), résumés de réflexion,
                                 #   chaque outil (arguments abrégés, statut, résultat abrégé), répliques
/narrator trace task <id>        # une tâche : brief, statut, durée, résultat, chemin de la transcription
/narrator why                    # dernier tour ayant agi (outil SPEECH ou WORLD réussi) : déclencheur,
                                 #   résumé de réflexion de chaque appel, actions ; chemin de la transcription
/narrator status                 # M0 + état du Directeur, chapitre et contexte, file de la boîte, tâches,
                                 #   blocage ou backoff, canal opérateur, Jev (actif, repli, disjoncteur),
                                 #   santé du Journal (taille, pertes, dernier flush), chaos
```

La sortie tient en 20 lignes grises dans le chat ; au-delà, elle est tronquée avec le chemin de la transcription.

anglais, et « prier le Narrateur-dieu » est dans le ton. Le message n'est pas diffusé ; l'auteur voit
`UiTexts["pray.sent"]` ; l'événement `ChatMessage(PRAY)` réveille le Directeur. Limite : une prière toutes les 10 s par
joueur.

`/narrator say` publie `NarratorSpoke(OPERATOR, operator = <nom>)` (la réplique s'affiche comme une réplique normale du
Narrateur et le Directeur l'apprend au réveil suivant). `/narrator whisper` poste `OperatorWhisper`.

## 19. Écarts par rapport à l'architecture (reportés dans `ARCHITECTURE.md`)

1. **Cycle de vie** : le mod, le serveur et les réglages ont trois durées de vie distinctes ; `/narrator reload` ne
   remplace que les réglages ; arrêt en deux temps (`SERVER_STOPPING`, `SERVER_STOPPED`).
2. **Schéma** : table `chat` à part (canaux `public`, `pray`, `whisper`, `narrator`, `operator`) ; plus de table
   `narrator_actions` (vue sur `tool_calls`) ; nouvelles tables `player_names`, `turns`, `conversations`, `tasks`,
   `chat_signals` ; pas de contrainte sur les grandes tables ; identifiants attribués par le code.
3. **État cohérent avec le monde dans le monde** : index des blocs posés (avec le poseur), lieux visités, état des
   garde-fous et échéance des créatures sont des pièces jointes Fabric, pas des lignes DuckDB.
4. **Pas d'outil `sql_schema`** : le schéma généré est la description de `sql`, et la macro `columns()` donne le détail.
5. **Outils** : 32 outils en M2 ; `world_effect` éclaté en six outils ; `remind_me` remplace les relances ; barre de boss
   en M4 ; téléportation dans la même dimension en M2 ; pas de `strict: true`.
6. **Canal privé** : `/pray` au lieu de `/narrateur`.
7. **Assistants** : l'Analyste seul en M2 ; l'Éclaireur arrive en M4.
8. **Consignes** : messages `system` en cours de conversation avec repli `USER_TAG` réglable et automatique.
9. **Chapitres** : seuil souple (clôture au moment calme) et seuil dur ; résumé factuel dans `conversations.summary` ;
   pas de résumé à l'arrêt du serveur.
10. **Messages au modèle** : en anglais, horodatage relatif (l'exemple français de l'architecture est remplacé).
11. **Règles du moteur** : tableau des composants, plafonds par niveau de chaos, quota de morts mesuré en temps joué.
12. **Jev** : 9 questions par message (les signaux de personnalité sont stockés dès M2 pour M3) ; questions en anglais ;
    heuristiques françaises dans un fichier de données.
13. **Configuration** : sections `journal`, `observer`, `director`, `workers`, `safety`, `jev`, `language`, `chaos`
    réintroduites avec leur jalon.
14. **Rétention** : rien n'est supprimé ; `CHECKPOINT` après chaque sauvegarde du monde.
